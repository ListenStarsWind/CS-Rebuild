一开始我对二分查找的理解其实比较表面：对于一组有序数据，每次取中间位置，根据目标值与中间值的关系，一次排除近乎一半的数据，因此把查找复杂度从线性级降低到对数级。

这种理解当然不能说错，但它只是二分查找最具体、最简单的一种表现形式。

继续往下看之后，我发现二分查找真正依赖的并不是“数组”，甚至也不只是“数据本身有序”，而是我们能否在某个有序搜索空间中构造出一个具有单调性的判定命题。

也就是说，对于搜索空间中的每一个候选值 xx，我们定义一个命题 P(x)P(x)。如果这个命题随着 xx 的变化呈现出类似：

```text
F F F F F T T T T T
          ↑
```

或者：

```text
T T T T T F F F F F
          ↑
```

这样的结构，那么二分查找真正寻找的，其实就是这个命题由假变真，或者由真变假的分界点。

这样一来，传统的“在有序数组中查找某个值”实际上只是这个模型的一个特例。

例如在升序数组中定义：

```c
P(i) = a[i] >= target;
```

由于数组本身有序，这个命题对于下标 `i` 就具有单调性。于是我们真正寻找的是“第一个使 `a[i] >= target` 成立的位置”。这也正是 `lower_bound` 的本质。

所以，与其说二分查找是在“找一个值”，不如说它是在寻找某种性质发生变化的边界。

这也让我重新理解了二分代码中最容易出错的 `+1`、`-1` 问题。

以前看二分代码时，很容易纠结到底应该写：

```c
left = mid + 1;
```

还是：

```c
right = mid - 1;
```

又或者：

```c
right = mid;
```

但这些实际上不应该靠记模板。

真正的判断依据只有两个问题：

第一，当前的判定结果说明目标边界位于 `mid` 的哪一侧？

第二，`mid` 本身还有没有可能就是答案？

如果 `mid` 已经被证明绝对不可能是答案，就应该把它排除，因此会出现 `mid + 1` 或 `mid - 1`。

如果 `mid` 自己仍然可能就是那个分界点，就必须保留它，因此只能写成 `left = mid` 或 `right = mid`。

所以这些看起来琐碎的边界处理，其实是在用代码表达严格的逻辑推导，而不是某种固定语法。

进一步想，二分查找真正困难的地方其实也不是它的原理。

原理本身很简单：每次利用判定结果排除一半左右的搜索空间。

真正困难的是抽象。

现实问题通常不会直接告诉我：

“这里有一个单调数组，请使用二分。”

更多时候，题目可能是在问：

- 最短需要多少时间；
- 最少需要多大的容量；
- 最快需要多高的速度；
- 最大能够切多长；
- 最远能够保持多少距离；
- 某个方案最小做到什么程度才可行。

这时真正需要做的，是从现实问题中找出一个适合参数化的量 xx，然后把原来的“求最优答案”转换成一个更容易判断的问题：

> 如果答案暂时假设为 xx，这个方案是否可行？

也就是说，把优化问题转换成判定问题。

例如原问题是：

> 最小需要多大的机器速度才能按时完成任务？

我不一定直接去计算这个最小速度，而是定义：

```c
P(v) = 速度为 v 时，能否按时完成任务;
```

如果速度为 `100` 时可以完成，那么 `101`、`102` 一般也都可以完成。

于是就形成了：

```text
F F F F F T T T T T
          ↑
```

我要寻找的就是第一个可行的速度。

反过来，如果问题是：

> 一根木头最多能够切成多长的等长木段，同时保证至少得到 k 段？

就可以定义：

```c
P(len) = 按照长度 len 切割时，能否得到至少 k 段;
```

如果长度 `10` 可以，那么 `9`、`8`、`7` 当然也可以。

因此会形成：

```text
T T T T T F F F F F
          ↑
```

我要寻找的是最后一个可行长度。

到了这里，所谓“二分答案”其实就很清楚了。

它并不是某种和普通二分完全不同的新算法，而只是把搜索对象从“数组下标”扩展成了“答案空间”。

因此，我现在认为二分查找真正值得记住的思维链应该是：

```text
现实问题
↓
找出一个可以参数化的量 x
↓
把“求最优值”转换成“给定 x 是否可行”
↓
分析这个判定命题是否具有单调性
↓
如果存在真假分界，就寻找这个边界
↓
最后才是写二分代码
```

而且还不能只满足“有单调性”。

一个有价值的二分建模通常还需要满足：给定一个候选值 xx 后，`P(x)` 本身能够比较高效地判断。

否则即使理论上可以二分，如果每次判断候选答案都极其昂贵，甚至比直接求解还麻烦，那么这种转换也没有太大意义。

所以现在看来，二分查找真正需要识别的是这样一种结构：

```text
有序的搜索空间
+
可以构造单调判定命题
+
判定候选答案是否可行比较容易
```

一旦这几个条件同时出现，就应该意识到这里很可能存在二分的空间。

因此，二分查找最大的难度并不在“取中点”“左右移动边界”这些实现细节上，而在于能否从具体问题中抽象出那个正确的命题，并看出它背后隐藏的单调性。

从这个角度来说，“二分查找”这个名字其实有些容易让人把注意力局限在“查找某个值”上。

我更愿意把它理解成：

> 利用单调判定，对有序搜索空间进行边界定位。

而“在有序数组中查找某个元素”，只是这个思想最简单、最直观的一种实例。

## 附录：二分查找相关命名约定

为了让代码本身能够直接体现“单调判定 + 边界搜索”的思维模型，二分相关代码不采用过度简写的竞赛式命名，而尽量使用能够暴露语义和算法角色的名称。

### 一、搜索区间

对于二分过程中不断收缩的当前搜索区间，统一使用：

```c
left
right
mid
```

例如：

```c
int left = min_speed;
int right = max_speed;

while (left < right) {
    int mid = left + (right - left) / 2;
}
```

这里需要区分两类概念：

```text
min_speed / max_speed
```

描述的是问题本身允许的搜索范围；

而：

```text
left / right
```

描述的是算法运行过程中当前仍然可能包含答案的区间。

因此，不建议把所有变量都简写成：

```c
l
r
m
```

在竞赛代码中这种写法没有问题，但在系统复习和长期维护代码中，它几乎不携带额外语义。

------

### 二、判定命题

二分真正依赖的不是数组，而是一个具有单调性的判定命题。

在纯理论或通用模板中，可以使用：

```c
bool predicate(int value);
```

其中 `predicate` 直接表示“谓词”或“判定命题”。

如果当前问题属于典型的“二分答案”，即判断一个候选答案是否可行，则使用：

```c
bool is_feasible(int value);
```

例如：

```c
bool is_feasible(int capacity);
```

不过，在具体问题中，优先使用具有实际语义的命题名称，而不是泛化名称。

例如：

```c
bool can_finish(int speed);
bool can_allocate(int capacity);
bool can_cut(int length);
bool can_place(int distance);
bool is_valid(int threshold);
```

因此判定函数的命名优先级可以理解为：

```text
具体语义命题
    >
is_feasible
    >
predicate
    >
check
```

`check()` 虽然常见，但它只表达“检查某件事”，并没有告诉读者到底在检查什么，因此只适合非常短的临时代码。

------

### 三、抽象边界函数

如果代码本身就是为了展示二分的理论模型，则直接使用“真假边界”命名。

寻找：

```text
F F F F T T T T
        ↑
```

时使用：

```c
find_first_true()
```

寻找：

```text
T T T T F F F F
      ↑
```

时使用：

```c
find_last_true()
```

例如：

```c
int find_first_true(int left, int right)
{
    while (left < right) {
        int mid = left + (right - left) / 2;

        if (predicate(mid))
            right = mid;
        else
            left = mid + 1;
    }

    return left;
}
```

这两个名称直接体现了二分的本质：

```text
寻找单调谓词的分界点。
```

------

### 四、数组边界查找

对于具体的有序数组边界问题，可以采用：

```c
find_first_ge()
find_first_gt()
find_last_le()
find_last_lt()
```

分别表示：

```text
第一个 >= target
第一个 >  target
最后一个 <= target
最后一个 <  target
```

例如：

```c
size_t find_first_ge(
    const int arr[],
    size_t size,
    int target
);
```

如果是在 C++ 中，也可以直接采用 STL 的术语：

```text
lower_bound
upper_bound
```

但在纯 C 学习代码中，`find_first_ge()` 这类名字往往更直接，不需要额外依赖术语记忆。

------

### 五、二分答案函数

如果二分只是实现手段，而函数真正的语义是求某个最优值，那么函数名称应该描述“求什么”，而不是“使用了什么算法”。

例如推荐：

```c
find_min_required_speed()
find_min_capacity()
find_max_cut_length()
find_max_distance()
```

而不推荐：

```c
binary_search_speed()
binary_search_capacity()
```

原因是：

```text
二分查找属于实现方式，
最小速度、最大长度才是函数真正提供的功能。
```

如果以后更换算法，函数语义仍然不会发生变化。

------

### 六、候选答案变量

在实际问题中，不应把所有候选值都统一命名为：

```c
x
```

而应直接使用其实际含义：

```c
speed
capacity
distance
length
time
days
workers
load
threshold
```

例如：

```c
bool can_finish(int speed);
```

但在二分循环内部，当前候选值仍然可以保留 `mid`：

```c
int mid = left + (right - left) / 2;

if (can_finish(mid))
    right = mid;
```

这里没有必要进一步写成：

```c
mid_speed
```

因为上下文已经足够明确。

------

### 七、最终答案

如果需要额外保存最终结果，优先使用具体问题中的语义名称。

例如：

```c
int min_speed = left;
int max_length = left;
int min_capacity = left;
```

只有在通用算法代码中，才考虑：

```c
boundary
result
answer
```

推荐优先级为：

```text
具体语义名称
    >
boundary
    >
result
    >
answer
```

不建议在长期维护代码中大量使用：

```c
ans
```

------

### 八、整体命名层级

最终可以统一成下面这套结构：

```text
当前搜索区间
    left
    right
    mid

通用判定命题
    predicate

通用可行性判断
    is_feasible

具体判定命题
    can_xxx
    is_xxx

抽象边界搜索
    find_first_true
    find_last_true

有序数组边界
    find_first_ge
    find_first_gt
    find_last_le
    find_last_lt

答案空间搜索
    find_min_xxx
    find_max_xxx

问题域边界
    min_xxx
    max_xxx

最终结果
    直接使用具体问题中的语义名称
```

这套命名体系的目的并不是单纯追求“名字更长”，而是让代码本身能够暴露算法结构。

看到：

```c
if (can_finish(mid))
    right = mid;
else
    left = mid + 1;
```

就能够直接读出：

```text
当前在寻找最小可行解；
can_finish 是单调判定命题；
mid 可行时仍可能就是最小可行值，因此保留 mid；
mid 不可行时，它以及左侧区域都可以排除。
```

如果变量名和函数名能够直接帮助恢复这套推理过程，那么命名本身就是算法表达的一部分，而不仅仅是代码风格问题。
