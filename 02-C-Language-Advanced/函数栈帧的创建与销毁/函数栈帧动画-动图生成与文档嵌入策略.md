# 函数栈帧动画：动图生成与文档嵌入策略

> 本文记录《函数栈帧的创建与销毁》配图的制作原则、技术路线和验收方法。正文采用可自动播放的 GIF 动图，独立 HTML 提供逐指令交互。本文是制作规范与执行计划，不把尚未完成的动画写成既成成果。

## 一、目标与交付形式

函数栈帧的建立和销毁是随指令执行不断变化的过程。单幅静态图只能呈现某个时刻，难以直观展示 `%rsp`、`%rbp`、栈内存及控制流之间的因果关系。因此，正文配图以 **GIF 动图** 为主，配套提供 **HTML 交互动画**。

| 交付物 | 用途 | 阅读方式 |
| --- | --- | --- |
| 分阶段 GIF | 直接嵌入 Markdown，展示栈帧的动态变化 | Typora、GitHub 页面自动播放 |
| 完整 HTML 动画 | 暂停、单步、回退，查看每条指令前后的状态 | 浏览器打开独立文件 |
| Markdown 文章 | 解释指令含义、调用约定和观察结论 | Typora、GitHub 阅读 |

GIF 不需要 JavaScript，适合图床托管；HTML 需要独立运行，不应尝试将脚本直接塞进 GitHub Markdown。两者应当来自**同一套指令状态与时间轴**，避免出现内容不一致的两个版本。

## 二、事实依据：先记录真实执行，再制作动画

本次复现环境为 Ubuntu x86-64、Clang 21、C17、LLDB，遵循 System V AMD64 ABI。动画中出现的机器指令、地址、寄存器值、栈槽位置，必须以本次实际反汇编和调试观察为准。

1. 保存相关函数的完整反汇编，并明确所用的构建选项。尤其注意 UBSan 等插桩会改变指令序列与栈空间布局。
2. 记录关键指令执行前后的 `%rip`、`%rsp`、`%rbp`，以及必要的 `%rax`、`%rdi`、`%rsi` 等寄存器。
3. 记录实际发生的内存写入、读取、返回地址压栈和保存旧帧指针的操作。
4. 只有在调试证据充分时，才为栈槽赋予具体语义；否则标记为“编译器生成的临时栈槽”等，避免将推断说成 ABI 规则。
5. 地址是一次运行中的示例值，受到 ASLR 等因素影响；**相对偏移、对象大小、控制流和调用约定**才是文章主要解释对象。

本项目已经讨论过的 `main` 中 `[rbp-4]`，可标注为“编译器生成的返回值预留槽（4B，本次未参与最终返回值传递）”。它不等同于 ABI 规定的返回值位置：`int` 返回值通过 `%eax` 传递。

## 三、画面布局与表示约定

### 1. 栈内存为视觉主体

- **低地址在上，高地址在下**。栈向低地址增长时，`%rsp` 在画面中向上移动。
- 内存按真实字节跨度线性布局，不允许为了视觉效果改变对象所占字节数。
- 地址刻度与内存对象边界分开绘制。返回地址、旧 `%rbp` 各占完整的 **8 字节区域**，不能被 4 字节刻度切割成两个对象；`int` 变量各占 4 字节。
- 栈旁可使用由疏到密的细微方向标识，辅助辨认地址增大方向，但不能暗示地址刻度非线性。
- `%rsp`、`%rbp` 必须以箭头指向**准确的地址边界**；两者地址相同时，使用不同侧的箭头避免遮挡。
- `subq` 等仅修改栈指针的指令**不会自动清零内存**。新纳入栈帧范围的字节应显示为“原有内容／未展开”，直到实际写入发生。

### 2. 指令与寄存器

左侧展示真实反汇编，突出当前 `%rip` 对应指令；旁边展示关键寄存器状态。非核心寄存器可以放在次要区域，但不能省略理解当前动作所必需的寄存器。

在 `call` 前保留调用方上下文；执行 `call` 后，先表现返回地址入栈，再切换到被调用函数的反汇编，同时保留“返回后将执行的地址”提示。不得把调用前后的代码当作一条连续、没有跳转的指令流。

### 3. 动画与机器执行状态的关系

一条指令可以为了教学效果拆成“定位目标地址—指针移动—内存高亮—写入数值”等连续视觉过渡，但这些只是**同一条指令的动画分解**，不是额外的机器指令，也不代表调试器能够在这些中间画面停住。

指令完成后，画面必须与真实执行后的架构状态一致。不能凭空擦除旧内存、重置寄存器，或跳过实际执行过的指令而不作说明。

## 四、内容分段与动画节奏

不建议把整个 `main → Add → main → libc` 生命周期压成一张很长的 GIF。应按照逻辑阶段拆分，文章中的每一张图只承担一个明确的解释任务。

| 阶段 | 主要内容 | 当前状态 |
| --- | --- | --- |
| A. `main` 栈帧建立 | libc `call main`；`push %rbp`；设置帧指针；预留 16B；初始化栈槽与 `a`、`b`、`c` | 已有 HTML v4，已有 GIF 测试版 |
| B. `main` 调用 `Add` | 读取 `a`、`b`；写入 `%edi`、`%esi`；`call Add` 压入返回地址 | 待制作 |
| C. `Add` 栈帧建立 | 保存旧 `%rbp`；预留 32B；保存参数并初始化 `z` | 待制作 |
| D. `Add` 运算与检查 | 执行加法、UBSan 溢出检查、赋值 `z`、准备返回值 | 待制作 |
| E. `Add` 返回 `main` | `%eax` 携带返回值；恢复栈指针和旧帧指针；`ret` | 待制作 |
| F. `main` 后续执行及返回 | 保存 `c`、调用 `printf`、返回 `0`、销毁栈帧 | 待制作；`printf` 内部不必逐层展开 |

### 播放节奏

- 每条指令先突出显示，再播放其状态变化，最后短暂停留。
- `call`、`push`、`sub`、`ret` 等直接影响栈结构的指令应停留更久。
- 在每个阶段的起点和终点设置明显的观察停顿，循环回到开头时不应让画面突然跳变而造成误解。
- GIF 应有可辨认的阶段标题、当前指令及关键变化说明；不应保留 HTML 的“上一步”“下一步”等无效按钮。
- GIF 的时长与帧率按清晰度、文件大小和阅读负担实际调整，不预设固定秒数。

### UBSan 的适度折叠

`Add(10, 20)` 没有发生有符号加法溢出。自动播放可以将 UBSan 检查指令快速连续播放，但**所有实际执行的指令仍须在时间轴中出现**，相关寄存器和临时栈槽写入应保留。条件跳转所绕过的错误处理函数是**未执行分支**，应明确标注“本次未进入”，不能与“已执行但加速展示”混淆。

HTML 单步模式应仍能逐条观察 UBSan 检查，不受 GIF 的播放节奏影响。

## 五、推荐制作流程

1. **采集**：固定源码、编译选项和反汇编，使用 LLDB 复核关键状态。
2. **建模**：为每条实际执行的指令建立执行前状态、执行后状态和必要的视觉过渡。把数据状态与 UI 渲染分离。
3. **交互验收**：先制作 HTML，检查自动播放、下一步、上一步、暂停、重置和指令跳转；保证手动与自动模式使用相同的状态模型。
4. **生成动图**：使用与 HTML 相同的渲染状态，隐藏控制按钮，按预设时间轴逐帧采集画面，编码为循环 GIF。应优先考虑确定性逐帧渲染，而不是人工录屏后随意截取。
5. **视觉检查**：逐帧核对指令、地址、箭头、内存对象边界和文本；尤其检查 `call`、`push`、`sub`、`ret` 前后的状态。
6. **压缩与导出**：在保证文字可读的前提下优化分辨率、帧率、调色板和相邻重复帧；避免为了减小文件而牺牲关键状态的停留时间。
7. **文档验收**：上传图床，在 Typora 与 GitHub 分别检查自动播放、循环、清晰度、显示宽度和加载速度。

GIF 是索引色格式，最多使用 256 色的单帧调色板，因此灰度或低饱和度界面通常更容易控制体积。对于长动画，应优先**拆分阶段**，而不是一味降低画质。

## 六、Markdown 嵌入与图床管理

文章使用标准 Markdown 图片语法：

```markdown
![main 函数栈帧建立过程](https://你的图床域名/图片路径/main-stack-frame.gif)

[打开交互版：逐条观察 main 栈帧建立](./assets/main-stack-frame.html)
```

这里的图床地址仅是占位示例，正式发布时替换为实际上传后的链接。GitHub 上的相对 HTML 链接通常会打开文件页面，**不保证直接执行 HTML**；如需在线交互，应使用允许执行脚本的独立静态网页托管地址，或者提示读者下载 HTML 后在浏览器中打开。

建议文件命名稳定、使用 ASCII 名称，例如：

```text
assets/
  main-frame-create.gif
  main-call-add.gif
  add-frame-create.gif
  add-compute-ubsan.gif
  add-return.gif
  main-return.gif
  stack-frame-interactive.html
```

每个 GIF 都应保留对应的本地原始文件，图床只承担发布与分发；不应把图床链接当成唯一备份。更新动画时最好采用新文件名或版本后缀，避免 CDN 缓存导致 Typora 与 GitHub 显示旧版本。

## 七、验收标准

**技术正确性**：每条实际执行的指令都有对应状态变化；栈槽大小与地址边界正确；指针箭头不偏移；未执行分支不会被误画为已执行；函数返回遵循 ABI。

**交互正确性**：HTML 自动播放与手动单步结果一致；前进、后退和重置不会丢失状态；暂停后不会发生后台继续推进。

**动图正确性**：GIF 能自动循环；每个关键状态有足够停留时间；画面文字可读；不会出现错误的中间内存状态；循环边界明确。

**文档兼容性**：Typora 与 GitHub 均可正常显示和播放；图床链接稳定；图片尺寸与正文宽度协调；即使读者不打开 HTML，也能通过动图和正文理解主要过程。

## 八、当前制作决策

- `main` 栈帧建立的 HTML **v4 单步修复版**已由使用者验证交互正常，可作为后续动画的控制逻辑基准。
- 已导出 `main` 栈帧建立 GIF 测试版；其用途首先是验证 Typora / GitHub 的嵌入效果，不应把它视为完整函数生命周期的最终动图。
- 后续继续制作 `main → Add → main`，UBSan 检查适度加速，但不得跳过实际执行的指令。
- 正文不以静态关键帧作为主要配图；使用分阶段 GIF，HTML 作为补充观察工具。

**最终原则：真实执行决定内容，动画负责解释变化，GIF 负责文档阅读，HTML 负责精细观察。**
