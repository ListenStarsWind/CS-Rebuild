## 一、为什么重写

原文写于 2024 年，以 Visual Studio 2013、32 位 x86 环境中的 C 程序为对象，通过汇编和栈内存变化解释函数栈帧。新文章不是旧文的语言润色，也不是简单把 `ebp/esp` 换成 `rbp/rsp`，而是**重新选择观察问题的起点、叙述顺序和证据组织方式**。

新实验在 Ubuntu x86-64 上使用 Clang、C17、CMake + Ninja、LLDB，并启用 ASan/UBSan；实际观察范围比旧文更广，涉及 `main`、`Add`、`printf`、C 运行库及部分上下文保存和收尾路径。这些扩展是实验档案的价值，不等于全部都应进入正文。

重写的目标是：让掌握 C 语言基础的读者，借助真实机器指令、寄存器与栈内存变化，理解一次函数调用怎样建立执行环境、传递参数、计算、返回并恢复调用者状态；最后理解具体栈帧布局的实现边界。

## 二、读者定位与写作姿态

读者已理解 C 函数、参数、局部变量、返回值和基本指针概念，但不要求预先掌握汇编、ABI、LLDB、运行库或 Sanitizer。**降低知识门槛不等于降低技术严谨性，也不等于把读者当成没有 C 基础的人。**

采用自然、克制、问题驱动的叙述方式：从一个读者已经理解的 C 现象出发，遇到无法仅靠 C 语义解释的细节，再引入必要的机器层知识。不要在开头罗列术语；不要连续使用“那么究竟发生了什么”“让我们继续看”之类悬疑式套话；也不要用密集的“可能、通常、视情况而定”替代精确的适用范围。

优先采用“观察到什么 → 为什么会这样 → 它解决了什么问题 → 这一结论适用于哪里”的局部组织方式，但不要机械地把它写成每一节固定的四段模板。

## 三、全文的中心问题

以如下小程序作为叙述入口，代码与实验版本保持一致；正式写作时，应与实际编译使用的源码逐字核对，尤其是头文件、函数签名、初始化和输出：

```c
#include <stdio.h>

int Add(int x, int y)
{
    int z = 0;
    z = x + y;
    return z;
}

int main(void)
{
    int a = 10;
    int b = 20;
    int c = 0;

    c = Add(a, b);
    printf("%d\n", c);
    return 0;
}
```

开篇不讲栈帧定义，而是承认：从 C 语言层面，程序的结果一目了然。进一步追问：

1. `a`、`b` 的值怎样交给 `x`、`y`？
2. `Add` 怎样知道执行完应返回 `main` 的哪一处？
3. `z` 等局部数据怎样保存、使用？
4. 返回值怎样交回调用者？
5. 函数返回时，相关执行状态与栈内存怎样变化？

这些问题是文章的**叙事主线**，不是需要在开头一次回答的知识点清单。

## 四、正文的叙述架构（八阶段）

以下是**逻辑阶段**，不要求正式成文时恰好使用八个一级标题。可以合并、拆分标题，但不得破坏因果线索。

### 阶段一：从 `Add(a, b)` 提出问题

先展示程序及可预期结果，再把焦点从“算出多少”转移到“怎样完成调用”。简短说明 C 源代码、编译器生成的机器指令和调试观察之间的关系。不要把编译过程误写成“C 代码先被一个汇编程序执行，再由汇编器转换”等不准确说法。

**进入下一阶段的理由**：为了回答调用问题，需要先能读懂最低限度的机器状态。

### 阶段二：最低限度的观察基础

仅介绍即将使用的内容：指令顺序、寄存器、地址、栈向低地址增长、栈指针的含义；`rsp`、`rbp`、`rip` 以及后续出现的参数和返回值寄存器按需解释。必要时说明图中地址方向与每格表示的字节范围。

不写成独立的汇编、CPU 或 ABI 教程。**知识出现的时机应服从正在解释的指令。**

### 阶段三：观察 `main` 如何建立执行环境

以实际 `push`、`mov`、`sub` 等指令为证据，解释旧帧指针的保存、当前帧指针的建立、栈指针的变化、局部空间的预留与变量初始化。将 `a`、`b`、`c` 的实际位置与稍后的 `Add` 调用联系起来，避免读者觉得离开了开篇问题。

在这一阶段结束附近**首次给出阶段性定义**：本次实验中，一次函数执行使用并组织的相关栈空间，可称为该函数的栈帧；它可能涉及返回地址、保存的状态、局部数据和临时值。不要将“栈帧严格等于 `rbp` 与 `rsp` 之间”作为普遍定义，也不要暗示返回地址一定落在 `sub` 预留的局部空间中。

这里还应轻轻埋下伏笔：`main` 也有调用者，栈上的返回地址与这一事实有关。**暂不展开 glibc 启动流程。**

### 阶段四：回到 `Add(a, b)` 的调用

顺着 `main` 中已初始化的 `a`、`b`，观察参数怎样进入本实验平台的参数寄存器，`call` 怎样保存返回位置并转移控制流，以及 `Add` 怎样建立自己的执行环境。

明确：当前实验采用 x86-64 System V ABI；前两个 `int` 参数通过相应的参数寄存器传递，并非像旧版 32 位实验那样直接以“依次压栈”作为主线。只做必要的旧文对照，不展开各平台调用约定大全。

### 阶段五：`Add` 的内部计算

结合实际内存图解释参数副本、局部变量 `z`、临时结果和加法。要承认当前实验启用了 UBSan，故存在额外的溢出检测及临时数据操作。正文仅说明它们为何出现、是否改变本次正常计算结果；`OF`、`seto`、分支及完整临时槽位的分析放附录。

**不得把 Sanitizer 插入的指令伪装成普通 C 加法必然生成的指令，也不得为了正文简洁而悄悄删除真实反汇编中会影响理解的步骤。**

### 阶段六：`Add` 返回 `main`

观察返回值怎样进入约定的返回值寄存器、栈指针如何恢复、旧帧指针如何恢复、`ret` 如何取得返回地址并把控制流交还调用者。随后观察 `main` 接收结果并继续执行。

特别强调：**栈空间不再归当前函数使用，不等于其中每个字节被清零**。如果后来其他调用覆盖了原位置，不能继续把旧图上的数据当作现存值。

### 阶段七：`main` 返回到运行库

在读者已经理解普通函数调用与返回后，回答此前埋下的问题：`main` 为什么也有调用者？它返回到哪里？

本次实验的真实停点是 `main` 返回后的 C 运行库指令地址 `0x7ffff7c2a1ca`；下一步可见 `movl %eax, %edi`，随后 `callq exit`，但后两条**没有在这次收尾中逐条执行**。正文可以依据已见指令说明运行库准备将 `main` 的返回值传给 `exit`，不得写成已经观察到 `exit` 内部执行或完整进程退出。

正文不展开 `_setjmp`、线程局部存储、指针混淆、影子栈等运行库细节；它们作为实验档案保存。

### 阶段八：从具体观察回到一般认识

逐一回应开头的问题，再说明哪些是 C 程序需要实现的语义，哪些是当前 ABI 的调用约定，哪些是 Clang 在本次编译条件下的具体安排。

必须指出：栈帧不必总由 `rbp` 建立；函数不必都预留与本实验相同的局部空间；参数与返回值不必全部通过栈；编译器优化、ABI、检测插桩和函数本身都会影响布局。**结尾不是否定前文观察，而是说明它为什么真实、又为什么不能无条件推广。**

## 五、正文与附录的职责边界

### 正文必须独立成立

读者只阅读正文，应该能完整理解 `main → Add → main` 的调用、执行与返回，以及 `main` 返回运行库的基本事实。正文允许引用附录，但**不能把核心解释外包给附录**。

正文需要展示足以支撑论证的关键指令、寄存器变化与内存图；不要求逐条覆盖全部执行轨迹。不要让正文变成一份删减版 LLDB 日志。

### 附录是可核查的独立实验档案

附录保存完整且**实际可取得**的逐指令记录、原始指令与地址、关键寄存器/内存状态、配图、环境、编译与调试方法、推导和实测的区分，以及 ASan/UBSan、运行库、`_setjmp`、`__sigsetjmp`、TLS、指针混淆、影子栈、`endbr64`、ASan trampoline 等扩展观察。

附录允许深入，甚至可以保留一些当下与正文无关、但未来值得复查的细节。不能因为“正文不需要”就丢弃辛苦获得的实验数据。

**档案完整性不等于伪造完整性。** 当前压缩包不包含全部历史静态图；未来用户逐张上传的图优先于压缩包旧图。未取得的图片、未保存的状态、未执行的步骤必须如实标识，不能靠推测补称“实测”。

### 附录组织建议

- 附录 A：逐指令实验记录（按真实执行顺序，保留原始步骤编号）。

- 非主线深入技术说明可置于 A 的对应步骤之后，或另设专题附录；不预先强制文件数量。

上述为**逻辑划分**，不是必须立即创建三个实体文件的要求。

## 六、正文与附录如何互相引用

采用轻量级的**阶段级双向引用**：正文在关键实验过程结束时，自然链接到附录的对应阶段；附录开头提供返回正文相应章节的入口。

## 七、动画、静态图与文字的分工

### 核心决策

**正文优先使用按完整技术过程组织的动画，动画之后配合较为具体的文字解释；附录保留可逐帧核对的静态图。** 动画解决连续性和正文插图过密的问题，文字解释指令语义及因果关系。

候选动画段落：`main` 栈帧建立、参数传递与 `Add` 调用、`Add` 内部计算、`Add` 返回、`main` 返回运行库。实际分组须依据原始图片和文章节奏确定，不是强制五段。

### 动画制作约束

1. 从**已核对的原始静态图**组织帧序列，不重新想象或虚构寄存器/内存状态。
2. 每帧对应清楚的指令执行前/后状态；区分“即将执行”与“刚刚执行”，避免状态错位。
3. 用当前指令高亮、适当停帧与循环末尾停顿帮助阅读。逐指令状态切换比无依据的平滑位移更符合实验性质。
4. 保留原有的地址方向（低地址在上，高地址在下）、比例（8 字节 78 像素；4 字节 39 像素）、寄存器箭头与数值含义。动画不能为追求效果而改变地址关系。
5. 区分已分配未写入、未使用、已释放、已知值和未知值；**未知区域不能自动填零**。
6. `printf` 等调用可能覆盖旧栈内容；不能把旧 `Add` 的数据一直画到后续状态中。
7. 推导帧必须标注推导性质，不能与实际单步帧混排而不提示。
8. GIF 作为首选兼容格式候选；文件过大时可评估动图 WebP，但需在 GitHub 与 Typora 实测。格式选择在素材制作阶段最终确定。
9. 正文即使不播放动画，仍应能通过文字和必要的关键状态理解机制；必要时提供静态封面或关键帧。
10. 只在确实有帮助时使用动画；单一状态或需要长时间核对的复杂图仍可使用静态图。

### 文字与动画的顺序

先交代本段观察目的，展示连续变化，再用文字逐一解释关键指令、寄存器变化、数据流向和机制；不是在每一帧之间插入长篇解释，也不是只放 GIF 不作说明。

### 原始素材与可复现性

保留原始 PNG、动图成品、必要的帧顺序清单与生成脚本。未来若修正一帧，应能重新生成对应动画。仓库中的素材是可长期核对的原始档案，不能只保留线上动图。

## 九、技术准确性的硬约束

### 分清四个层次

- **C 语言语义**：调用函数、传值、局部对象生存期、返回值等。
- **ABI/调用约定**：当前 x86-64 System V 环境中的参数与返回值寄存器、栈对齐、寄存器保存规则等。
- **编译器实现**：Clang 具体生成的序言/尾声、局部槽位、优化选择、Sanitizer 插桩。
- **本次观察**：特定二进制、特定断点与单步结果、具体地址和值。

不可从第四层的一个样本直接推出第一层的普遍规定；也不可因为实现存在差异，就对当前实测事实含糊其辞。

### 关键指令与状态

- `pushq %rbp` 在本次 64 位模式中使 `rsp` 减 8，并将旧 `rbp` 写入新栈顶；`movq %rsp, %rbp` 复制寄存器值，不改变 `rsp`；`subq $imm, %rsp` 改变栈指针，不自动清零整段空间。
- 不把“指令执行后的架构状态变化”称作多线程意义上的“原子动作”。
- `call` 保存返回地址并转移控制流；`ret` 取回返回地址。准确区分调用者/被调用者与指令前/后状态。
- 当前 `main` 的关键位置：`rbp` 尾部 `e050`、局部空间预留后 `rsp` 尾部 `e040`；`a=10` 在 `e048`，`b=20` 在 `e044`，`c` 在 `e040`（由 0 变为 30）。这些为交接记录中的已知实验数据，正式引用前与图片和原始日志核对。
- 当前 `Add` 的关键位置：`rbp` 尾部 `e030`、预留后 `rsp` 尾部 `e010`；参数、临时值和 `z` 的具体偏移以已核验的实验记录为准。
- `printf("%d\n", 30)` 输出 `30\n`，其返回值是输出字符数 3；`main` 随后返回 0。不要混淆 `printf` 的返回值与 `main` 的返回值。
- 内存被释放/栈指针恢复不等于字节清零；数据是否仍在原地址需要重新观察，不能靠旧帧延续。
- `endbr64` 的出现不证明 IBT 实际启用；`jmp` 与 `call` 的返回地址行为不同；`_setjmp`/`__sigsetjmp` 的尾跳及上下文缓冲区问题放附录，不擅自简化为“恢复旧函数栈帧”。
- 不把 Sanitizer 插桩误当成 C 语义所要求的机器指令。

### 实测、推导、未验证必须区分

交接材料指出：收尾 104—106 为补充重建；107 与实际停点核对；108—109 为根据可见指令作出的后续推导，**没有逐条执行**。不能把 104—109 全部称作真实单步观察，也不能写成已经进入并观察 `exit` 内部。

在附录中采用清晰状态标记（例如“实际单步”“与实测停点核对”“基于指令语义推导”“未验证”），并在图注或表头解释其含义。正文只在相关处用一句话交代证据边界，不把每段写成免责声明。

## 十、旧文与新文的关系

旧文可以提供问题来源和对照价值，但不应决定新版的讲述顺序。允许在合适位置简短比较 32 位 x86 与 x86-64 System V 的参数传递等差异，目的在于说明“具体实现会变化”，不是扩展成 ABI 百科。

需纠正旧文中可能误导的表达：`dword` 是双字（通常 4 字节），不是“双字节”；`ebp/esp` 或 `rbp/rsp` 不是对所有函数都成立的固定边界；`0xCCCCCCCC` 不是所有未初始化局部变量的必然值；源代码与机器码的关系应按编译与链接过程准确描述。

## 十一、审稿与验收清单

### 结构验收
