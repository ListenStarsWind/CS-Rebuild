# 附录 A：main 调用前后的运行库执行过程

正文沿着 `main` 与 `Add` 的调用和返回，观察函数栈帧怎样建立、使用和撤销。本附录把观察范围移到 `main` 的直接调用者：先看运行库怎样准备接续点、登记线程恢复关系并调用 `main`，再看 `main` 返回后，运行库怎样组织收尾，最终结束进程。

前半部分仍以逐条机器指令及栈状态为线索，遇到恢复机制、线程清理和 GOT 时补充必要背景；后半部分随问题转向退出回调与模块生命周期，逐渐改用源码解释整体安排，以关键汇编和调试读数定位。第 A.10、A.11 节尤其保留这种阅读方法的变化，不展开动态链接器排序算法、各模块终结方法及内核退出实现。

### 材料与阅读约定

本附录依据原始调试归档与静态图整理。调用 `main` 之前的配图沿用原图地址、寄存器值与步骤顺序，箭头表示当时尚待执行的指令。同一状态的两张图分别展示不同范围的栈空间。`main` 内部的栈帧过程已在正文说明，本附录在调用与返回处与之衔接。

退出阶段包含两份实验材料：原始程序启用了 AddressSanitizer、UndefinedBehaviorSanitizer；后续 `main-debug` 对照程序未启用 Sanitizer。它们的主程序机器码和退出登记内容可能不同。文中保留各自的原始读数，并说明所属实验；即使运行库地址碰巧一致，也不把它们拼成同一次运行。额外的 Sanitizer 调用链与报错分析集中放在文末补充实验中。

绝对地址用于指认本次材料中的位置，`<+偏移>` 相对于该代码块所属函数的入口计算。栈地址与成员偏移也按本次 x86-64、64 位指针布局说明。重新构建、运行或更换运行库后，需要重新定位。公开源码用于解释结构和机制；原始材料未完整保存运行库的精确版本标识，因此内部名称与成员语义的源码对应，不等同于已经核实本机二进制的每一处编译细节。

文中的 C 风格结构和伪代码用于展开布局及数据流，部分成员重新命名，不能直接代替 glibc 的接口声明。对实测、由指令推演的状态，以及参考源码解释的未执行分支，分别在相关位置交代。

## A.1 运行库函数的栈帧与调用准备

```asm
0x7ffff7c2a150 <+0>:  pushq %rbp
0x7ffff7c2a151 <+1>:  movq  %rsp, %rbp
0x7ffff7c2a154 <+4>:  subq  $0x90, %rsp
0x7ffff7c2a15b <+11>: movq  %rdi, -0x78(%rbp)
0x7ffff7c2a15f <+15>: leaq  -0x70(%rbp), %rdi
0x7ffff7c2a163 <+19>: movl  %esi, -0x7c(%rbp)
0x7ffff7c2a166 <+22>: movq  %rdx, -0x88(%rbp)
0x7ffff7c2a16d <+29>: movq  %fs:0x28, %rax
0x7ffff7c2a176 <+38>: movq  %rax, -0x8(%rbp)
0x7ffff7c2a17a <+42>: xorl  %eax, %eax

; 下一节从这条调用继续
0x7ffff7c2a17c <+44>: callq 0x7ffff7c44fa0 ; _setjmp
```

正文从 `main` 的入口展开，附录则将观察位置移到它的直接调用者。LLDB 将当前运行库函数显示为 `libc.so.6` 中的 `___lldb_unnamed_symbol_2a150`。此时 `main` 尚未被调用，眼前建立的是运行库函数自己的栈帧。

本节配图将同一状态下的连续栈内存分为两页，上页末尾与下页开头以地址衔接。图中箭头指向尚未执行的指令：例如，箭头停在 `movq %rsp, %rbp` 时，只能确认前面的 `pushq` 已经完成，不能把当前这条 `movq` 的效果也算进去。

### A.1.1 建立当前运行库函数的栈帧

入口处的状态为：

```text
rip = 0x7ffff7c2a150
rsp = 0x7fffffffe0f8
rbp = 0x7fffffffe150
```

`%rsp` 指向此前调用当前函数时压入的返回地址。`%rbp` 此刻仍是上一级调用者使用的帧指针。接下来的三条指令依次保存旧帧指针、建立当前帧基址，再预留局部空间。

第0步：停在当前运行库函数入口，`pushq %rbp` 尚未执行。

![运行库压栈rbp，第1页](https://img.mdwind.online/img/%E8%BF%90%E8%A1%8C%E5%BA%93%E5%8E%8B%E6%A0%88rbp_1.png)

![运行库压栈rbp，第2页](https://img.mdwind.online/img/%E8%BF%90%E8%A1%8C%E5%BA%93%E5%8E%8B%E6%A0%88rbp_2.png)

执行 `<+0>` 的 `pushq %rbp` 后，`%rsp` 减少8，来到 `0x7fffffffe0f0`；原 `%rbp` 的值 `0x7fffffffe150` 写入这里的8字节。`%rbp` 寄存器本身还没有改变。保存旧帧指针与保存返回地址是两件事：前者由眼前的 `pushq` 完成，后者早已由进入本函数的那次 `call` 完成。

第1步：旧 `%rbp` 已压栈，下一条将当前 `%rsp` 复制到 `%rbp`。

![运行库栈基准，第1页](https://img.mdwind.online/img/%E8%BF%90%E8%A1%8C%E5%BA%93%E6%A0%88%E5%9F%BA%E5%87%86_1.png)

![运行库栈基准，第2页](https://img.mdwind.online/img/%E8%BF%90%E8%A1%8C%E5%BA%93%E6%A0%88%E5%9F%BA%E5%87%86_2.png)

执行 `<+1>` 后，`%rbp = %rsp = 0x7fffffffe0f0`。当前函数由此取得了自己的栈内定位基准，后续的 `-0x78(%rbp)`、`-0x8(%rbp)` 都相对于这里计算。

第2步：帧基址已建立，`subq $0x90, %rsp` 尚未执行。

![运行库预留栈空间，第1页](https://img.mdwind.online/img/%E8%BF%90%E8%A1%8C%E5%BA%93%E9%A2%84%E7%95%99%E6%A0%88%E7%A9%BA%E9%97%B4_1.png)

![运行库预留栈空间，第2页](https://img.mdwind.online/img/%E8%BF%90%E8%A1%8C%E5%BA%93%E9%A2%84%E7%95%99%E6%A0%88%E7%A9%BA%E9%97%B4_2.png)

随后 `<+4>` 将 `%rsp` 减去 `0x90`，也就是144字节：

```text
rsp = 0x7fffffffe060
rbp = 0x7fffffffe0f0

当前函数预留的局部空间：
[0x7fffffffe060, 0x7fffffffe0f0)
```

这就是当前运行库函数建立的栈帧。`%rsp` 指向栈顶，`%rbp` 作为帧基址；预留的144字节用于存放本函数需要保存的数据。后面会看到传入参数的副本、一个用于状态恢复的局部对象，以及栈保护值被安排在其中。

与正文中的 `main`、`Add` 一样，`subq` 只是留出空间。各个位置何时写入、写入什么，要继续看后面的指令。

### A.1.2 保存传入参数，并准备局部恢复记录的地址

先回顾本实验采用的 System V AMD64 ABI。对于通过通用寄存器传递的普通整数和指针参数，依次使用下面这些位置：

| 同类参数的传递顺序 | 64位寄存器 | 传递32位整数时使用的名称 |
| --- | --- | --- |
| 第1个 | `%rdi` | `%edi` |
| 第2个 | `%rsi` | `%esi` |
| 第3个 | `%rdx` | `%edx` |
| 第4个 | `%rcx` | `%ecx` |
| 第5个 | `%r8` | `%r8d` |
| 第6个 | `%r9` | `%r9d` |

这里列的是普通整数和指针的常见传参顺序。`float`、`double` 等参数通常使用另一组寄存器 `%xmm0`～`%xmm7`，并按各自的规则分配；混合参数不能简单按全部参数的序号套用上表。寄存器不足或参数分类要求通过内存传递时，则使用栈。后面的实验没有浮点参数，这里先不展开向量寄存器。

当前运行库函数接收到的前三个参数分别是 `main` 的入口地址、`argc = 1` 和 `argv` 指针，因此入口处对应 `%rdi`、`%esi` 和 `%rdx`。接下来，它把这些值保存到自己的栈帧中。

这种“先保存、再复用”的过程后面还会多次出现。同一个寄存器会在不同阶段承担不同任务；把仍然需要的旧值留在栈上，就可以让寄存器继续参与新的调用或计算。之后需要旧值时，再从栈中取回。这里保存的是本函数稍后还要使用的参数；另外一些指令则会保存调用约定要求保留的寄存器，供返回调用者前恢复。两者都利用栈保存数值，但保存的目的需要结合具体指令判断。

第3步：144字节局部空间已预留，下一条保存 `main` 的入口地址。

![写入第一个形参，第1页](https://img.mdwind.online/img/%E5%86%99%E5%85%A5%E7%AC%AC%E4%B8%80%E4%B8%AA%E5%BD%A2%E5%8F%82_1.png)

![写入第一个形参，第2页](https://img.mdwind.online/img/%E5%86%99%E5%85%A5%E7%AC%AC%E4%B8%80%E4%B8%AA%E5%BD%A2%E5%8F%82_2.png)

`<+11>` 将 `%rdi` 中的8字节数值保存到 `-0x78(%rbp)`：

```text
0x7fffffffe0f0 - 0x78 = 0x7fffffffe078

[0x7fffffffe078, 0x7fffffffe080)
    main 入口地址 = 0x55555566abc8
```

这条指令保存的是入口地址，并没有复制 `main` 的机器指令。保存后，`%rdi` 便可以用于准备后续调用，同时保留日后调用 `main` 所需的函数指针。

第4步：`main` 入口地址已写入栈中，下一条准备 `_setjmp` 的第一个实参。

![准备第一个实参，第1页](https://img.mdwind.online/img/%E5%87%86%E5%A4%87%E7%AC%AC%E4%B8%80%E4%B8%AA%E5%AE%9E%E5%8F%82_1.png)

![准备第一个实参，第2页](https://img.mdwind.online/img/%E5%87%86%E5%A4%87%E7%AC%AC%E4%B8%80%E4%B8%AA%E5%AE%9E%E5%8F%82_2.png)

`<+15>` 使用 `leaq` 计算 `-0x70(%rbp)`，得到 `0x7fffffffe080`，并把它放入 `%rdi`。

如果从 C 语言的角度理解，这里可以看作当前函数准备使用一个栈上的局部变量，只不过它是一个保存恢复状态的结构体，而不是一个整数。前面的 `subq` 已经为它和其他局部数据留出了空间，但它的成员尚未被逐项写入。接下来怎样填充这个对象，就要进入 `_setjmp` 继续观察。

结合 glibc 的结构定义和后续写入，可以将它辨认为 `struct pthread_unwind_buf` 类型的局部恢复记录。结构开头是跳转上下文，后面还有用于衔接恢复关系和清理状态的私有成员。为了便于后续对照，先按本次64位布局列出一份示意：

| 相对对象起点的偏移 | 字节数 | 后续保存的内容 |
| --- | ---: | --- |
| `+0x00` | 8 | `%rbx` |
| `+0x08` | 8 | `%rbp`，按实现进行指针混淆后保存 |
| `+0x10` | 8 | `%r12` |
| `+0x18` | 8 | `%r13` |
| `+0x20` | 8 | `%r14` |
| `+0x28` | 8 | `%r15` |
| `+0x30` | 8 | 恢复执行时使用的栈指针，混淆后保存 |
| `+0x38` | 8 | 恢复执行的指令地址，混淆后保存 |
| `+0x40` | 4 | 是否保存了信号阻塞集的标记 |
| `+0x44` | 4 | 对齐填充 |
| `+0x48` | 8 | 先前登记的恢复节点指针 `prev` |
| `+0x50` | 8 | 原有清理处理器链表头指针 `cleanup` |
| `[+0x58, +0x68)` | 16 | 其余私有字段及预留空间，本节暂不展开 |

表格描述的是随后怎样使用这片空间，并不表示当前这些内容已经写入。前64字节对应恢复上下文；`+0x40` 之后还包含标记与私有数据，并不是再跟着一份本次必定保存的信号阻塞集。恢复函数中的可选体系结构扩展也可能涉及后部空间，后面遇到相应指令时再说明。

这份局部记录的起点是 `0x7fffffffe080`。按上面的布局，它占用 `[0x7fffffffe080, 0x7fffffffe0e8)`；紧接着的 `0x7fffffffe0e8` 是后面保存栈保护值的位置。记录本身仍然是当前函数栈帧中的一个局部对象。

从调用的角度看，眼前这条 `leaq` 就是在取这个对象开头的地址，作为后续 `_setjmp` 写入恢复上下文时的实参。它相当于把一个局部对象的地址交给函数，由函数通过指针填充相关成员。前面先保存 `main` 入口地址，正是因为 `%rdi` 在这里接到了新的传参任务。

随后 `<+19>` 将 `%esi` 中的 `argc` 保存到 `-0x7c(%rbp)`，写入宽度为4字节。

第5步：`%rdi` 已指向局部上下文区域；`argc` 的保存尚未执行。

![写入第二个形参，第1页](https://img.mdwind.online/img/%E5%86%99%E5%85%A5%E7%AC%AC%E4%BA%8C%E4%B8%AA%E5%BD%A2%E5%8F%82_1.png)

![写入第二个形参，第2页](https://img.mdwind.online/img/%E5%86%99%E5%85%A5%E7%AC%AC%E4%BA%8C%E4%B8%AA%E5%BD%A2%E5%8F%82_2.png)

再执行 `<+22>`，将 `%rdx` 中的 `argv` 指针保存到 `-0x88(%rbp)`，写入宽度为8字节。复制的只是指针值，不包含它所指向的整个参数数组。

第6步：`argc = 1` 已写入栈中，下一条保存 `argv` 指针。

![写入第三个形参，第1页](https://img.mdwind.online/img/%E5%86%99%E5%85%A5%E7%AC%AC%E4%B8%89%E4%B8%AA%E5%BD%A2%E5%8F%82_1.png)

三份参数副本的位置如下：

| 寻址表达式 | 地址范围（半开区间） | 字节数 | 保存内容 |
| --- | --- | ---: | --- |
| `-0x78(%rbp)` | `[0x7fffffffe078, 0x7fffffffe080)` | 8 | `main` 入口地址 `0x55555566abc8` |
| `-0x7c(%rbp)` | `[0x7fffffffe074, 0x7fffffffe078)` | 4 | `argc = 1` |

### A.1.3 保存栈保护值，清零临时寄存器

前面的局部变量通过 `%rbp` 加偏移定位，`<+29>` 却使用了 `%fs:0x28`。这里换了一种基准：当前线程的 FS 基址。

可以联系线程局部存储（TLS）来理解。多个线程共享进程的地址空间，但运行库还需要为每个线程保存各自的管理信息，例如线程描述符的指针、定位线程局部变量的数据，以及后面会看到的清理和恢复节点指针。在本次 Linux x86-64 环境中，FS 基址提供了访问这些线程相关数据的固定入口：同样写成 `%fs:某个偏移`，在线程切换后可以访问相应线程自己的数据。

这些信息不全都紧挨在 FS 基址后面；有些字段本身保存指针，进一步指向其他区域。这里先认识几处后面会用到的位置：

| 本次实现中的位置 | 保存内容或用途 |
| --- | --- |
| FS 基址附近的头部字段 | 线程控制块、自身线程描述符的指针，以及定位各模块 TLS 数据的表指针 |
| `%fs:0x28` | 栈保护值 `stack_guard` |
| `%fs:0x30` | 指针混淆使用的保护值 `pointer_guard` |
| `%fs:0x2f8` | 旧式清理处理器链表头指针 |
| `%fs:0x300` | 当前登记的恢复节点指针 |

这些偏移属于当前平台和运行库实现，不能当作所有系统的统一布局。对眼前指令而言，只需要先知道 `%fs:0x28` 是“FS 基址加 `0x28` 处的内存”，而不是绝对地址 `0x28`。`<+29>` 从这里读取8字节到 `%rax`，取得本次线程的栈保护值，也就是栈金丝雀。

第7步：三份参数副本已保存，下一条读取线程局部的栈保护值。

![读取栈金丝雀，第1页](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96%E6%A0%88%E9%87%91%E4%B8%9D%E9%9B%80_1.png)

![读取栈金丝雀，第2页](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96%E6%A0%88%E9%87%91%E4%B8%9D%E9%9B%80_2.png)

读取完成后，`%rax = 0x0ed6d86fcaf33200`。随后 `<+38>` 把这份保护值保存到 `-0x8(%rbp)`，也就是 `0x7fffffffe0e8`：

```text

```

## A.2 保存一个可以重新接续的执行位置

上一节中，运行库已经在自己的栈帧里预留了局部空间，并把其中一块空间的地址放进 `%rdi`。接下来，它将调用 `_setjmp`，把恢复执行所需的信息写进去。不过，在跟进这个函数之前，还需要先弄清一个问题：这里所说的“恢复”，究竟是怎样一种恢复？

### A.2.1 从逐层返回，到跨越调用层次

通常，函数调用与返回具有明确的层次。假设外层函数调用中间函数，中间函数再调用内部函数。内部工作结束后，先返回中间函数，中间函数完成自己的工作，再返回外层。每一层都有自己的返回位置，也有机会处理下层交回的结果。

如果内部函数发现当前任务必须放弃，也可以沿用这个过程：先返回一个表示失败的结果，中间函数检查结果，再决定怎样向外传递。这样做没有问题，但意味着沿途各层都需要参与这次结果传递。

另一种需求是：外层事先准备好一个接续位置，内部遇到约定的情况时，直接把控制权交回那里。中间函数不再继续执行原来的普通返回路径，外层则从准备好的位置接着处理。这就是这里要理解的非局部跳转（nonlocal jump）：目标位置可以跨越当前函数及中间的调用层次。

| 比较的方面 | 普通函数返回 | 通过已保存上下文接续执行 |
| --- | --- | --- |
| 返回到哪里 | 当前函数的直接调用者 | 先前保存的接续位置，可以跨越多层调用 |
| 怎样找到目标 | 使用当前调用对应的返回地址 | 使用保存区记录的接续地址和必要状态 |
| 中间调用怎样结束 | 沿调用关系逐层返回 | 被跨过的普通返回路径不再执行 |
| 沿途资源怎样处理 | 各层可以在返回前自行处理 | 需要使用方另行安排，普通 `longjmp` 不提供通用自动清理 |

`setjmp` 和 `longjmp` 提供了这样一组保存与接续机制。保存方先记录接续执行所需的信息；恢复方以后使用这份记录，把执行流重新送到保存调用之后。第一次执行保存调用时返回零，经恢复机制接续到这里时，则表现为取得了一个非零返回值。外围代码据此选择不同分支。

这里“再次取得返回值”的说法，是从调用点观察到的效果。恢复时并不需要重新从保存函数的入口执行一遍，也不会重新执行先前那条调用指令。

### A.2.2 恢复的是执行条件，已经发生的事情仍然存在

要从外层指定的位置继续运行，只知道那个位置的代码地址还不够。外层代码接下来可能访问自己的局部变量，也可能依赖某些应该跨调用保留的寄存器。栈位置和必要的寄存器状态，都需要与这个接续位置相匹配。

因此，在本次 x86-64 实现中，保存的信息包括接续地址、栈指针，以及被调用者保存寄存器的值。恢复方使用这些信息，重新建立从该位置继续执行的条件。

为什么不必保存所有寄存器？因为这里的目标是形成符合函数调用约定的接续状态。一次普通调用结束后，调用者本来就不能依赖参数寄存器及其他调用者保存寄存器仍保留旧值；需要跨调用使用的数据，编译器会按调用约定安排。保存区保留必要的被调用者保存寄存器，再配合栈位置和接续地址，就能支持这种接续。具体保存哪些项目，后面还会逐条对照。

具体接续时，恢复代码读回保存的值，对经过指针混淆的项目作反向处理，恢复必要寄存器，再把目标栈位置装入 `%rsp`，跳向保存的接续地址。CPU 可以执行这样的寄存器修改和跳转，并不要求必须先执行完中间各层的函数尾声。调整栈指针后，被跨过的栈区域通常仍保留原来的字节，只是不再属于当前活动调用链。

不过，重新取得这些执行条件，并不意味着整个程序回到了过去。假如内部函数已经修改了全局变量、申请了堆内存，或者向文件写入了内容，跳回保存点不会自动撤销这些操作。保存区也没有复制整片栈内存。还有一种情况需要注意：在执行 `setjmp` 的那个函数里，如果某个自动局部变量没有用 `volatile` 修饰，而且它的值在 `setjmp` 返回后、`longjmp` 发起前发生了改变，那么经 `longjmp` 接续回来以后，这个变量的值是不确定的。不能依赖它保留修改后的值，也不能认为它一定恢复成保存点时的旧值。

同样，保存了栈地址，也不意味着那个栈帧会被永久保留。保存点所在的函数必须仍处于有效的调用期间；如果它已经返回，再试图使用旧记录跳回去，就不满足这一机制的使用条件。

可以把这里的恢复理解为：放弃当前调用链中被跨过部分的后续执行，把控制权交回一个事先准备好的接续位置。接续点随后可以记录错误、重新尝试、处理下一项工作，也可以开始收尾。恢复到哪里，以及到那里以后做什么，是两个需要分别考虑的问题。

### A.2.3 恢复到一个位置，也可以是为了结束线程

线程退出提供了一个具体的使用场景。线程可能在很深的业务调用中执行 `pthread_exit`，此时需要放弃当前业务调用链，并进入线程退出处理。若要求每一层业务函数都先收到某个退出标记、再逐层返回，线程退出机制就会依赖业务代码的配合。

在这里涉及的 glibc/NPTL 实现中，线程启动外围预先准备了相应的上下文记录。退出或取消路径可以组织必要的栈展开和清理，在到达目标边界时，借助内部的非局部跳转机制，把执行流接回外围的收尾分支。此时，重新取得栈位置和必要寄存器，是为了让收尾代码继续执行；业务函数原来的后半段已经不再继续。

这里需要把两件事放在一起看：展开过程可以沿途执行必要的清理，最后的机器状态恢复则负责接续到目标位置。前者可能逐帧进行，后者能够跨越普通返回层次。因此，线程退出不能简单等同于一次普通 `longjmp`。普通 `longjmp` 本身不承诺自动逐帧调用 C++ 局部对象的析构函数；C++ 对跨越非平凡析构的使用还施加了额外限制，不能把它当作异常展开的替代品。

| 所说的“恢复” | 恢复后发生什么 |
| --- | --- |
| 本节的执行上下文恢复 | 同一线程使用保存的必要状态，从约定位置接续执行 |
| 整个程序状态回滚 | 还需要还原内存及外部副作用，超出了本节机制的能力 |
| 调度中的线程上下文恢复 | 由调度相关机制使线程继续原来被暂停的执行，与这里主动选择旧接续点的用途不同 |
| 线程退出中使用上下文恢复 | 控制权回到线程外围的收尾路径，随后继续退出工作 |

本次运行库在调用 `main` 之前所做的准备，就与主线程的这类外围处理有关。`main` 正常返回时，会沿正常路径把结果交给 `exit`；如果通过相应的线程退出机制接续到保存点，则进入另一条处理分支。不能因为存在这个保存点，就认为内核会在段错误发生后自动找到它、让程序重新继续运行。

以上关于恢复与线程退出的说明，结合了 glibc 源码中的实现关系。本次静态图记录的是保存阶段的正常执行，没有展示一次实际触发线程退出、展开并恢复到这里的完整实验。

### A.2.4 回到这次调用：先保存，再关联，最后才可能使用

在这一位置，`_setjmp` 要做的是采集当前执行状态，并把接续所需的信息写入传入的保存区。称它为初始化也可以，但这里填入的是当时实际的寄存器和控制流信息，而不是一组固定初值。

程序可以同时保留多组有效的恢复记录。假设 A、B 分别保存了不同的接续点，恢复时使用 A 的记录，就会接续到 A；使用 B 的记录，就会接续到 B。因此，发起恢复的代码需要明确选择哪份保存区。普通 `longjmp` 通过传入的保存区参数确定目标，并不会自动判断调用者原本想使用哪一组。若误传了另一份仍有效的记录，就可能接续到另一个位置。

在本次 glibc 线程管理场景里，运行库还需要管理当前采用的恢复节点，以及它与先前节点的关系，所以在保存机器状态之外，又设置了链式关联。后面可以看到一个类似链表插入的动作：先把线程中原来的节点指针保存到当前对象的 `prev` 成员里，再让线程中的当前节点指针指向这个新对象。以线程保存的指针作为链表入口来看，这是头插；新节点成为当前入口，旧节点仍能沿 `prev` 找到。

这一步就是把新的一组恢复关系登记到线程管理结构里。保存区中的机器状态回答“使用这份记录时怎样接续”，链式关联则回答“当前登记的是谁，以及此前还有谁”。链表提供管理关系，目标仍需要由运行库正确选择；它本身不会识别 A、B 两组的业务意图，也不是所有 `setjmp`／`longjmp` 用法都必须具备的结构。

因此，`_setjmp` 先填入接续需要的机器状态，后续运行库再填写外层结构体的关联信息并登记节点，真正的恢复则由以后的另一条执行路径发起。三者的职责可以这样对应：

| 阶段 | 完成的工作 |
| --- | --- |
| 保存接续点 | 写入必要机器状态，使保存调用首次返回零 |
| 建立线程关联 | 保存旧关联，并把当前对象接到线程的管理结构中 |
| 使用保存记录 | 恢复必要状态，以非零返回值接续到保存调用之后 |

现在再看汇编，`_setjmp` 为什么需要接收一块局部空间的地址，就比较清楚了。

### A.2.5 调用 `_setjmp`：先形成这一次普通调用

```asm
0x7ffff7c2a17c <+44>: callq  0x7ffff7c44fa0 ; _setjmp
0x7ffff7c2a181 <+49>: endbr64
```

执行 `callq` 之前，`%rdi` 已经指向 `0x7fffffffe080`，也就是前面计算出的 `%rbp-0x70`。这是本次传入的保存区起点。此时运行库栈帧的 `%rbp` 为 `0x7fffffffe0f0`，`%rsp` 为 `0x7fffffffe060`。

![call setjmp_1.png](https://img.mdwind.online/img/call%20setjmp_1.png)

![call setjmp_2.png](https://img.mdwind.online/img/call%20setjmp_2.png)

这条 `callq` 先把下一条指令地址 `0x7ffff7c2a181` 压栈，再跳到 `_setjmp`。因此，进入函数时 `%rsp` 变为 `0x7fffffffe058`，该位置存放本次调用的返回地址。

这个地址有两重关联：保存函数完成工作后，正常返回到这里；以后若使用保存记录进行非局部恢复，接续地址也指向这里。相应地，保存的目标栈指针应当是这次调用返回以后使用的 `0x7fffffffe060`。后面的实现会分别取得这两个值，而不是把栈地址与栈内保存的代码地址混为一谈。

### A.2.6 `_setjmp` 入口：落点标记与第二个实参

```asm
0x7ffff7c44fa0 <+0>: endbr64
0x7ffff7c44fa4 <+4>: xorl   %esi, %esi
0x7ffff7c44fa6 <+6>: jmp    0x7ffff7c44ed0 ; __sigsetjmp
```

![可落点标记_1.png](https://img.mdwind.online/img/%E5%8F%AF%E8%90%BD%E7%82%B9%E6%A0%87%E8%AE%B0_1.png)

![可落点标记_2.png](https://img.mdwind.online/img/%E5%8F%AF%E8%90%BD%E7%82%B9%E6%A0%87%E8%AE%B0_2.png)

`call` 和 `jmp` 都是汇编中转移执行流的常见指令，也都可以用于进入其他函数。二者的一项关键区别，是有没有为返回做好准备：这里的 `callq` 会将下一条机器指令的地址压栈；`jmp` 不压入新的返回地址，因此，如果没有已有的返回地址或其他返回安排，它不会自动回到这次跳转之后的位置继续执行。

此外，调用和跳转都有直接、间接的形式。直接形式的目标由指令中编码的信息确定，例如本次 `callq 0x7ffff7c44fa0`。代码区通常具有写保护，目标不必另外从可写的数据区中取得，因此相对不容易因为某个数据指针被改写而改变这次调用的去向。这里的“直接”指目标的确定方式，并不意味着它一定采用绝对地址编码。

间接形式则从寄存器或内存中取得目标地址。例如，后面调用 `main` 时会使用 `callq *%rax`：先把入口地址读入 `%rax`，再按照这个地址调用。这样的方式能够支持函数指针等正常需求，但也带来一种风险：如果目标地址来自可写内存，那么那里的指针可能先被错误写入或恶意篡改，再被读入寄存器，最终使执行流进入不该进入的位置。

为此，英特尔在 CET 中提供了间接分支跟踪（Indirect Branch Tracking，IBT）。对启用了这项检查的间接 `call` 或 `jmp`，处理器会要求目标处以相应的落点标记开始；在这里的 64 位代码中，这个标记就是 `endbr64`。受检查的间接分支如果落到没有相应标记的位置，就会触发控制保护异常。

所以，如果一个函数入口没有标记，它仍可以接受直接调用，但不能直接作为这类受检查的间接调用的落点；如果函数内部其他位置也没有标记，同样不能通过受检查的间接跳转进入。这里约束的是接受 IBT 检查的分支，具体实现还存在免于跟踪的安排，不能把这个限制扩大到所有形式的控制流转移。

本次 `endbr64` 恰好位于 `_setjmp` 的入口，使这个入口具备接受相应间接分支的条件。标记也可以出现在函数内部。例如，用跳转表实现的 `switch` 如果采用受 IBT 检查的间接跳转，就可以在各个目标分支的起始位置放置标记，而不必只在函数入口放置。

不过，标记只说明“这个位置允许成为相应间接分支的落点”，不会判断“这一次调用在业务上是否应该来到这里”。跳到另一个同样带有标记的错误目标，仍可能通过这项检查。

如果 IBT 没有启用，就没有这项落点检查；在支持正常执行这些指令的环境中，`endbr64` 也不会因此限制间接调用或跳转。单凭图中出现了这条指令，不能认定当前已经开启 IBT，可以将它理解为运行库对启用该机制的运行环境所做的兼容准备。本次从调用者进入 `_setjmp` 使用的是直接 `callq`，这次调用本身不依赖入口标记完成目标检查。

执行完标记后，来到 `xorl %esi,%esi`。自异或使 `%esi` 清零，写入 32 位寄存器同时将 `%rsi` 的高 32 位清零。

![准备第二个实参_1.png](https://img.mdwind.online/img/%E5%87%86%E5%A4%87%E7%AC%AC%E4%BA%8C%E4%B8%AA%E5%AE%9E%E5%8F%82_1.png)

![准备第二个实参_2.png](https://img.mdwind.online/img/%E5%87%86%E5%A4%87%E7%AC%AC%E4%BA%8C%E4%B8%AA%E5%AE%9E%E5%8F%82_2.png)

按照前面的传参约定，`%rdi` 仍携带保存区地址，`%esi` 则准备给后面的 `__sigsetjmp` 作为第二个实参。这个参数称为 `savemask`：值为零，表示这次不额外保存当前线程的信号阻塞集。

这里的零只控制保存行为，并没有清空线程当前的信号阻塞集。至于为什么选择不保存，可以结合这个接续点的用途来理解。

前面已经看到，这份记录是为主线程的退出或取消处理准备的。恢复到这里以后，执行流进入的是退出收尾分支，不再继续 `main` 中被放弃的业务逻辑。因此，从用途上推断，它没有为了日后继续原业务而恢复旧信号阻塞集的需要。这个解释与运行库实际选择的“不保存”方式相符，但属于对用途的分析，不是从一条清零指令中就能读出的设计说明。

这里说“主线程退出”比直接说“进程退出”更准确。根据本次调用者后面的分支及对应 glibc 源码，主线程先处理线程专有数据，并减少线程计数；如果仍有其他线程，就只结束当前线程，如果它已是最后一个线程，才进入 `exit(0)` 结束进程。主线程执行 `pthread_exit`，并不意味着一定同时结束整个进程。

即使程序刚进入 `main` 时阻塞集碰巧是默认状态，也不能据此认为后来恢复到这里时仍然如此。`execve` 可以保留先前的阻塞集，而程序在保存点之后执行的具体逻辑也可能修改它。由于这里没有保存和恢复阻塞集，接续时保留的是恢复发生时的状态；它可能与保存点时不同。

这种不同没有破坏“接回退出路径”的用途：这里不要求还原一份供原业务继续使用的信号环境。不过，这不意味着信号状态在所有退出处理中都无关紧要，只是这次上下文保存没有承担还原它的职责。后面还会看到影子栈；若相应保护已启用，普通栈与影子栈的返回关系就必须得到协调，否则后续受保护的返回可能触发控制保护异常。两者是否需要恢复，要看后续执行具体依赖什么，不能只凭它们都是某种“旧状态”就一概处理。

### A.2.7 用 `jmp` 进入实际保存逻辑

```asm
0x7ffff7c44fa6 <+6>: jmp    0x7ffff7c44ed0 ; __sigsetjmp

; 下一节即将进入的位置
0x7ffff7c44ed0 <+0>: endbr64
0x7ffff7c44ed4 <+4>: movq   %rbx, (%rdi)
```

![进入快照保存的主逻辑_1.png](https://img.mdwind.online/img/%E8%BF%9B%E5%85%A5%E5%BF%AB%E7%85%A7%E4%BF%9D%E5%AD%98%E7%9A%84%E4%B8%BB%E9%80%BB%E8%BE%91_1.png)

![进入快照保存的主逻辑_2.png](https://img.mdwind.online/img/%E8%BF%9B%E5%85%A5%E5%BF%AB%E7%85%A7%E4%BF%9D%E5%AD%98%E7%9A%84%E4%B8%BB%E9%80%BB%E8%BE%91_2.png)

在这组图中，第二个实参已经清零，当前待执行的是 `<+6>` 的 `jmp`。执行它以后，控制流进入 `__sigsetjmp`，由那里的代码实际保存上下文。

`jmp` 不会像 `callq` 那样再次压入返回地址。因此，此时栈顶仍然保留最初那次 `callq _setjmp` 压入的 `0x7ffff7c2a181`。后续保存逻辑处理完毕，经过内部尾声的正常 `retq`，就能直接回到原来的调用者。

这里仍然是在第一次调用中保存信息并正常返回，尚未发生非局部恢复。`_setjmp` 通过清零第二个实参，再跳入公共实现，选择了“不保存信号阻塞集”的保存方式。接下来需要逐项检查的是：它究竟把哪些寄存器写到了保存区的哪些位置，又怎样从当前栈中提取未来的接续地址和栈位置。

## A.3 把接续需要的机器状态写入保存区

`_setjmp` 已经准备好实参，并通过 `jmp` 进入 `__sigsetjmp`。从这里开始，前面预留的局部空间将逐项写入实际数据：先记录需要保留的寄存器，再保存将来接续时应使用的栈位置和代码位置。

### A.3.1 先把结构体布局放在手边

为便于对照，可以把 glibc 的实际布局展开成下面这份 C 风格声明。成员名称按本节的解释重新拟定，偏移按本次 x86-64、64 位指针的布局标出；源码中的数组和多层私有成员访问则作了展开。

```c
#include <stdint.h>

struct ResumePointState {
    /* 接续执行所需的机器状态 */

    /* +0x00 */ uint64_t saved_rbx;          // 保存 rbx 的原值
    /* +0x08 */ uint64_t saved_rbp_mangled;  // 保存混淆后的 rbp，本次为栈帧基准
    /* +0x10 */ uint64_t saved_r12;          // 保存 r12 的原值
    /* +0x18 */ uint64_t saved_r13;          // 保存 r13 的原值
    /* +0x20 */ uint64_t saved_r14;          // 保存 r14 的原值
    /* +0x28 */ uint64_t saved_r15;          // 保存 r15 的原值
    /* +0x30 */ uint64_t resume_rsp_mangled; // 接续时应使用的 rsp，经过混淆
    /* +0x38 */ uint64_t resume_pc_mangled;  // 接续执行的代码地址，经过混淆

    /* +0x40 */ int32_t mask_was_saved;       // 是否保存信号阻塞集，后面本次写入 0
    /* +0x44 */ uint8_t alignment_padding[4]; // 对齐填充

    /* 线程恢复节点的管理信息，稍后由运行库填写 */

    /* +0x48 */ struct ResumePointState *prev; // 此前登记的恢复节点
    /* +0x50 */ void *saved_cleanup_head;      // 登记时的旧式清理链表头
    /* +0x58 */ uint8_t private_tail[16];      // 剩余私有空间，结合具体路径解释
};

/* 本次布局：对齐为 8 字节，总大小为 0x68，即 104 字节。 */
```

这里展示的是外层 `pthread_unwind_buf` 的展开布局。本节主要填写前八个机器状态槽位；信号阻塞集保存标志与节点关联信息，要在后面才处理。声明中的 `private_tail` 保留原始空间形式：外层源码的私有区包含取消类型等信息，而后面可选的影子栈保存又会使用其中的空间，不能提前将整块区域解释为一个独占的影子栈成员。

本次 `%rdi` 指向 `0x7fffffffe080`。因此，`0x8(%rdi)` 就对应 `saved_rbp_mangled`，`0x30(%rdi)` 对应 `resume_rsp_mangled`。结构体里的偏移与接下来看到的寻址偏移，可以一一对应。

```asm
0x7ffff7c44ed4 <+4>: movq   %rbx, (%rdi)
```

当前先执行入口的 `endbr64`，它的作用上一节已经讨论。`_setjmp` 是通过直接 `jmp` 来到这里的，沿途没有压入新的返回地址，也没有另外建立栈帧。当前 `%rsp` 仍为 `0x7fffffffe058`，`%rbp` 仍为运行库调用者的 `0x7fffffffe0f0`。

下一条 `movq` 把 `%rbx` 的八字节原值写入 `%rdi` 指向的位置，即保存区的 `+0x00`。

本次 `%rbx` 的值为 `0x7fffffffe178`，与 `argv` 数组地址相对应。`<+4>` 将这个指针值写入保存区的 `+0x00` 槽位。

在本平台的调用约定中，`rbx`、`rbp`、`r12`～`r15` 承担着保留跨调用数据的职责。调用者可以将后续仍需使用的数据放入这些寄存器，并依赖它们在普通函数调用返回后保持原值。非局部恢复也利用了这项约定：保存点记录它们的值，恢复时重新装回，使接续点之后的代码仍能使用原先的数据。

这些寄存器具有明确的保留职责，其中数据的具体意义则由使用它们的代码决定。`setjmp` 只记录寄存器的当前值，不解释它们存放的是启动参数、地址还是其他中间结果。各个槽位按照寄存器命名，正好与汇编中的逐项写入相对应。

### A.3.3 保存 rbp：先复制，再混淆，最后写入

```asm
0x7ffff7c44ed7 <+7>:  movq %rbp, %rax
0x7ffff7c44eda <+10>: xorq %fs:0x30, %rax
0x7ffff7c44ee3 <+19>: rolq $0x11, %rax
0x7ffff7c44ee7 <+23>: movq %rax, 0x8(%rdi)
```

`<+7>` 先把 `%rbp` 的值复制到临时寄存器 `%rax`。本次复制的是 `0x7fffffffe0f0`，正在使用的 `%rbp` 本身保持不变。

![暂存恢复时的栈基址_1.png](https://img.mdwind.online/img/%E6%9A%82%E5%AD%98%E6%81%A2%E5%A4%8D%E6%97%B6%E7%9A%84%E6%A0%88%E5%9F%BA%E5%9D%80_1.png)

![暂存恢复时的栈基址_2.png](https://img.mdwind.online/img/%E6%9A%82%E5%AD%98%E6%81%A2%E5%A4%8D%E6%97%B6%E7%9A%84%E6%A0%88%E5%9F%BA%E5%9D%80_2.png)

接下来的 `xorq` 从 `%fs:0x30` 读取指针保护值，与 `%rax` 异或；`rolq $0x11` 则把所得的 64 位数循环左旋 17 位。这里的 `0x11` 是十六进制，换成十进制就是 17。

![栈基址指针混淆_1.png](https://img.mdwind.online/img/%E6%A0%88%E5%9F%BA%E5%9D%80%E6%8C%87%E9%92%88%E6%B7%B7%E6%B7%86_1.png)

![栈基址指针混淆_2.png](https://img.mdwind.online/img/%E6%A0%88%E5%9F%BA%E5%9D%80%E6%8C%87%E9%92%88%E6%B7%B7%E6%B7%86_2.png)

循环移位与丢弃高位的普通左移不同：从高位移出去的比特会回到低位，信息没有丢失。因此，这个变换是可逆的。若用 `G` 表示指针保护值、`P` 表示原值，保存过程可以写为：

```text
保存值 = 循环左旋64位(P XOR G, 17)
原值   = 循环右旋64位(保存值, 17) XOR G
```

固定的旋转次数本身不是秘密；异或与循环移位共同构成这里的指针混淆，恢复方按相反顺序处理。

图中箭头仍指着写入指令，表示此刻结果已经在 `%rax` 中准备好，目标槽位尚未由这条指令写入。执行后，`saved_rbp_mangled` 才具有这个混淆值。后面的图也沿用同样的“当前待执行指令”表示方式。

#### A.3.3.1 为什么对这些值进行混淆

这里保护的是保存区中的副本。它们暂时作为普通数据放在内存里，真正恢复时却会决定使用哪一片栈空间，以及从哪里继续执行。攻击者如果能够定向改写这些保存值，内存破坏就可能进一步发展成对执行流的控制，造成信息泄露、数据篡改等后果。

直接保存原始地址时，攻击者可能尝试把自己选定的地址写入相应槽位。经过混淆后，恢复方还要进行反向变换；直接写入目标地址，恢复得到的不会就是那个目标。攻击者需要构造与保护值相匹配的保存值，才能准确得到预期的执行去向。

指针混淆在内存破坏与定向控制执行流之间增加了一道障碍。攻击者即使获得对保存区的写入能力，也还需要解决混淆值的构造问题，才能使程序沿选定的路径继续执行。盲目覆盖可能得到无效地址并使程序崩溃；保护信息泄露或更强的读写能力，则可能削弱这项措施的效果。

这是一项降低漏洞利用机会的加固措施。它提高了将关键保存值改造成可控执行目标的难度，不能据此保证所有篡改最终都会导致终止。

本次使用的指针保护值位于 `%fs:0x30`；前面读取的栈金丝雀位于 `%fs:0x28`，二者分别用于对应的保护机制。

### A.3.5 保存接续以后应使用的 rsp

```asm
0x7ffff7c44efb <+43>: leaq 0x8(%rsp), %rdx
0x7ffff7c44f00 <+48>: xorq %fs:0x30, %rdx
0x7ffff7c44f09 <+57>: rolq $0x11, %rdx
0x7ffff7c44f0d <+61>: movq %rdx, 0x30(%rdi)
```

当前 `%rsp` 为 `0x7fffffffe058`，该位置保存着最初 `callq _setjmp` 压入的返回地址。`<+43>` 使用 `leaq` 计算 `%rsp+8`，得到 `0x7fffffffe060`，没有读取这个地址中的内容。

![暂存恢复后应当处于的rsp地址_1.png](https://img.mdwind.online/img/%E6%9A%82%E5%AD%98%E6%81%A2%E5%A4%8D%E5%90%8E%E5%BA%94%E5%BD%93%E5%A4%84%E4%BA%8E%E7%9A%84rsp%E5%9C%B0%E5%9D%80_1.png)

![暂存恢复后应当处于的rsp地址_2.png](https://img.mdwind.online/img/%E6%9A%82%E5%AD%98%E6%81%A2%E5%A4%8D%E5%90%8E%E5%BA%94%E5%BD%93%E5%A4%84%E4%BA%8E%E7%9A%84rsp%E5%9C%B0%E5%9D%80_2.png)

为什么要加八？因为将来接续到保存调用之后，应当具有“这次调用已经返回”的栈状态。正常的 `retq` 取走八字节返回地址后，栈指针就会从 `0x7fffffffe058` 回到 `0x7fffffffe060`。这里提前记录的正是那个返回以后的位置。

这时，变化的是临时寄存器 `%rdx`，实际 `%rsp` 仍指向 `0x7fffffffe058`。保存代码没有提前弹出返回地址，也没有改变当前栈顶。

随后，用同一个指针保护值异或，并循环左旋 17 位。

本次混淆结果为 `0x40bbe00ab4f8be57`。执行 `<+61>` 后，它被写入 `%rdi+0x30`，即 `0x7fffffffe0b0`，对应 `resume_rsp_mangled`。

这个成员表示恢复后要装入 `%rsp` 的值，而不是保存时 `%rsp` 的原样副本。理解它的语义，比只记住“这里存了一个栈指针”更重要。

### A.3.6 从栈顶取出接续代码地址

```asm
0x7ffff7c44f11 <+65>: movq (%rsp), %rax
0x7ffff7c44f15 <+69>: nop
0x7ffff7c44f16 <+70>: xorq %fs:0x30, %rax
0x7ffff7c44f1f <+79>: rolq $0x11, %rax
0x7ffff7c44f23 <+83>: movq %rax, 0x38(%rdi)
```

`<+65>` 换成了 `movq (%rsp),%rax`。这次确实读取内存，取出当前栈顶存储的八字节返回地址：`0x7ffff7c2a181`，也就是运行库调用者的 `<+49>`。

![暂存恢复后应当处于的rip地址_1.png](https://img.mdwind.online/img/%E6%9A%82%E5%AD%98%E6%81%A2%E5%A4%8D%E5%90%8E%E5%BA%94%E5%BD%93%E5%A4%84%E4%BA%8E%E7%9A%84rip%E5%9C%B0%E5%9D%80_1.png)

它没有读取当前 `%rip`。当前正在执行的是保存函数内部的指令，而将来需要接续的是原始调用之后的位置；那个位置已经由 `callq` 压在栈顶，直接取出即可。

## A.4 影子栈、保存标志与第一次返回

前八个机器状态槽位已经写入，接续所需的普通寄存器、栈位置和代码位置都有了记录。接下来，`__sigsetjmp` 检查是否还需要保存影子栈指针，再进入后续函数处理信号阻塞集的保存标志，最后返回运行库调用者。

### A.4.1 普通栈之外，为什么还有一份返回记录

```asm
0x7ffff7c44f27 <+87>:  testl  $0x2, %fs:0x48
0x7ffff7c44f33 <+99>:  je     0x7ffff7c44f3e ; <+110>
0x7ffff7c44f35 <+101>: rdsspq %rax
0x7ffff7c44f3a <+106>: movq   %rax, 0x58(%rdi)
0x7ffff7c44f3e <+110>: jmp    0x7ffff7c44f50
```

![检查是否启用影子栈的标记位_1.png](https://img.mdwind.online/img/%E6%A3%80%E6%9F%A5%E6%98%AF%E5%90%A6%E5%90%AF%E7%94%A8%E5%BD%B1%E5%AD%90%E6%A0%88%E7%9A%84%E6%A0%87%E8%AE%B0%E4%BD%8D_1.png)

![检查是否启用影子栈的标记位_2.png](https://img.mdwind.online/img/%E6%A3%80%E6%9F%A5%E6%98%AF%E5%90%A6%E5%90%AF%E7%94%A8%E5%BD%B1%E5%AD%90%E6%A0%88%E7%9A%84%E6%A0%87%E8%AE%B0%E4%BD%8D_2.png)

这里涉及 Intel CET 的另一项机制：影子栈（Shadow Stack）。前面讨论的 IBT 检查间接调用和跳转的目标位置，影子栈则维护函数调用的返回关系。

普通调用中，`call` 把返回地址压入普通栈；启用影子栈保护后，处理器还会在影子栈中保存一份返回地址。执行 `ret` 时，处理器检查两份返回地址是否一致。不一致，就触发控制保护异常。

这相当于在普通栈之外保留了一份受保护的返回记录。普通栈中的返回地址若被改写，受保护的另一份仍可用于返回检查。影子栈页面具有专门的访问保护，普通内存写指令无法像改写普通栈那样随意修改其中的记录。

普通栈除了返回地址，还存放局部变量、暂存寄存器等数据。影子栈主要维护返回记录，两者推进的步幅和使用方式不同，需要各自的指针：普通栈使用 `%rsp`，影子栈使用 SSP。这里的 `rdsspq` 就是读取影子栈指针的指令。

#### A.4.1.1 非局部恢复怎样影响两套栈

设想外层函数保存了接续点，之后依次调用中间函数和内部函数。正常返回时，每次 `ret` 都使用并撤去当前一层的返回记录，两套栈随着调用与返回保持对应。

如果内部函数发起非局部跳转，普通栈位置被直接恢复到外层，控制流也接回外层的代码，中间那些普通返回便被跨过了。影子栈若还停留在较深调用对应的位置，后续返回就可能出现错位。

| 时刻 | 普通栈及执行位置 | 影子栈 |
| --- | --- | --- |
| 内部函数发起恢复前 | 对应内部调用层次 | 维护当前调用链的返回记录 |
| 只恢复普通栈并跳回外层 | 已接回外层 | 仍可能停在被跨过的调用层次 |
| 外层随后沿原调用关系返回 | 取出外层应使用的返回地址 | 取出的记录可能属于另一层调用 |

间接 `jmp` 只转移执行流，不会像 `ret` 那样消费对应的影子栈返回记录。普通 `longjmp` 接续后，程序还可能继续业务逻辑，并在以后从外层函数正常返回，所以恢复实现需要协调影子栈位置。

glibc 的通用 x86-64 恢复实现中，可以看到读取保存的 SSP、使用 `rstorssp` 或 `incsspq` 等专门指令进行调整的逻辑。保存 SSP 时尚处于 `setjmp` 调用内部，接续目标却是调用已经返回的位置；源码还专门计入了越过这一次保存调用所需的额外调整。它与上一节普通栈保存 `%rsp+8` 的考虑相呼应。

线程退出则有不同的后续执行方式。本文对照源码所述的 glibc 取消专用恢复路径，通过内部 `__longjmp_cancel` 恢复必要机器状态，而不恢复 SSP；这一结论针对该内部路径。本次静态图没有实际触发取消恢复，也没有执行影子栈启用时的保存分支。接续后执行的是退出收尾，最后结束线程，不再通过被跨过的旧调用帧逐层返回。

这时，旧影子栈记录不再用于完成那些旧调用的返回。收尾代码仍然可以调用其他函数：新的 `call` 会建立新的返回记录，相应的 `ret` 使用这些新记录，结束后继续收尾。关键在于，它最终不会再沿旧调用链返回。

所以，普通非局部跳转与线程退出是否需要恢复这部分状态，取决于接续后怎样执行。通用恢复要为后续正常返回准备一致的返回关系；取消专用路径则利用退出过程不再通过旧调用帧返回的特点，只恢复其所需的状态。这也与上一节私有空间可以复用的布局相联系。

### A.4.2 本次跳过 SSP 保存

若进入保存分支，`rdsspq %rax` 会读取 SSP，随后将其写入 `%rdi+0x58`。按本次保存区起点 `0x7fffffffe080` 计算，这个位置是 `0x7fffffffe0d8`，对应前面结构体的 `private_tail` 起点。

这八字节与外层私有区域存在空间复用；在取消专用路径中，恢复方并不使用这份 SSP 记录。本次分支直接跳过，`+0x58` 没有由这两条指令写入。

影子栈保存属于公共保存实现的可选能力。这里继续通过 `jmp` 进入下一部分，原先栈顶的返回地址仍保持不变。

### A.4.3 进入后续函数，建立自己的栈帧

```asm
0x7ffff7c44f59 <+9>:  movq  %rdi, %rbx
```

`xorl %eax,%eax` 将 `%eax` 清零，提供这次保存调用正常返回时的返回值。之后，调用者将使用这个零选择正常执行路径。

`movq -0x8(%rbp),%rbx` 从 `0x7fffffffe048` 读回旧值，恢复 `%rbx=0x7fffffffe178`。本层对 `%rbx` 的临时使用到这里结束。

接着执行 `leave`。

![将两个栈指针恢复为退出这一层的状态_1.png](https://img.mdwind.online/img/%E5%B0%86%E4%B8%A4%E4%B8%AA%E6%A0%88%E6%8C%87%E9%92%88%E6%81%A2%E5%A4%8D%E4%B8%BA%E9%80%80%E5%87%BA%E8%BF%99%E4%B8%80%E5%B1%82%E7%9A%84%E7%8A%B6%E6%80%81_1.png)

它可以按下面两个动作理解：

```asm
movq %rbp, %rsp

```

先将 `%rsp` 移到本层栈帧基准 `0x7fffffffe050`，撤去基准以下的使用空间；再从该位置取出旧 `%rbp`，使 `%rbp` 恢复为 `0x7fffffffe0f0`。弹栈后，`%rsp` 到达 `0x7fffffffe058`，重新指向最初保存调用的返回地址。

![再退出一次 恢复回到 main 调用者状态_1.png](https://img.mdwind.online/img/%E5%86%8D%E9%80%80%E5%87%BA%E4%B8%80%E6%AC%A1%20%E6%81%A2%E5%A4%8D%E5%9B%9E%E5%88%B0%20main%20%E8%B0%83%E7%94%A8%E8%80%85%E7%8A%B6%E6%80%81_1.png)

![再退出一次 恢复回到 main 调用者状态_2.png](https://img.mdwind.online/img/%E5%86%8D%E9%80%80%E5%87%BA%E4%B8%80%E6%AC%A1%20%E6%81%A2%E5%A4%8D%E5%9B%9E%E5%88%B0%20main%20%E8%B0%83%E7%94%A8%E8%80%85%E7%8A%B6%E6%80%81_2.png)

最后的 `retq` 取出 `0x7ffff7c2a181` 并转移执行流，`%rsp` 随之增加八字节，回到 `0x7fffffffe060`。这与上一节保存的接续栈位置相同。

这里经历的是第一次调用的正常返回。虽然实现中经过了 `_setjmp`、`__sigsetjmp` 和后续保存函数，但中间用 `jmp` 衔接，最终只有最初那条 `callq` 对应的返回地址需要由 `retq` 使用。

返回后的关键状态为：

```text
rip = 0x7ffff7c2a181    运行库调用者 <+49>
rsp = 0x7fffffffe060   保存调用返回后的栈位置
rbp = 0x7fffffffe0f0   运行库调用者的栈帧基准
eax = 0               首次正常返回值
```

运行库随后检查 `%eax`：

```asm
0x7ffff7c2a181 <+49>: endbr64
0x7ffff7c2a185 <+53>: testl %eax, %eax
0x7ffff7c2a187 <+55>: jne   0x7ffff7c2a1d1 ; <+129>
```

本次为零，继续向下填写节点关联信息并登记当前节点。若以后经相应的非局部恢复路径重新接续到这里，非零返回值则会使执行流进入另一条处理分支。节点登记的具体指令留到下一节继续对照。

## A.5 关联清理边界，登记恢复节点

保存函数已经正常返回，运行库重新取得执行权。此时，局部对象中已经记录了接续所需的机器状态，接下来还要把它与线程原有的恢复关系关联起来，并登记为当前恢复节点。

这段代码先检查保存调用的返回值，再填写两个指针成员，最后更新线程中的节点入口。

```asm
0x7ffff7c2a181 <+49>: endbr64
0x7ffff7c2a185 <+53>: testl  %eax, %eax
0x7ffff7c2a187 <+55>: jne    0x7ffff7c2a1d1 ; <+129>

0x7ffff7c2a189 <+57>: movq   %fs:0x300, %rax
0x7ffff7c2a192 <+66>: movq   %rax, -0x28(%rbp)
0x7ffff7c2a196 <+70>: movq   %fs:0x2f8, %rax
0x7ffff7c2a19f <+79>: movq   %rax, -0x20(%rbp)
0x7ffff7c2a1a3 <+83>: leaq   -0x70(%rbp), %rax
0x7ffff7c2a1a7 <+87>: movq   %rax, %fs:0x300
```

### A.5.1 这里所说的清理，具体清理什么

线程执行过程中，可能已经持有互斥锁、申请了堆内存，或者打开了文件。正常完成工作时，可以在后续代码中解锁、释放内存、关闭文件。如果线程提前退出或被取消，这些后续操作就可能没有机会执行。

线程清理处理器（cleanup handler）为这种情况提供了一种安排：程序事先登记一个回调函数及其参数，在线程取消或通过 `pthread_exit` 退出时，由线程库按相应规则调用它。回调可以执行解锁、释放某块内存等收尾操作，具体负责哪些资源，由登记的函数决定。

这里涉及的 `%fs:0x2f8`，对应本次 glibc 实现中旧式清理处理器链表的头指针。链上的节点记录清理回调、参数以及前一个节点等信息。“旧式”指 glibc 为兼容维护的内部表示；线程清理接口的实现还可以与栈展开机制配合。

登记顺序具有明确作用：对相应清理处理器，按后登记先处理的方式组织，适合与嵌套的资源取得和释放相对应。完整的线程退出还包含其他阶段，例如线程专有数据析构；这些阶段之间的关系，需要结合整个退出机制来看。一条清理链表的顺序，描述的是它所管理的那组处理器。

本节没有登记新的旧式清理处理器。它做的是保存当前清理链表的位置，使新的恢复节点带有与之对应的清理边界。

```asm
0x7ffff7c2a187 <+55>: jne   0x7ffff7c2a1d1 ; <+129>
```

上一节的 `retq` 已将执行流送回 `<+49>`，当前 `%rsp=0x7fffffffe060`，`%rbp=0x7fffffffe0f0`，`%eax=0`。

```c
current_node->saved_cleanup_head = thread->cleanup;
```

这个成员记录的是建立当前恢复关系时，线程旧式清理处理器链表的头指针，也就是当前恢复节点对应的清理边界。它不新增清理处理器，只保存登记这一刻的清理链位置。此后如果又压入了新的清理处理器，那么在线程取消、`pthread_exit` 或内部展开回到当前恢复节点时，线程退出机制会从当前清理链头开始，按后进先出的顺序执行登记在该边界之后的处理器，直到到达 `saved_cleanup_head` 保存的边界为止；在这里讨论的嵌套恢复节点场景中，边界及更早的处理器留给外层恢复关系；实际展开同时结合当前栈帧位置推进。控制流最后借助运行库内部的非局部跳转恢复到当前节点的保存调用之后，表现为保存调用返回非零，进入该节点的退出处理分支。清理处理器的执行和 `longjmp` 的控制转移是两件事：前者由线程退出/展开逻辑按边界驱动，后者只负责把执行流送到恢复点。

例如，登记恢复节点时已有清理处理器甲，节点保存甲的位置；后来又依次登记乙、丙。展开到这一层时，先执行丙、乙，遇到甲这个保存的边界后停止；甲留给外层关系处理。这里“边界之外”是相对于当前恢复节点而言：从内层看是后压入的乙、丙，从外层看甲才是它要处理的范围。实际展开还会结合当前栈帧位置，决定这一轮应推进到哪里。本次保存的边界为空，表示登记这一刻旧式清理链上没有处理器；保存空边界与非空边界使用的是同一套指令。

这里要区分两条链：`cleanup_jmp_buf` 链通过 `prev` 连接恢复/展开节点，当前对象是这条链上的新节点；旧式清理处理器链通过 `%fs:0x2f8` 维护，当前代码只保存它的边界，没有向它压入新节点。因此，`saved_cleanup_head` 记录的是“当前恢复关系对应的清理边界”，不是“当前对象在清理链上的位置”。本节只更新 `%fs:0x300`，不写 `%fs:0x2f8`，正说明这里登记的是恢复关系，而不是新的清理处理器。

恢复节点链与清理处理器链在这里发生关联：`prev` 联系此前的恢复节点，`saved_cleanup_head` 记录当前恢复节点对应的旧式清理边界。二者分别回答“恢复到哪一层”和“这一层清理到哪里为止”。

### A.5.5 将当前对象登记为新的恢复节点

```asm
0x7ffff7c2a1a3 <+83>: leaq -0x70(%rbp), %rax
0x7ffff7c2a1a7 <+87>: movq %rax, %fs:0x300
```

前两个指针成员写好以后，`leaq` 再次计算当前对象的地址。

![读取当前上下文恢复节点的基地址_1.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96%E5%BD%93%E5%89%8D%E4%B8%8A%E4%B8%8B%E6%96%87%E6%81%A2%E5%A4%8D%E8%8A%82%E7%82%B9%E7%9A%84%E5%9F%BA%E5%9C%B0%E5%9D%80_1.png)

![读取当前上下文恢复节点的基地址_2.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96%E5%BD%93%E5%89%8D%E4%B8%8A%E4%B8%8B%E6%96%87%E6%81%A2%E5%A4%8D%E8%8A%82%E7%82%B9%E7%9A%84%E5%9F%BA%E5%9C%B0%E5%9D%80_2.png)

得到 `%rax=0x7fffffffe080`。这次计算地址后，不再将它传给保存函数，而是准备交给线程的当前恢复节点入口。

![将线程维护结构体相关成员索引更新_1.png](https://img.mdwind.online/img/%E5%B0%86%E7%BA%BF%E7%A8%8B%E7%BB%B4%E6%8A%A4%E7%BB%93%E6%9E%84%E4%BD%93%E7%9B%B8%E5%85%B3%E6%88%90%E5%91%98%E7%B4%A2%E5%BC%95%E6%9B%B4%E6%96%B0_1.png)

![将线程维护结构体相关成员索引更新_2.png](https://img.mdwind.online/img/%E5%B0%86%E7%BA%BF%E7%A8%8B%E7%BB%B4%E6%8A%A4%E7%BB%93%E6%9E%84%E4%BD%93%E7%9B%B8%E5%85%B3%E6%88%90%E5%91%98%E7%B4%A2%E5%BC%95%E6%9B%B4%E6%96%B0_2.png)

执行 `<+87>` 后，线程的 `cleanup_jmp_buf` 指向当前栈上的对象。前面保存的机器状态及刚填好的关联信息，可以通过这个线程成员找到。

把主要数据流放在一起，就是下面的 C 风格表示：

```c
/* current_node 指向本次栈上的恢复节点。 */
current_node->prev = thread->cleanup_jmp_buf;
current_node->saved_cleanup_head = thread->cleanup;

/* 完成关联信息填写后，更新当前恢复节点入口。 */
thread->cleanup_jmp_buf = current_node;
```

以线程保存的指针为链表入口来看，这是头插：新节点成为当前入口，旧入口保存在新节点的 `prev` 中。本次旧入口为空，所以形成的关系是线程入口指向当前节点，当前节点的 `prev` 为空。

这里登记了新的恢复关系，没有同时登记新的旧式清理处理器。清理入口继续沿用，只把它的当前位置保存到当前节点，代码中也就没有向 `%fs:0x2f8` 写回的操作。

### A.5.6 对照本节填写的成员

| 位置 | 本次地址或访问形式 | 含义 | 本次操作后的值 |
| --- | --- | --- | --- |
| 节点 `+0x48` | `0x7fffffffe0c8` | `prev`，此前恢复节点 | `0` |
| 节点 `+0x50` | `0x7fffffffe0d0` | `saved_cleanup_head`，登记时的清理边界 | `0` |
| 线程当前恢复入口 | `%fs:0x300` | `cleanup_jmp_buf` | `0x7fffffffe080` |
| 线程旧式清理入口 | `%fs:0x2f8` | `cleanup` | 保持原值，本次为 `0` |

前几节先提供空间、填写机器状态，这一段则完成关联和登记。当前对象仍位于运行库函数的栈帧中；线程中的入口保存它的地址，将它纳入运行库维护的恢复关系。接下来，执行流继续准备 `main` 的实参，并调用 `main`。

## A.6 通过 GOT 取得环境参数，调用 main

线程恢复节点已经登记完毕，运行库开始准备调用 `main`。接下来的六条指令依次取得环境变量的访问地址、准备实参，再取回 `main` 的入口地址，完成调用。

```asm
0x7ffff7c2a1b0 <+96>:  movq  0x1d9de9(%rip), %rax
0x7ffff7c2a1b7 <+103>: movq  -0x88(%rbp), %rsi
0x7ffff7c2a1be <+110>: movl  -0x7c(%rbp), %edi
0x7ffff7c2a1c1 <+113>: movq  (%rax), %rdx
0x7ffff7c2a1c4 <+116>: movq  -0x78(%rbp), %rax
0x7ffff7c2a1c8 <+120>: callq *%rax
```

### A.6.1 为什么要先取地址，再读取变量

```asm
0x7ffff7c2a1b0 <+96>: movq 0x1d9de9(%rip), %rax
```

![读取main第三参数的二级指针_1.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E7%AC%AC%E4%B8%89%E5%8F%82%E6%95%B0%E7%9A%84%E4%BA%8C%E7%BA%A7%E6%8C%87%E9%92%88_1.png)

![读取main第三参数的二级指针_2.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E7%AC%AC%E4%B8%89%E5%8F%82%E6%95%B0%E7%9A%84%E4%BA%8C%E7%BA%A7%E6%8C%87%E9%92%88_2.png)

这里使用 RIP 相对寻址。计算基准是下一条指令的地址 `0x7ffff7c2a1b7`，加上偏移 `0x1d9de9`，得到实际读取位置：

```text
0x7ffff7c2a1b7 + 0x1d9de9 = 0x7ffff7e03fa0
```

指令从这个位置读取八字节，放入 `%rax`。结合后续操作和 glibc 的调用逻辑，这里通过 GOT 表项取得全局变量 `__environ` 的地址。本次读出的地址为 `0x7ffff7e0bd58`。

后面还有一条 `movq (%rax),%rdx`，才会读取这个变量中的值。为什么一个变量要经过这样两次读取，需要从共享库怎样引用符号说起。

#### A.6.1.1 RIP 相对寻址能解决什么

假设共享库中有一个整数变量，某个函数要读取它：

```c
int value;

int read_value(void)
{
    return value;
}
```

如果已经确定访问的就是本模块内的定义，而且指令与变量之间的相对位置能够在链接时确定，就可以生成类似下面的访问：

```asm
movl value(%rip), %eax
```

整个模块换一个装载地址，指令与变量随模块一起移动，二者之间的距离仍保持不变。代码依靠这个距离找到变量，无需把某次运行的绝对地址固定在指令里。

这说明，位置无关代码可以利用模块内部的相对位置访问数据。GOT 要处理的情况还多一层：最终访问的符号定义，可能并不在当前模块预先确定的那个位置。

#### A.6.1.2 符号引用最终采用哪个定义

ELF 动态链接中，某些符号引用允许参与运行时的符号查找。即使共享库自身定义了一个默认可见的全局符号，该引用也可能按照解析规则绑定到其他模块提供的定义，这涉及符号抢占或符号介入（symbol interposition）。

例如，主程序与共享库都提供名为 `value` 的全局符号。对于允许参与动态查找的引用，最终采用哪个定义，需要结合符号的绑定、可见性和查找范围等规则确定。函数内部局部变量遮蔽全局变量，则通常在编译时已经确定引用对象，属于另一类名字解析。

至此，可以区分两种地址问题：

| 问题 | 能否只依靠本模块内部的固定相对位置解决 |
| --- | --- |
| 本模块装载到哪里 | 指令与目标随模块一起移动时可以 |
| 本次引用最终采用哪个模块中的定义 | 还需要确定实际符号绑定 |

GOT，即全局偏移表（Global Offset Table），在代码与实际目标之间提供一层间接访问。代码先找到本模块的表项，表项再给出最终目标地址。例如：

```asm
movq value@GOTPCREL(%rip), %rax  # 读取表项，取得 value 的地址
movl (%rax), %eax               # 通过这个地址读取整数值
```

代码与本模块表项之间的相对位置，可以预先安排；表项中的目标地址，则交给链接和装载过程确定。这让代码保持稳定的访问方式，适应运行时采用的实际地址。

#### A.6.1.3 谁建立表项，谁填写地址

编译器生成访问符号的指令及相关重定位信息，链接器安排所需的 GOT 表项，并在需要时留下动态重定位记录。运行时的动态链接器依据这些记录完成符号查找，将解析出的地址写入对应位置。

几种信息在这个过程中各有用途：

| 信息 | 承担的工作 |
| --- | --- |
| 动态符号及相关名字信息 | 描述需要查找的符号 |
| 重定位记录 | 指明需要处理的位置及处理方式 |
| GOT 表项 | 保存代码实际使用的地址结果 |

本次访问数据符号时，CPU 执行的是对已填写表项的普通内存读取。符号解析的结果已经成为一个可直接使用的地址，访问代码无需每次按名字重新查找。

相关 ELF 模块分别拥有自己的 GOT 设施。这里的统一性体现在访问方式：使用方通过约定的表项取得目标，具体目标由解析和重定位过程落实。它无需是一张覆盖整个进程所有资源的总表，也无需在每次访问时更新。

#### A.6.1.4 将地址变化集中到表项中

如果把运行时需要修正的目标地址直接放在指令里，装载时就可能需要修改相应代码页。GOT 把这类变化集中到地址表项中，机器指令继续使用既定的寻址方式，减少了修改代码区的需求，也有利于保留可共享的代码页。

多处指令引用同一符号时，还可以使用相应的共同表项。动态链接器按符号解析规则选定目标，填写地址；使用方随后读取这个结果。选择目标与使用目标在这层表项处衔接起来。

表项能够在重定位阶段被填写，并不要求它在整个运行期间始终可写。完成相关重定位后，部分区域可以配合 RELRO 等保护转为只读。这里讨论的灵活性，是地址能够按装载结果安排，而不是程序运行中任意改写目标的接口。

#### A.6.1.5 为什么保存对象地址，而不是复制对象的值

变量的地址使代码能够继续访问实际对象。若 GOT 只保存整数变量在某个时刻的数值，原变量修改以后，表项中的副本便可能过期；写入副本，也不会自动修改原对象。多处引用各自复制数据，还需要额外处理它们之间的同步关系。

表项保存对象地址后，不同模块中绑定到同一个定义的引用，可以通过各自的访问设施读写同一个实际对象。变量保留自己的存储位置、大小及可变状态，表项负责提供通向它的地址。

这个安排也适用于大小、类型不同的对象：表项提供地址，具体访问宽度和操作由使用代码确定。它本身无需复制不同大小的变量值，也不承担识别 C 类型的职责。对于函数地址，使用方取得目标后进行调用；对于数据地址，使用方按照所需类型读取或写入。

从结构上看，这与 C++ 虚表具有相似的间接访问思路：使用方按约定找到表项，再通过表项取得具体目标。虚表服务于虚函数分派，GOT 服务于这里的符号地址访问，各自采用不同的目标选择规则，却都让稳定的使用方式与具体目标之间多了一层可安排的关系。

### A.6.2 回到 __environ：三个地址层次

`__environ` 本身是一个指针变量，可以用下面的声明理解：

```c
char **__environ; // 指向环境字符串指针数组
```

所以，GOT 中提供的变量地址，与该变量中保存的数组地址，要分开看。

| 层次 | 本次位置或数值 | 含义 |
| --- | --- | --- |
| GOT 表项位置 | `0x7ffff7e03fa0` | 本条 RIP 相对寻址找到的读取位置 |
| 表项中保存的地址 | `0x7ffff7e0bd58` | `__environ` 变量的地址 |
| `__environ` 的值 | `0x7fffffffe188` | 环境字符串指针数组的地址，即本次 `envp` |

若用 C 风格表示这两次读取的数据关系，就是：

```c
char ***environ_address = /* 从 GOT 表项取得的变量地址 */;
char **envp = *environ_address;
```

第一次取得变量所在位置，第二次取得变量当前保存的值。这里始终访问实际变量，不另外复制一份环境数组。

本次材料直接展示了 RIP 相对寻址和随后两次读取的数据关系。该表项的具体重定位类型、最终绑定来源，以及是否发生符号介入，还需要实验文件的动态重定位表与运行时绑定证据进一步核验。

### A.6.3 从栈上取回 argv 和 argc

```asm
0x7ffff7c2a1b7 <+103>: movq -0x88(%rbp), %rsi
0x7ffff7c2a1be <+110>: movl -0x7c(%rbp), %edi
```

GOT 读取之后，代码先准备另外两个参数。第 A.1 节保存入口参数时，已经将 `argv` 和 `argc` 写入运行库自己的栈帧，现在从那里取回。

![读取main第二参数argv_1.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E7%AC%AC%E4%BA%8C%E5%8F%82%E6%95%B0argv_1.png)

![读取main第二参数argv_2.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E7%AC%AC%E4%BA%8C%E5%8F%82%E6%95%B0argv_2.png)

`<+103>` 从 `%rbp-0x88=0x7fffffffe068` 读取八字节指针，本次为 `0x7fffffffe178`，放入 `%rsi`，作为 `main` 的第二个参数 `argv`。

![读取main第一参数argc_1.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E7%AC%AC%E4%B8%80%E5%8F%82%E6%95%B0argc_1.png)

![读取main第一参数argc_2.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E7%AC%AC%E4%B8%80%E5%8F%82%E6%95%B0argc_2.png)

`<+110>` 从 `%rbp-0x7c=0x7fffffffe074` 读取四字节整数，本次为 1，放入 `%edi`，作为第一个参数 `argc`。写入 `%edi` 同时清零 `%rdi` 的高 32 位。

同一份数据进入不同函数时，参数位置也会变化。`argc` 此前是本运行库函数的第二个参数，由 `%esi` 传入；现在成为 `main` 的第一个参数，由 `%edi` 传出。`argv` 则从此前的第三个参数变成第二个参数，交给 `%rsi`。

栈上的暂存使原始入口参数跨过了前面的上下文保存与节点登记；到了实际调用 `main` 时，运行库再把它们放进本次调用需要的寄存器。

### A.6.4 读取环境数组地址，准备第三个参数

```asm
0x7ffff7c2a1c1 <+113>: movq (%rax), %rdx
```

![读取main第三参数的指针_1.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E7%AC%AC%E4%B8%89%E5%8F%82%E6%95%B0%E7%9A%84%E6%8C%87%E9%92%88_1.png)

![读取main第三参数的指针_2.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E7%AC%AC%E4%B8%89%E5%8F%82%E6%95%B0%E7%9A%84%E6%8C%87%E9%92%88_2.png)

此时 `%rax` 仍为前面取得的 `0x7ffff7e0bd58`。这条指令读取该地址中的八字节数值，得到环境数组地址 `0x7fffffffe188`，放入 `%rdx`。

glibc 的这条通用启动路径按三个实参准备调用：`argc`、`argv`、`envp`。环境数组中的元素指向相应的环境字符串，数组最后以空指针结束。

第三个环境参数属于此实现支持的惯例；ISO C 常见的 `main` 定义仍是无参数或 `argc`、`argv` 两参数形式。本次应用程序写成 `int main(void)`，运行库仍按自身预先编译好的通用流程准备寄存器，`main` 按自己的代码使用需要的数据。

至此，参数状态为：

| 参数 | 寄存器 | 本次值 |
| --- | --- | --- |
| `argc` | `%edi` | `1` |
| `argv` | `%rsi` | `0x7fffffffe178` |
| `envp` | `%rdx` | `0x7fffffffe188` |

### A.6.5 取回 main 入口，执行间接调用

```asm
0x7ffff7c2a1c4 <+116>: movq  -0x78(%rbp), %rax
0x7ffff7c2a1c8 <+120>: callq *%rax
```

![读取main入口地址_1.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E5%85%A5%E5%8F%A3%E5%9C%B0%E5%9D%80_1.png)

![读取main入口地址_2.png](https://img.mdwind.online/img/%E8%AF%BB%E5%8F%96main%E5%85%A5%E5%8F%A3%E5%9C%B0%E5%9D%80_2.png)

`%rbp-0x78=0x7fffffffe078` 中保存着第 A.1 节暂存的 `main` 函数指针。执行 `<+116>`，将本次入口地址 `0x55555566abc8` 读入 `%rax`。

环境参数已经交给 `%rdx`，`%rax` 现在转而承担提供调用目标的任务。

![call main_1.png](https://img.mdwind.online/img/call%20main_1.png)

![call main_2.png](https://img.mdwind.online/img/call%20main_2.png)

图中处于 `callq *%rax` 尚未执行的时刻。三个参数和目标地址已经准备好，当前 `%rsp=0x7fffffffe060`，`%rbp=0x7fffffffe0f0`。

执行这条寄存器间接调用时，处理器先把下一条指令地址 `0x7ffff7c2a1ca` 压入普通栈，再转移到 `%rax` 指向的入口。按这条指令推演，进入 `main`、尚未执行其第一条指令时，状态为：

```text
rip = 0x55555566abc8    main 入口
rsp = 0x7fffffffe058   call 压入返回地址后的栈顶
rbp = 0x7fffffffe0f0   此刻仍为运行库调用者的栈帧基准

[0x7fffffffe058] = 0x7ffff7c2a1ca
```

这次压栈使用了前面 `_setjmp` 调用曾使用过的位置，写入的是新的返回地址。`main` 此时还没有执行自己的 `pushq %rbp`，随后才会保存调用者的帧指针并建立自己的栈帧。到这里，运行库的调用准备与正文中 `main` 的起点接上了。

## A.7 从 main 返回，进入进程退出处理

```asm
; main 的调用者
0x7ffff7c2a1c8 <+120>: callq  *%rax
0x7ffff7c2a1ca <+122>: movl   %eax, %edi
0x7ffff7c2a1cc <+124>: callq  0x7ffff7c47ba0 ; exit

; exit
0x7ffff7c47ba0 <+0>:   endbr64
0x7ffff7c47ba4 <+4>:   pushq  %rbp
0x7ffff7c47ba5 <+5>:   movl   $0x1, %ecx
0x7ffff7c47baa <+10>:  movl   $0x1, %edx
0x7ffff7c47baf <+15>:  leaq   0x1bcaca(%rip), %rsi
0x7ffff7c47bb6 <+22>:  movq   %rsp, %rbp
0x7ffff7c47bb9 <+25>:  callq  0x7ffff7c47910 ; 对应 __run_exit_handlers
```

前面已经走过了调用 `main` 之前的准备过程。正文也已经展示了 `main` 怎样建立栈帧、调用 `Add`，以及最后怎样撤销自己的栈帧。现在，我们从 `main` 的返回位置继续向后看。

### A.7.1 当前由谁执行，又准备结束谁

从这里开始，执行流进入进程退出阶段。本次仍由主线程执行：它完成 `main` 的调用，接收返回值，再调用 `exit`，组织整个进程结束前的收尾。

这里需要同时留意两件事：当前执行代码的线程，以及这些操作所针对的生命周期。主线程调用 `pthread_exit`，结束的是自身线程；只要还有其他线程存活，进程就可以继续运行。而这里调用的 `exit` 将结束整个进程，进程中仍然存活的其他线程最终也会被终止。

我们正在跟踪的这条从 `main` 正常返回的路径由主线程执行。至于 `exit` 本身，任意线程都可以调用，调用者同样会触发进程退出。因此，后面这些工作的进程级作用范围，来自 `exit` 的职责。

以进程退出为目标的收尾，其中仍然包含针对当前线程的处理。接下来会看到，运行库先检查当前线程的线程局部存储（TLS）析构，再处理进程范围内登记的退出回调，随后还有动态链接器组织的模块终结以及标准 I/O 收尾。它们处在同一条退出路径中，处理对象却有不同的范围。

其他线程最终被终止，也不能据此认为它们都会完整执行各自的线程退出清理。观察当前线程实际执行的收尾时，仍然需要把这一范围保留下来。

### A.7.2 把 main 的返回结果交给 exit

```asm
0x7ffff7c2a1ca <+122>: movl %eax, %edi
0x7ffff7c2a1cc <+124>: callq 0x7ffff7c47ba0 ; exit
```

正文末尾，`main` 将 `%eax` 清零，撤销自己的栈帧，再执行 `retq`。先前调用 `main` 时，`callq` 压入的返回地址是 `0x7ffff7c2a1ca`，所以普通返回之后，执行流来到这里。

按照本次使用的调用约定，整数返回值放在 `%eax` 中，第一个整数参数则通过 `%edi` 传递。因此，`<+122>` 把刚刚取得的返回值复制到下一个函数接收参数的位置。随后调用 `exit`，这个数值就成为传入的退出状态。

从前后联系来看，可以写成下面这样的 C 代码：

```c
int result = main(argc, argv, __environ);
exit(result);
```

这里是对运行库调用逻辑的概括。本程序中的 `main` 返回 `0`，所以这次调用相当于 `exit(0)`。数值没有改变，它在调用关系中的作用发生了变化：先是 `main` 的返回结果，随后成为 `exit` 的实参。

至此，正文中的 `return 0` 也与进程退出联系起来。`main` 先完成自身的函数返回，运行库接过它的结果，继续承担结束进程之前的工作。

### A.7.3 exit 准备了哪些参数

```asm
0x7ffff7c47ba0 <+0>:   endbr64
0x7ffff7c47ba4 <+4>:   pushq  %rbp
0x7ffff7c47ba5 <+5>:   movl   $0x1, %ecx
0x7ffff7c47baa <+10>:  movl   $0x1, %edx
0x7ffff7c47baf <+15>:  leaq   0x1bcaca(%rip), %rsi
0x7ffff7c47bb6 <+22>:  movq   %rsp, %rbp
0x7ffff7c47bb9 <+25>:  callq  0x7ffff7c47910
```

`exit` 的入口很短。`endbr64` 的含义前面已经讨论过，`pushq %rbp` 和 `movq %rsp, %rbp` 也仍然是在建立当前函数的栈帧。具体的退出处理被交给另一个内部函数，所以中间几条指令主要用于准备新的实参。

LLDB 在这里将目标显示为未命名的内部符号。结合 glibc 源码及后续汇编，可以把它对应到 `__run_exit_handlers`，其调用形式为：

```c
__run_exit_handlers(status, &__exit_funcs, true, true);
```

四个参数与寄存器的关系如下：

| 参数 | 传递位置 | 本次内容 | 作用 |
|---|---|---|---|
| `status` | `%edi` | `0` | 进程退出状态 |
| `listp` | `%rsi` | `&__exit_funcs` | 退出回调链表头指针变量的地址 |
| `run_list_atexit` | `%edx` | `1` | 启用退出回调处理之后的标准 I/O 收尾 |
| `run_dtors` | `%ecx`，内部检查 `%cl` | `1` | 启用当前线程的 TLS 析构处理 |

第一个参数已经放在 `%edi` 中，这几条指令没有改写它，内部函数可以继续接收同一个值。第二个参数通过 `leaq` 准备，第三、第四个参数分别写入 `%edx` 和 `%ecx`。

这也再次体现了参数寄存器的分工：上层完成一次参数传递后，当前函数又成为下一次调用的调用者，继续按约定安排寄存器。参数准备的指令顺序可以变化，只要在实际调用时，各参数已经位于规定的位置即可。

两个值为 `1` 的参数控制不同阶段。`run_dtors` 决定是否先执行当前线程的 TLS 析构处理；`run_list_atexit` 在这一实现中控制末尾是否调用 `_IO_cleanup`，进行标准 I/O 收尾。进程退出回调链表的遍历由内部函数的主体完成，不能仅凭 `run_list_atexit` 的名字，把它理解为整个回调遍历的总开关。

本次两个开关均为真。下一节进入内部函数后，就可以把这些参数与具体分支逐一对应起来。

### A.7.4 为什么传入链表头指针的地址

```asm
0x7ffff7c47baf <+15>: leaq 0x1bcaca(%rip), %rsi
```

这条指令使用下一条指令的地址作为 RIP 相对寻址的计算基准：

```text
0x7ffff7c47bb6 + 0x1bcaca = 0x7ffff7e04680
```

执行后，`%rsi` 中保存 `0x7ffff7e04680`。结合源码，这个位置对应 `__exit_funcs` 变量自身的地址。

先用一个简化声明表示：

```c
struct exit_function_list;

struct exit_function_list *__exit_funcs;
```

`__exit_funcs` 是一个指针变量，它保存退出回调链表的头节点地址。因此，这里存在几个需要分清的层次：

| 表达式 | 含义 |
|---|---|
| `&__exit_funcs` | 头指针变量自身的地址，本次为 `0x7ffff7e04680` |
| `__exit_funcs` | 变量中保存的头节点地址 |
| `*__exit_funcs` | 头指针非空时，它所指向的节点对象 |

本条 `leaq` 只计算第一层地址，不读取变量中保存的头节点地址。内部函数接收的形参类型也相应为：

```c
struct exit_function_list **listp;
```

为什么需要这一层间接访问？因为退出处理过程中，内部函数不仅要读取链表，还要在一个节点处理完后推进链表入口。通过传入头指针变量的地址，它就可以更新实际维护的头指针，例如：

```c
*listp = cur->next;
```

这样，调用方保存的链表入口也会随之变化。后面查看节点与内存时，这几个层次会直接体现在取地址、解引用及成员访问的指令中。

### A.7.5 call 留下返回地址，退出流程继续向前

```asm
0x7ffff7c2a1cc <+124>: callq 0x7ffff7c47ba0 ; exit
0x7ffff7c2a1d1 <+129>: callq 0x7ffff7c99370
```

`callq exit` 仍然遵循 `call` 的机器行为，把下一条指令的地址 `0x7ffff7c2a1d1` 压栈，再转移到 `exit`。同样，`exit` 内部的调用也会把 `0x7ffff7c47bbe` 压入栈中。

不过，`exit` 在正常情况下不会返回。运行库完成收尾后，会进入最终的进程终止路径。因此，虽然栈中存在返回地址，这条正常退出路径也不会沿这些地址逐层返回到 `_start`。

后续无 Sanitizer 的对照实验中，在内部处理函数入口查看调用栈，归档记录如下：

```text
frame #0: 0x00007ffff7c47910 libc.so.6`___lldb_unnamed_symbol_47910
frame #1: 0x00007ffff7c47bbe libc.so.6`exit + 30
frame #2: 0x00007ffff7c2a1d1 libc.so.6`___lldb_unnamed_symbol_2a150 + 129
frame #3: 0x00007ffff7c2a28b libc.so.6`__libc_start_main + 139
frame #4: 0x0000555555555075 main-debug`_start + 37
```

这里保留的是该次对照实验的原始输出，`main-debug` 的代码地址属于那份二进制。我们借助这份记录观察调用关系。

其中 `exit + 30` 与调用者的 `<+129>`，对应两次 `call` 留下的返回位置。调用栈展示这些位置，并不说明它们已经执行。尤其是 `<+129>`，前面已经见过，它还有来自 `_setjmp` 非零返回分支的入口；本次 `main` 正常返回后调用 `exit`，不会再从 `exit` 普通返回到那里。

现在，退出状态、链表入口和两个控制参数都已准备完成。执行流从 `exit` 进入内部处理函数，接下来便可以看这些收尾工作怎样依次展开。

## A.8 当前线程的 TLS 析构与进程退出回调的组织

```asm

0x7ffff7c47910 <+0>:   endbr64
0x7ffff7c47914 <+4>:   pushq  %rbp
0x7ffff7c47915 <+5>:   movq   %rsp, %rbp
0x7ffff7c47918 <+8>:   pushq  %r15
0x7ffff7c4791a <+10>:  pushq  %r14
0x7ffff7c4791c <+12>:  movl   %edi, %r14d
0x7ffff7c4791f <+15>:  pushq  %r13
0x7ffff7c47921 <+17>:  pushq  %r12
0x7ffff7c47923 <+19>:  pushq  %rbx
0x7ffff7c47924 <+20>:  subq   $0x28, %rsp
0x7ffff7c47928 <+24>:  movq   %rsi, -0x38(%rbp)
0x7ffff7c4792c <+28>:  movl   %edx, -0x4c(%rbp)
0x7ffff7c4792f <+31>:  testb  %cl, %cl
```

上一节中，`exit` 已经准备好退出状态、退出回调链表入口，以及控制收尾阶段的两个开关。进入内部处理函数后，执行流首先转向当前线程的 TLS 析构检查。完成这一阶段，才开始访问进程退出回调链表。

这里把动态链接器管理的主程序、共享库等 ELF 对象称为“ELF 模块”。它们是加载与管理的单位，可以承载业务功能、运行库功能或辅助功能；一项功能也可能直接链接进主程序，并不一定对应独立的共享库。第 A.9 节引入动态链接器终结回调时，还会结合其职责继续说明。

### A.8.1 保存入口参数，先检查当前线程的析构记录

函数入口依然先建立栈帧，并保存准备使用的被调用者保存寄存器。随后几条指令把需要长期保留的入口参数安排到寄存器或当前栈帧中：

| 入口参数 | 保存或使用位置 | 后续用途 |
|---|---|---|
| `%edi` 中的退出状态 | `%r14d` | 向需要退出状态的回调及最终终止操作传参 |
| `%rsi` 中的 `&__exit_funcs` | `-0x38(%rbp)` | 读取、更新退出回调链表入口 |
| `%edx` 中的标准 I/O 收尾开关 | `-0x4c(%rbp)` | 控制末尾的标准 I/O 收尾 |
| `%cl` 中的 TLS 析构开关 | `<+31>` 立即检查 | 决定是否先执行 TLS 析构处理 |

后面还要调用其他函数，而这些入口参数需要继续使用，所以不能一直依赖入口时的参数寄存器。退出状态被复制到 `%r14d`，另外两个参数保存在当前栈帧内。前面讨论过的寄存器保存约定，在这里承担了具体任务。

本次第四个参数为真，`testb %cl, %cl` 检查后，执行流跳到 `<+597>`，调用 `__call_tls_dtors`。调用结束，再从 `<+602>` 跳回 `<+39>`，继续后面的处理。

这里处理的是当前线程登记的 TLS 对象析构记录。线程局部存储中的对象可能需要在生命周期结束时执行清理，运行库为此保存对应的函数和对象信息。本文沿用 POSIX 线程的执行背景理解即可；各种语言运行时如何把自身对象接入底层机制，属于更上层的安排。这里的具体登记机制也与 `pthread_key_create` 使用的线程特定数据析构机制有所区别，后者另有自己的管理路径。

`<+10>` 读取一个用于定位线程局部变量的偏移，随后 `<+18>` 通过 FS 基址加上这一偏移，取出当前线程的析构链表头。此前归档在 `<+23>` 停下时记录了：

```text
r12 = 0xffffffffffffff60   ; 即 -0xa0
rbx = 0x0000000000000000
```

这份实测中，当前线程的链表头为空，所以跳到 `<+94>`，恢复寄存器并返回。下面的非空循环没有在这份记录中实际执行，但结合完整汇编与 glibc 源码，可以说明它准备处理的数据及处理方式。

每个节点对应一条析构记录。本次 x86-64 布局可以简化表示为：

```c
struct TlsDestructorRecord {
    /* +0x00 */ uintptr_t encoded_func;           // 混淆后的析构函数地址
    /* +0x08 */ void *object;                     // 交给析构函数的对象
    /* +0x10 */ struct link_map *module;          // 所属模块的运行时记录
    /* +0x18 */ struct TlsDestructorRecord *next; // 下一条析构记录
};                                              // 共 0x20 字节
```

这里使用 `encoded_func` 突出内存中保存的是混淆后的地址位模式，方便与反混淆指令对照；glibc 源码中的对应成员采用函数指针类型。其余成员直接对应节点内的对象指针、模块记录和后继节点。

`<+32>` 取后继节点，`<+36>` 取函数地址。随后先右循环移位 17 位，再与 `%fs:0x30` 中的 pointer guard 异或，还原函数指针。这正好与前面见过的指针混淆过程互相对应。

`<+57>` 把对象地址放进 `%rdi`，`<+61>` 再通过 `%rax` 间接调用。概括起来，就是取出一条记录，执行类似 `func(object)` 的操作。

### A.8.3 先摘下当前记录，回调后重新读取链表头

```asm
0x7ffff7c47710 <+32>: movq 0x18(%rbx), %rdx
...
0x7ffff7c47724 <+52>: movq %rdx, %fs:(%r12)
0x7ffff7c47729 <+57>: movq 0x8(%rbx), %rdi
0x7ffff7c4772d <+61>: callq *%rax
...
0x7ffff7c47744 <+84>: movq %fs:(%r12), %rbx
0x7ffff7c47749 <+89>: testq %rbx, %rbx
0x7ffff7c4774c <+92>: jne  0x7ffff7c47710 ; <+32>
```

这个循环有一个值得注意的细节：调用回调之前，`<+52>` 已经把当前线程的链表头更新为当前记录的后继，当前记录便从待处理链表中摘下。回调结束后，循环又从线程局部存储中重新读取实际的链表头。

这一写法可以容纳回调期间发生的新登记。假设链表原来依次为 A、B，准备调用 A 时，链表头已经指向 B。若 A 的回调又登记了 C，由于登记采用头插，待处理链表就变为 C、B。回调返回后重新读取链表头，下一次取得的便是 C，之后再处理 B。

如果始终沿着调用之前暂存的后继 B 前进，就无法跟上这次插入。现在，循环以线程局部变量中实际保存的链表头为准，新登记的记录也能进入接下来的处理。

### A.8.4 为什么先处理这些 TLS 析构

```asm
0x7ffff7c4772f <+63>: movq 0x10(%rbx), %rax
0x7ffff7c47733 <+67>: lock
0x7ffff7c47734 <+68>: subq $0x1, 0x498(%rax)
0x7ffff7c4773c <+76>: movq %rbx, %rdi
0x7ffff7c4773f <+79>: callq 0x7ffff7c283e0 ; 源码对应 free
```

清理方法本身也有依赖。TLS 对象的析构函数可能位于某个 ELF 模块中，执行时还可能使用其他对象、函数或运行库服务。要完成这次析构，这些依赖就需要在调用期间仍然可用。如果已经执行相关对象的终结，或者卸载承载析构代码的模块，再回来进行 TLS 析构，就可能失去正常执行的条件。

因此，当前线程的 TLS 析构被安排在后续进程退出回调与模块终结之前。这一阶段顺序为它保留了较完整的运行环境。具体对象之间更细的依赖，仍然需要各自的生命周期设计来配合。

节点中的 `module` 成员也参与了依赖管理。`<+63>` 取得所属模块记录，`<+68>` 对该记录内的一个计数原子减一。结合源码，这个字段对应 `l_tls_dtor_count`，用于协调尚待执行的 TLS 析构与模块卸载。

计数是在析构回调返回之后递减的。这样，析构执行期间仍保留相应的待处理计数；运行库的模块卸载路径会参考这一计数，协调模块的生命周期。这里的原子操作还涉及与并发模块卸载之间的内存顺序配合，具体实现不再展开。

最后，`<+76>` 将当前登记节点的地址交给 `%rdi`，随后释放节点。被释放的是运行库保存的这条登记记录；对象本身需要怎样清理，由前面调用的析构方法负责。

### A.8.5 转向进程退出回调链表

TLS 析构处理返回后，执行流回到 `__run_exit_handlers` 的 `<+39>`。以下偏移量重新属于该函数：

```asm
0x7ffff7c47937 <+39>: leaq     0x1be66a(%rip), %rbx
0x7ffff7c4793e <+46>: xorl     %eax, %eax
0x7ffff7c47940 <+48>: movl     $0x1, %edx
0x7ffff7c47945 <+53>: lock
0x7ffff7c47946 <+54>: cmpxchgl %edx, (%rbx)
0x7ffff7c47949 <+57>: jne      0x7ffff7c47b86 ; <+630>
0x7ffff7c4794f <+63>: movq     -0x38(%rbp), %rax
0x7ffff7c47953 <+67>: movq     (%rax), %r15
0x7ffff7c47956 <+70>: testq    %r15, %r15
0x7ffff7c47959 <+73>: je       0x7ffff7c47a10 ; <+256>
```

这里开始取得进程退出回调链表所用的锁。链表中的登记信息由进程中的线程共享，访问和修改需要相应的协调。后面调用回调时还会释放、重新取得这把锁，下一节再结合完整过程讨论。

取得锁之后，`<+63>` 从当前栈帧中取回 `&__exit_funcs`，`<+67>` 读取其中保存的头节点地址，再检查节点是否为空。这正好接上上一节中“头指针变量地址”与“头节点地址”的区分。

接下来先看看这些回调是怎样表示和组织的。了解数据含义之后，再读具体选择、调用回调的汇编，会更容易把各条指令联系起来。

### A.8.6 怎样把不同形式的回调放进同一个数组

退出时需要调用的方法并不只有一种形式。有些函数没有参数，有些需要退出状态和附带数据，还有些需要对象地址以及模块归属信息。glibc 通过类型标签和联合体，把这些不同形式组织成大小一致的记录。

下面保留实际结构的主要关系，并标出本次平台上的偏移：

```c
struct ExitFunction {
    /* +0x00 */ long flavor;                 // 记录类别及槽位状态

    /* +0x08 */ union {
        void (*at)(void);                   // 无参数回调

        struct {
            void (*fn)(int status, void *arg);
            void *arg;                      // 登记时附带的数据
        } on;

        struct {
            void (*fn)(void *arg, int status);
            void *arg;                      // 对象地址或其他附带数据
            void *dso_handle;               // 所属模块的关联标识
        } cxa;
    } func;
};                                          // 共 0x20 字节
```

联合体中的成员共用存储空间，其容量由最大的一种形式决定。加上前面的 `flavor`，每个元素在这里统一占用 `0x20` 字节，便可以放进同一个数组中。

`flavor` 说明当前槽位应如何解释。与本次讨论有关的取值为：

| 值 | 名称 | 含义 |
|---|---|---|
| `0` | `ef_free` | 空闲槽位 |
| `1` | `ef_us` | 已占用、尚待填写完成的内部状态 |
| `2` | `ef_on` | 带退出状态与附带数据的回调 |
| `3` | `ef_at` | 无参数回调 |
| `4` | `ef_cxa` | 带附带数据及模块关联信息的回调 |

这些值表示互斥的类别或状态。处理一条记录时，运行库先查看标签，再选择联合体中的对应成员及调用形式。

| 记录类别 | 登记时保存的主要信息 | 执行时的调用形式 |
|---|---|---|
| `ef_at` | 函数地址 | `fn()` |
| `ef_on` | 函数地址、`arg` | `fn(status, arg)` |
| `ef_cxa` | 函数地址、`arg`、模块标识 | glibc 内部采用 `fn(arg, status)` |

这里列出的是内部记录形式。公开登记接口与内部类别之间可以存在转换，实际采用哪一种形式，要看登记实现。

其中，`status` 来自当前这次退出调用。本次 `exit(0)` 传入的状态已经保存在 `%r14d`，调用需要退出状态的回调时再取出。它由这次退出处理统一提供，不必保存在每一条登记记录中。`arg` 则属于某一次登记，各条记录可以保存不同的值。

以 `__cxa_atexit` 为例，登记可以概括为：

```c
__cxa_atexit(cleanup_object, object_address, module_handle);
```

运行库取得一个可用槽位，保存函数地址、对象地址和模块标识，并把类别设置为 `ef_cxa`。函数地址在保存时会经过指针混淆，调用前再还原。

公开的 `__cxa_atexit` 接口接收 `void (*)(void *)` 形式的函数；上面结构中的 `cxa.fn` 则展示 glibc 内部保存和调用时使用的形式。这属于当前实现与调用约定的安排，普通 C 程序不宜照此随意改换不兼容的函数指针类型。

退出时，运行库取出该记录，按相应类别准备参数，再间接调用。`dso_handle` 用于关联记录与所属模块，例如在共享模块卸载时识别相关登记；它不作为第三个参数传给这个回调。

如果一个清理方法需要更多数据，可以让 `arg` 指向一个结构体：

```c
struct CleanupContext {
    void *buffer;       // 待释放的缓冲区
    int descriptor;     // 待关闭的描述符
};
```

回调取得指针后，再按照双方约定读取成员。运行库只需要保存一个附带数据指针，具体数据怎样解释，由登记者和回调决定；这片数据也需要保持有效，直到相应回调使用完毕。

这样，统一的记录格式便能承载不同的清理任务。数组管理面对的是相同大小的元素，实际调用则依据标签保留各自所需的参数安排。

### A.8.7 用链表连接固定容量的数组块

单条记录统一之后，外层采用下面的组织方式：

```c
struct ExitFunctionList {
    /* +0x000 */ struct ExitFunctionList *next; // 后继数组块
    /* +0x008 */ size_t idx;                   // 待处理槽位的上界
    /* +0x010 */ struct ExitFunction fns[32];   // 每条记录占 0x20 字节
};                                            // 共 0x410 字节
```

每个节点容纳 32 条记录，节点之间再通过链表连接。这个固定容量数组属于节点内部；第一块节点由运行库静态分配，后续容量不足时可以动态申请新的节点。

这种组织方式可以分批扩充：通常连续登记多条记录，只需要使用当前块中的下一个槽位；需要新容量时再申请一整块，不必每条记录单独分配一个链表节点，也不必为了扩大容量搬迁整个已有数组。实现还会考虑可复用的数组块与尾部空闲槽位。需要申请新块时，新块被接入链表头，原来的节点继续保留。

记录的位置也保存了登记顺序。通常在块内从前向后使用槽位，执行退出回调时则从后向前处理；较新的块位于链表前面，也先被访问。块间次序与块内次序配合，支持按登记顺序的逆序进行处理。

这部分通常直接依照现有位置反向遍历。后面进入动态链接器的模块终结时，还会遇到依据模块依赖关系组织顺序的另一层处理。登记次序与依赖关系都影响清理，但需要结合具体机制判断它们怎样发挥作用。

`idx` 表示当前块中待处理槽位的上界。槽位可能已经被标为空闲，因此不能始终把它当作精确的有效回调数量。读取数组元素时，还需要查看各条记录的 `flavor`。

归档中，原始 Sanitizer 版本在 `<+70>` 处读到头节点地址 `0x7ffff7e05fc0`，该节点的 `idx` 为 `5`；后来的无 Sanitizer 对照版本在对应位置读到同一节点地址，`idx` 为 `1`。这两份记录来自不同实验：业务源码之外，参与程序运行的组件也会登记自己的退出工作，构建配置会影响实际看到的回调记录。

至此，当前线程的 TLS 析构检查已经结束，执行流取得了进程退出回调链表，记录及数组块的含义也有了对应。接下来再看运行库怎样选中一条记录、还原函数地址、准备参数，以及在回调返回后继续处理登记变化。

```asm

0x7ffff7c4796f <+95>:  je   0x7ffff7c47ad8 ; <+456>
0x7ffff7c47975 <+101>: subq $0x1, %rax

0x7ffff7c47980 <+112>: movq %rax, 0x8(%r15)
```

上一节已经认识了退出回调记录及其外层数组块。现在，运行库持有退出链表锁，`%r15` 指向当前节点，执行流开始从其中选择一条记录。

### A.9.1 从最后一个待处理槽位开始

节点内偏移 `0x8` 保存 `idx`。`<+88>` 读取这一上界，检查为零时转向节点处理完成的分支；还有待处理槽位时，就先减一，并在 `<+112>` 写回节点。

因此，原始 Sanitizer 版本的 `idx` 为 `5` 时，首先选择 `fns[4]`；去除 Sanitizer 后的对照版本为 `1`，首先选择 `fns[0]`。两次实验分别从各自节点的末尾向前处理。

为便于区分，相关观测并列如下。表中每列均属于相应实验，不能拼成同一次退出序列。

| 实验 | 二进制 | 头节点地址 | `idx` | 首选槽位 | 回调目标 | 是否实际命中回调后的 `<+358>` |
|---|---|---|---|---|---|---|
| 原始 Sanitizer 版本 | 原始 `build/main`，后归档于 `archive/pre-cmake-redesign/main` | `0x7ffff7e05fc0` | `5` | `fns[4]` | `0x7ffff7fca380` | 原记录未命中，出现 LSan 致命错误；额外调用链见文末补充 |
| 无 Sanitizer 对照版本 | `build/main-debug` | `0x7ffff7e05fc0` | `1` | `fns[0]` | `0x7ffff7fca380` | 已实际命中 |

两次实验的节点地址与回调目标数值相同，登记内容和数量不同。地址相同本身不能证明同一进程实例、同一次运行或相同构建；实验归属以各自的记录为准。


每条记录占 `0x20` 字节，数组在节点内的起始偏移为 `0x10`，所以目标地址可以表示为：

```c
记录地址 = 节点地址 + 0x10 + 索引 * 0x20;
```

`<+116>` 左移 5 位，完成索引乘以 32。`<+120>` 加上节点基址之后，`%rax` 仍然只包含“节点地址加索引乘以 32”。数组起点的额外 `0x10` 留在后续访存指令中。因此，`<+123>` 的 `0x10(%rax)` 才对应所选记录的 `flavor`。

接下来的比较根据标签选择调用形式：`3` 对应无参数的 `ef_at`，`4` 对应 `ef_cxa`，`2` 对应 `ef_on`。空闲及尚未填写完成的内部状态不进入这几类回调调用。本次实际选中的记录类别为 `4`，执行流跳到 `<+304>`。

`<+105>` 还保存了登记计数器 `__new_exitfn_called` 的当前值。它暂存在 `%r12` 中，等回调返回后，再用来判断期间是否发生了新登记。

### A.9.2 取出函数和参数，更新记录状态

```asm
0x7ffff7c47a40 <+304>: movq 0x18(%rax), %rcx
0x7ffff7c47a44 <+308>: movq 0x20(%rax), %r8
0x7ffff7c47a48 <+312>: movq $0x0, 0x10(%rax)
0x7ffff7c47a50 <+320>: movq %rcx, %rax
0x7ffff7c47a53 <+323>: movl %r13d, %ecx
0x7ffff7c47a56 <+326>: rorq $0x11, %rax
0x7ffff7c47a5a <+330>: xorq %fs:0x30, %rax
```

结合上一节给出的结构，几次访问可以一一对应：

| 当前寻址表达式 | 对应成员 | 操作 |
|---|---|---|
| `0x18(%rax)` | `fns[i].func.cxa.fn` | 取得混淆后的函数地址 |
| `0x20(%rax)` | `fns[i].func.cxa.arg` | 取得登记时附带的数据 |
| `0x10(%rax)` | `fns[i].flavor` | 写入 `ef_free` |

这里已经先递减了 `idx`，现在又在实际调用之前，把记录标为空闲。两个操作相互配合：前者推进当前遍历的位置，后者让其他可能检查记录的终结路径知道，这条记录已经被接手处理。

这一点与模块终结有关。进程退出处理器会访问这些记录，模块终结时的相关机制也可能访问其中属于特定模块的登记。glibc 源码在此明确说明，将 `ef_cxa` 记录预先标为空闲，是为了避免模块卸载与进程退出之间的竞争导致同一回调被调用两次。

所需的函数地址和附带数据已经取到寄存器中，可以继续使用这些副本完成调用。随后，函数地址被转移到 `%rax`，先右循环移位 17 位，再与 `%fs:0x30` 中的 pointer guard 异或，恢复实际入口地址。前面保存接续点时见过的指针混淆，在退出回调记录中再次出现。

### A.9.3 释放链表锁，再执行回调

```asm
0x7ffff7c47a63 <+339>: xchgl %ecx, (%rbx)
0x7ffff7c47a65 <+341>: cmpl  $0x1, %ecx
0x7ffff7c47a68 <+344>: jg    0x7ffff7c47b48 ; <+568>
0x7ffff7c47a6e <+350>: movl  %r14d, %esi
0x7ffff7c47a71 <+353>: movq  %r8, %rdi
0x7ffff7c47a74 <+356>: callq *%rax
```

`%rbx` 保存退出链表锁的地址，`%r13d` 此前已被清零，所以 `<+323>` 之后 `%ecx` 也是零。`xchgl` 把零写入锁，同时把原来的锁状态取回 `%ecx`，随后检查是否需要进入唤醒等待者的分支。内存形式的 `xchg` 本身提供原子交换语义。

这里为何要在调用之前解锁？因为回调要执行的工作由登记者决定，其中可能再次登记退出方法，也可能调用具有其他锁依赖的函数。登记操作还需要取得同一把链表锁；如果当前线程一直持有它，再在回调内部尝试获取，就可能等待自己尚未释放的锁。

运行库因此把共享记录的处理与回调的执行分开：先在锁保护下取得调用材料、更新记录，再释放锁，将执行权交给回调。这样，回调可以间接进入登记等需要使用这把锁的路径。

解锁时若发现有等待者，会进入 `<+568>` 所在的唤醒路径；这属于锁竞争时的处理，本节沿着无需唤醒的路径继续看。

随后，两条传参指令把这一记录转成实际调用：

```c
rdi = arg;
esi = status;
```

附带数据来自 `%r8`，退出状态来自入口时保存的 `%r14d`。本次分别为 `NULL` 和 `0`，与 `ef_cxa` 内部使用的 `fn(arg, status)` 形式对应。最后，通过 `%rax` 中的地址间接调用。

### A.9.4 本次回调为什么进入动态链接器

在 `<+356>` 调用之前，归档记录了反混淆后的目标：

```text
rax = 0x00007ffff7fca380
所属映像：ld-linux-x86-64.so.2
映像内偏移：0x5380
LLDB 显示：___lldb_unnamed_symbol_5380
```

旧版选中的 `fns[4]` 与无 Sanitizer 对照版本选中的 `fns[0]`，均指向这个入口。结合后续内部行为及 glibc 源码，可以将它对应到动态链接器的 `_dl_fini`。这里的函数名来自源码对应，LLDB 当时显示的仍是未命名符号。

上一节已经把动态链接器管理的主程序、共享库等 ELF 对象称为 ELF 模块。ELF 是本次 Linux 环境中可执行文件和共享库采用的文件格式；各个模块具有自己的代码、数据及运行时管理信息，动态链接器据此组织它们的加载和终结。

模块可以提供业务功能，也可以提供运行库或辅助功能；功能与模块并不一定一一对应。某些辅助运行时代码可以直接链接进主程序。本次 Sanitizer 的若干回调被 LLDB 识别为属于 `main` 映像，就属于需要结合实际构建结果判断的情况。

这些模块除了正常运行的代码，还可以安排生命周期末尾执行的终结方法。模块内部可能需要处理对象、释放资源或完成其他收尾。动态链接器掌握模块的加载与依赖信息，因此由 `_dl_fini` 组织这部分终结过程。

它会收集仍然加载的相关模块，根据依赖关系安排处理次序，再逐个调用模块的终结入口。假设 A 依赖 B，A 的终结方法仍可能使用 B 提供的服务，就需要在 B 的相关服务结束之前完成 A 的终结。运行期间还可能通过 `dlopen` 加载其他模块，终结时因而需要重新考虑模块之间的关系。

落实到单个模块，动态链接器会依据 `DT_FINI_ARRAY`、`DT_FINI` 等动态信息调用相应的终结函数。具体释放什么资源、改变哪些状态，由各模块的终结方法决定。代码仍然映射在进程地址空间中，也不意味着模块内部对象和服务仍保持正常运行时期的使用条件。

因此，这条通用退出记录内部还包含另一层调度：`__run_exit_handlers` 调用 `_dl_fini`，后者组织模块终结，再由各模块执行自己的收尾。模块终结完成后，动态链接器回调可以返回，运行库继续后续退出工作。

glibc 的启动过程会接收动态链接器提供的 `rtld_fini` 函数指针，并把它登记到退出处理机制中。于是，组织程序启动环境的一方，在正常退出时也获得执行收尾的机会。下一节再结合对应汇编，观察这一层调度怎样展开。

### A.9.5 登记位置与实际执行顺序

在连续登记的通常情形下，数组块与块内位置反映登记先后，退出处理器从较新的记录向较旧的记录推进。槽位还可能被复用，因此某个固定下标并不永久代表同一条登记；需要结合当前记录状态及新登记检查解释。不过，槽位复用本身不意味着运行库放弃逆登记顺序的安排。完整退出过程还包含回调内部的嵌套调用。

例如，模块终结辅助代码可以进入 `__cxa_finalize`，处理与相应模块关联的已登记记录。这样，外层退出处理器正在执行一条回调时，其中某些其他记录就可能已经通过内层终结路径得到处理。

因此，要解释完整的执行顺序，需要同时看外层逆序遍历、记录的模块归属，以及回调之间的嵌套调用。登记位置提供明确的遍历次序，单独观察位置却不足以还原整个调用过程。

这也让前面预先更新记录状态的意义更具体：多个终结入口可能接触同一批登记记录，记录状态需要让它们协调已经接手或完成的工作。后续遍历再次遇到相应槽位时，可以依据状态决定如何处理。

### A.10.1 到这里，换一种阅读方式

最初跟到这个函数时，我只确认了它的大致任务：组织进程中 ELF 模块的终结，考虑模块之间的依赖关系，再依次执行对应的终结方法。至于内部怎样收集信息、实现排序，以及处理各种特殊情况，当时并没有继续逐项追踪。

走到这里，继续逐条阅读汇编的收益已经有所变化。前面关注的是一条指令怎样修改寄存器和栈、参数怎样传递、返回位置怎样保存。现在看到的长段指令，主要在落实动态链接器的数据结构、遍历和管理规则。想理解这些规则，直接查阅对应源码，往往比先从指令中重新拼出整套逻辑更清楚。

因此，这一段保留关键汇编位置作为对照，结合源码说明整体安排。具体排序算法、审计机制及各模块自己的终结代码，就停在这里，不再逐条展开。

### A.10.2 终结方法也需要其他模块继续提供服务

前面已经把动态链接器管理的主程序、共享库等 ELF 对象称为 ELF 模块。它们在运行期间相互调用，也可能在终结时继续依赖彼此。

假设模块 A 使用模块 B 提供的服务，A 的终结方法也可能需要调用 B，才能完成自己的收尾。如果 B 已经先销毁了相关状态，A 即使还能找到函数入口，也未必仍然具备正常调用这些服务的条件。

所以，终结需要考虑模块之间的依赖：在存在明确依赖的情况下，先完成使用者的终结，再处理它所依赖的模块。模块代码是否仍在地址空间中，与模块内部对象和服务是否仍然可用，是需要分别观察的两件事。

这也解释了为什么不能简单地把最初的初始化过程倒放。程序运行期间可能通过 `dlopen` 加载其他模块，模块集合及其依赖关系已经发生变化。glibc 源码因此在终结阶段重新组织模块次序，以适应退出时实际存在的加载关系。

这套安排依据动态链接器掌握的信息进行。具体业务在指针、回调和对象之间建立的所有关系，并不会自动全部转化为加载器可识别的模块依赖；终结方法自身仍然需要遵守相应的生命周期约定。

### A.10.3 先准备处理清单，再交给模块执行

从源码整体看，`_dl_fini` 按动态链接命名空间遍历模块。这里的命名空间可以理解为动态链接器分别管理的模块集合及符号查找范围。普通程序主要涉及默认集合，更复杂的加载方式还可以使用其他集合。本文只需要知道，它会按这些管理单位组织处理。

对于当前集合，运行库先在加载器锁保护下取得模块信息，建立临时的模块指针数组。数组元素指向动态链接器保存的模块运行时记录，也就是 `link_map` 对象。随后，根据模块依赖安排数组中的处理顺序。

这样的数组相当于本轮终结的处理清单：既便于排序，后面也可以依据它继续工作，而不用始终沿着原来的加载链表前进。

准备清单时，还会临时增加相关模块的打开计数，避免处理期间模块被卸载。清单保存的是指针，所以除了知道要处理谁，还需要保证使用这些指针时，对应模块仍然存在。

完成这些准备后，动态链接器释放加载器锁，再调用各模块的终结方法。终结代码可能直接或间接进入其他运行库路径，其中也可能需要使用加载器锁。先整理好本轮清单、保护模块生命周期，再释放锁执行，便能为这些调用留下条件。

这里与上一节的安排形成了联系：退出回调管理器调用回调之前释放退出链表锁，动态链接器调用模块终结方法之前释放加载器锁。两把锁保护不同的结构，但都需要考虑把执行权交给外部代码后可能发生什么。

### A.10.4 从模块次序进入模块自身的终结入口

排序完成后，动态链接器沿数组逐个取得模块记录，结合模块状态判断是否需要执行终结，再把当前记录交给内部的 `_dl_call_fini`。上面的 `<+435>` 对应源码中对初始化状态 `l_init_called` 的检查。

这一层调用主要根据模块动态信息找到相应的终结入口。其中，`DT_FINI_ARRAY` 描述一组终结函数，当前实现从数组末尾向前执行；随后再调用存在的 `DT_FINI` 入口。这里也就从运行库统一组织的过程，进入了模块各自安排的收尾。

模块的终结方法可能处理内部对象、释放资源，还可能通过模块关联的登记机制进一步执行退出回调。具体任务要看对应模块的实现。本文在这里确认调度关系，不继续进入每个模块逐项查看。

需要区分的是两层顺序：`_dl_fini` 安排模块之间的终结次序，单个模块的终结入口再执行其内部安排。加上上一节见过的退出回调嵌套关系，完整退出过程需要结合这些层次来理解。

### A.11.1 退出记录处理完毕，结束链表管理

归档中的对照实验实际停在了 `<+456>`。此时，当前节点的 `idx` 已经为零，没有更多槽位需要遍历。

`<+456>` 读取节点的 `next`，随后取回头指针变量的地址，在 `<+463>` 把链表入口推进到后继节点。若还有后继，便释放刚刚处理完的动态节点，再继续处理后面的数组块。

链表末端是运行库静态分配的初始节点，它本身也容纳回调记录。处理到它时，后继为空，执行流直接转向 `<+256>`，不会调用 `free` 释放这块静态存储。头指针已经更新为空，而初始节点的存储仍然存在。

这也与前面分块扩充的方式相互对应：容量不足时动态申请新的数组块，处理完后逐块回收；最初静态提供的数组块则有不同的存储期。

```asm

0x7ffff7c47a12 <+258>: movb  $0x1, 0x1be9cf(%rip)
0x7ffff7c47a19 <+265>: xchgl %eax, (%rbx)
0x7ffff7c47a1b <+267>: cmpl  $0x1, %eax
0x7ffff7c47a1e <+270>: jg    0x7ffff7c47b79 ; <+617>
0x7ffff7c47a24 <+276>: cmpb  $0x0, -0x4c(%rbp)
0x7ffff7c47a28 <+280>: jne   0x7ffff7c47b6f ; <+607>
```

归档同样记录了 `<+256>` 的实际命中。结合源码，`<+258>` 把 `__exit_funcs_done` 设为真，标记退出回调处理已经完成。登记路径会检查这一状态，到这里便不再接受新的相关退出登记。

标志更新发生在锁保护下，随后释放链表锁。如果存在等待者，还需要进入唤醒分支。本次对 `<+617>` 设置的断点没有命中，程序最终正常退出。

### A.11.2 为什么还需要标准 I/O 收尾

```asm
0x7ffff7c47b6f <+607>: callq 0x7ffff7c968c0 ; 源码对应 _IO_cleanup
0x7ffff7c47b74 <+612>: jmp   0x7ffff7c47a2e ; <+286>
```

`<+276>` 检查的是入口时保存的 `run_list_atexit`。本次值为 `1`，所以进入 `<+607>`，调用标准 I/O 收尾函数。这个调用位置在对照实验中实际命中；内部函数在 LLDB 中仍显示为未命名符号，结合 glibc 源码对应到 `_IO_cleanup`。

使用 `printf`、`fprintf` 等接口时，输出可以先进入运行库维护的用户态缓冲区，再由运行库安排写出。函数返回，并不意味着所有数据都已经交给内核。比如，向普通文件写入少量内容时，内容可能暂时留在 `FILE` 流关联的缓冲区中。

进程结束之后，这片用户态内存也会失去。内核可以回收进程资源，却不会替运行库解释缓冲区中哪些字节还应当作为输出提交。因此，在最终终止进程之前，标准 I/O 层需要尝试刷新尚未提交的缓冲输出，并完成相应的缓冲管理收尾。

`_IO_cleanup` 就承担这一层工作。结合源码，其核心包括刷新输出流以及随后对流缓冲状态的整理。这里确认它的作用即可，不再展开不同流类型、缓冲模式及内部调用的实现细节。

本程序此前已经在终端看到 `30`。这份观测不能用来断言最终收尾时一定还有哪些字节待写出；这里说明的是正常退出路径为标准 I/O 提供的整体收尾机会。

需要分清两个层次：标准 I/O 收尾面对运行库管理的流和用户态缓冲，内核最终退出面对进程持有的内核资源。刷新缓冲也不等于保证普通文件的数据已经持久写入物理存储介质，那还涉及后续的内核与存储设备行为。

退出回调也可能继续产生输出，所以这一轮标准 I/O 收尾安排在退出回调处理之后，再进入最终终止。

### A.11.3 把退出状态交给 _exit

```asm
0x7ffff7c47a2e <+286>: movl  %r14d, %edi
0x7ffff7c47a31 <+289>: callq 0x7ffff7cee300 ; _exit
```

标准 I/O 收尾返回后，执行流跳回 `<+286>`。这里再次取出一直保存在 `%r14d` 中的退出状态，把它放进第一个整数参数寄存器 `%edi`，调用 `_exit`。

本次状态为 `0`。它来自 `main` 的返回结果，经过运行库的收尾过程一直保存到这里，最终作为进程退出状态交给终止路径。

`exit` 与 `_exit` 在本次路径中的职责也因此清楚了：`exit` 组织用户态的退出处理，包括当前线程适用的 TLS 析构、退出回调和标准 I/O 收尾；这些阶段完成后，再调用 `_exit` 请求最终终止。直接调用 `_exit`，则不会再补做前面这套普通退出回调和标准 I/O 刷新流程。

在本次 Linux/glibc 环境中，`_exit` 的实现通过 `exit_group` 系统调用请求终止整个线程组，也就是这里讨论的整个进程。进程中若还有其他线程，它们也会被终止。

这一点与前面讨论的线程退出相呼应：主线程执行了本次退出路径，但最终请求的作用范围是整个进程。至于其他线程各自可能安排的用户态清理，不能因为最终发生了进程终止，就认为它们都曾完整执行。

这里关于 `exit_group` 的说明来自对应平台的实现源码。本次实验没有继续保存系统调用入口的寄存器读数，也没有逐项跟踪内核内部的退出处理，所以不把这一部分写成已经单步观察到的机器指令过程。

### A.11.4 用户态收尾结束之后

进入内核终止路径后，内核负责结束进程中的执行线程，释放进程持有的文件描述符引用、撤销相应地址空间，并推进退出状态的保存及父进程通知等工作。资源若还有其他持有者，会依照各自的引用关系继续存在；进程结束并不意味着所有关联对象都立即从系统中消失。

这些工作属于操作系统的进程生命周期管理。本次追踪到用户态与内核的交接处就结束，不继续进入内核逐项展开。

无 Sanitizer 对照实验最后记录到的结果是：

```text
Process ... exited with status = 0
```

从正文中的函数调用走到这里，各层结束的含义也逐渐分开了。`Add` 返回，是把结果交回 `main`；`main` 的 `retq` 返回到调用它的运行库代码；运行库随后组织对象、模块和标准 I/O 的收尾，最后通过 `_exit` 进入内核终止路径。

所以，`main` 撤销栈帧只是自身调用的结束。它之后仍然有运行库代码继续执行，直到最终请求终止进程，这条执行路径才真正走到尽头。

## 补充实验：Sanitizer 版本为何未返回到断点

本补充集中记录额外实验中的调用链及异常现象，供核对第 A.9 节所述的嵌套回调关系。

### 补.1 补充调用栈确认的嵌套关系

根据补充实验提供的调用栈信息，按实际调用方向可以整理为：

```text
__run_exit_handlers
    调用动态链接器的 _dl_fini
_dl_fini
    调用 _dl_call_fini
_dl_call_fini
    执行主程序的终结辅助函数
__do_global_dtors_aux
    调用 __cxa_finalize
__cxa_finalize
    调用已登记的 __lsan::DoLeakCheck
```

这是对补充记录的结构化整理，下面保留其中可用于定位的栈帧信息；当前提供的是实验结果摘录，并非完整的 LLDB 原始输出。

| 栈帧 | 记录中的位置 | 可以确认的关系 |
|---|---|---|
| `#0` | `__lsan::DoLeakCheck` | 已进入 LSan 泄漏检查函数 |
| `#1` | `__cxa_finalize +194` | 检查函数由模块关联的回调处理路径调用 |
| `#2` | `__do_global_dtors_aux +39` | 来源为主程序终结辅助代码 |
| `#3` | 动态链接器内部函数 `<+98>` | 按调用链与偏移对应模块终结路径，源码名称未由 LLDB 解析确认 |
| `#4` | 动态链接器内、按源码对应为 `_dl_fini` 的入口 `<+504>` | 当前仍位于该回调调用链中；源码名称属于行为与偏移对应 |
| `#5` | `__run_exit_handlers <+358>` | 外层正在等待该回调返回 |

`#5` 的 `<+358>` 是 `<+356>` 调用时压入的返回地址。调用栈显示它，并不表示执行流已经返回并执行该指令。`#4` 中的 `<+504>` 也应按相同原则理解为下层调用后的接续位置。

### 补.2 对此前异常现象的解释

原始 Sanitizer 版本在退出时报告 LeakSanitizer 致命错误，并提示其无法在 `ptrace` 调试环境下正常完成检测。补充调用栈进一步确认，这次泄漏检查是在动态链接器执行主程序终结方法的过程中，经由 `__cxa_finalize` 触发的。

据此，可以把未命中回调后断点的经过解释为：模块终结路径进入 LSan 检查，检查在调试环境中失败并终止进程，执行流未能正常返回外层的 `<+358>`。这一解释结合了此前的错误输出、补充调用栈以及 LSan 的实现行为；调用栈本身没有展示具体失败的底层跟踪操作。

先前“模块已进入终结状态，导致 Sanitizer 代码无法正常执行”的推测，应由上述解释替换。补充实测已经进入 `__lsan::DoLeakCheck`，失败发生在后续检测过程。

去除 Sanitizer 后，对照实验实际命中了 `<+358>`，因此可以继续追踪原生运行库的后续退出路径。

### 补.3 对顺序与状态协调的补充认识

旧版首先选择 `fns[4]` 中的动态链接器回调，但该回调内部又通过模块终结进入 `__cxa_finalize`，触发其他已登记记录。实际调用顺序因此包含嵌套关系，不能只把槽位顺序写成一条扁平调用序列。

这一现象也说明，外层遍历与模块终结之间需要协调记录状态。已经由内层处理的记录，后面不应再次作为待执行回调调用；具体状态检查可结合 `__cxa_finalize` 的实现进一步对照。
