## 八、当前线程的 TLS 析构与进程退出回调的组织

上一段中，`exit` 已经准备好退出状态、退出回调链表入口，以及控制收尾阶段的两个开关。进入内部处理函数后，执行流首先转向当前线程的 TLS 析构检查。完成这一阶段，才开始访问进程退出回调链表。

### 1. 保存入口参数，先检查当前线程的析构记录

函数入口依然先建立栈帧，并保存准备使用的被调用者保存寄存器。随后几条指令把需要长期保留的入口参数安排到寄存器或当前栈帧中：

| 入口参数 | 保存或使用位置 | 后续用途 |
|---|---|---|
| `%edi` 中的退出状态 | `%r14d` | 向需要退出状态的回调及最终终止操作传参 |
| `%rsi` 中的 `&__exit_funcs` | `-0x38(%rbp)` | 读取、更新退出回调链表入口 |
| `%edx` 中的标准 I/O 收尾开关 | `-0x4c(%rbp)` | 控制末尾的标准 I/O 收尾 |
| `%cl` 中的 TLS 析构开关 | `<+31>` 立即检查 | 决定是否先执行 TLS 析构处理 |

后面还要调用其他函数，而这些入口参数需要继续使用，所以不能一直依赖入口时的参数寄存器。退出状态被复制到 `%r14d`，另外两个参数保存在当前栈帧内。前面讨论过的寄存器保存约定，在这里承担了具体任务。

本次第四个参数为真，`testb %cl, %cl` 检查后，执行流跳到 `<+597>`，调用 `__call_tls_dtors`。调用结束，再从 `<+602>` 跳回 `<+39>`，继续后面的处理。

这里处理的是当前线程登记的 TLS 对象析构记录。线程局部存储中的对象可能需要在生命周期结束时执行清理，运行库为此保存对应的函数和对象信息。本文沿用 POSIX 线程的执行背景理解即可；各种语言运行时如何把自身对象接入底层机制，属于更上层的安排。这里的具体登记机制也与 `pthread_key_create` 使用的线程特定数据析构机制有所区别，后者另有自己的管理路径。

### 2. 析构记录中保存了什么

下面是补充实验中给出的完整反汇编，来自去除 Sanitizer 后的程序运行。此处绝对地址与前面归档中的对应运行库地址一致，偏移量属于 `__call_tls_dtors`：

```asm
0x7ffff7c476f0 <+0>:  endbr64
0x7ffff7c476f4 <+4>:  pushq  %rbp
0x7ffff7c476f5 <+5>:  movq   %rsp, %rbp
0x7ffff7c476f8 <+8>:  pushq  %r12
0x7ffff7c476fa <+10>: movq   0x1bc67f(%rip), %r12
0x7ffff7c47701 <+17>: pushq  %rbx
0x7ffff7c47702 <+18>: movq   %fs:(%r12), %rbx
0x7ffff7c47707 <+23>: testq  %rbx, %rbx
0x7ffff7c4770a <+26>: je     0x7ffff7c4774e ; <+94>
0x7ffff7c4770c <+28>: nopl   (%rax)
0x7ffff7c47710 <+32>: movq   0x18(%rbx), %rdx

0x7ffff7c47717 <+39>: rorq   $0x11, %rax

0x7ffff7c47729 <+57>: movq   0x8(%rbx), %rdi

0x7ffff7c4772f <+63>: movq   0x10(%rbx), %rax
0x7ffff7c47733 <+67>: lock

0x7ffff7c4773c <+76>: movq   %rbx, %rdi
0x7ffff7c4773f <+79>: callq  0x7ffff7c283e0 ; 源码对应 free
0x7ffff7c47744 <+84>: movq   %fs:(%r12), %rbx
0x7ffff7c47749 <+89>: testq  %rbx, %rbx
0x7ffff7c4774c <+92>: jne    0x7ffff7c47710 ; <+32>

0x7ffff7c4774f <+95>: popq   %r12
0x7ffff7c47751 <+97>: popq   %rbp
0x7ffff7c47752 <+98>: retq
```

`<+10>` 读取一个用于定位线程局部变量的偏移，随后 `<+18>` 通过 FS 基址加上这一偏移，取出当前线程的析构链表头。此前归档在 `<+23>` 停下时记录了：

```text
r12 = 0xffffffffffffff60   ; 即 -0xa0
rbx = 0x0000000000000000
```

这份实测中，当前线程的链表头为空，所以跳到 `<+94>`，恢复寄存器并返回。下面的非空循环没有在这份记录中实际执行，但结合完整汇编与 glibc 源码，可以说明它准备处理的数据及处理方式。

每个节点对应一条析构记录。本次 x86-64 布局可以简化表示为：

```c
struct TlsDestructorRecord {
    /* +0x00 */ uintptr_t encoded_func;           // 混淆后的析构函数地址
    /* +0x08 */ void *object;                     // 交给析构函数的对象
    /* +0x10 */ struct link_map *module;          // 所属模块的运行时记录
    /* +0x18 */ struct TlsDestructorRecord *next; // 下一条析构记录
};                                              // 共 0x20 字节
```

这里使用 `encoded_func` 突出内存中保存的是混淆后的地址位模式，方便与反混淆指令对照；glibc 源码中的对应成员采用函数指针类型。其余成员直接对应节点内的对象指针、模块记录和后继节点。

`<+32>` 取后继节点，`<+36>` 取函数地址。随后先右循环移位 17 位，再与 `%fs:0x30` 中的 pointer guard 异或，还原函数指针。这正好与前面见过的指针混淆过程互相对应。

`<+57>` 把对象地址放进 `%rdi`，`<+61>` 再通过 `%rax` 间接调用。概括起来，就是取出一条记录，执行类似 `func(object)` 的操作。

### 3. 先摘下当前记录，回调后重新读取链表头

```asm
0x7ffff7c47710 <+32>: movq 0x18(%rbx), %rdx
...
0x7ffff7c47724 <+52>: movq %rdx, %fs:(%r12)
0x7ffff7c47729 <+57>: movq 0x8(%rbx), %rdi
0x7ffff7c4772d <+61>: callq *%rax
...
0x7ffff7c47744 <+84>: movq %fs:(%r12), %rbx
0x7ffff7c47749 <+89>: testq %rbx, %rbx
0x7ffff7c4774c <+92>: jne  0x7ffff7c47710 ; <+32>
```

这个循环有一个值得注意的细节：调用回调之前，`<+52>` 已经把当前线程的链表头更新为当前记录的后继，当前记录便从待处理链表中摘下。回调结束后，循环又从线程局部存储中重新读取实际的链表头。

这一写法可以容纳回调期间发生的新登记。假设链表原来依次为 A、B，准备调用 A 时，链表头已经指向 B。若 A 的回调又登记了 C，由于登记采用头插，待处理链表就变为 C、B。回调返回后重新读取链表头，下一次取得的便是 C，之后再处理 B。

如果始终沿着调用之前暂存的后继 B 前进，就无法跟上这次插入。现在，循环以线程局部变量中实际保存的链表头为准，新登记的记录也能进入接下来的处理。

### 4. 为什么先处理这些 TLS 析构

```asm
0x7ffff7c4772f <+63>: movq 0x10(%rbx), %rax
0x7ffff7c47733 <+67>: lock
0x7ffff7c47734 <+68>: subq $0x1, 0x498(%rax)
0x7ffff7c4773c <+76>: movq %rbx, %rdi
0x7ffff7c4773f <+79>: callq 0x7ffff7c283e0 ; 源码对应 free
```

清理方法本身也有依赖。TLS 对象的析构函数可能位于某个 ELF 模块中，执行时还可能使用其他对象、函数或运行库服务。要完成这次析构，这些依赖就需要在调用期间仍然可用。如果已经执行相关对象的终结，或者卸载承载析构代码的模块，再回来进行 TLS 析构，就可能失去正常执行的条件。

因此，当前线程的 TLS 析构被安排在后续进程退出回调与模块终结之前。这一阶段顺序为它保留了较完整的运行环境。具体对象之间更细的依赖，仍然需要各自的生命周期设计来配合。

节点中的 `module` 成员也参与了依赖管理。`<+63>` 取得所属模块记录，`<+68>` 对该记录内的一个计数原子减一。结合源码，这个字段对应 `l_tls_dtor_count`，用于协调尚待执行的 TLS 析构与模块卸载。

计数是在析构回调返回之后递减的。这样，析构执行期间仍保留相应的待处理计数；运行库的模块卸载路径会参考这一计数，协调模块的生命周期。这里的原子操作还涉及与并发模块卸载之间的内存顺序配合，具体实现不再展开。

最后，`<+76>` 将当前登记节点的地址交给 `%rdi`，随后释放节点。被释放的是运行库保存的这条登记记录；对象本身需要怎样清理，由前面调用的析构方法负责。

### 5. 转向进程退出回调链表

TLS 析构处理返回后，执行流回到 `__run_exit_handlers` 的 `<+39>`。以下偏移量重新属于该函数：

```asm
0x7ffff7c47937 <+39>: leaq     0x1be66a(%rip), %rbx
0x7ffff7c4793e <+46>: xorl     %eax, %eax
0x7ffff7c47940 <+48>: movl     $0x1, %edx
0x7ffff7c47945 <+53>: lock
0x7ffff7c47946 <+54>: cmpxchgl %edx, (%rbx)
0x7ffff7c47949 <+57>: jne      0x7ffff7c47b86 ; <+630>
0x7ffff7c4794f <+63>: movq     -0x38(%rbp), %rax
0x7ffff7c47953 <+67>: movq     (%rax), %r15
0x7ffff7c47956 <+70>: testq    %r15, %r15
0x7ffff7c47959 <+73>: je       0x7ffff7c47a10 ; <+256>
```

这里开始取得进程退出回调链表所用的锁。链表中的登记信息由进程中的线程共享，访问和修改需要相应的协调。后面调用回调时还会释放、重新取得这把锁，下一段再结合完整过程讨论。

取得锁之后，`<+63>` 从当前栈帧中取回 `&__exit_funcs`，`<+67>` 读取其中保存的头节点地址，再检查节点是否为空。这正好接上上一段中“头指针变量地址”与“头节点地址”的区分。

接下来先看看这些回调是怎样表示和组织的。了解数据含义之后，再读具体选择、调用回调的汇编，会更容易把各条指令联系起来。

### 6. 怎样把不同形式的回调放进同一个数组

退出时需要调用的方法并不只有一种形式。有些函数没有参数，有些需要退出状态和附带数据，还有些需要对象地址以及模块归属信息。glibc 通过类型标签和联合体，把这些不同形式组织成大小一致的记录。

下面保留实际结构的主要关系，并标出本次平台上的偏移：

```c
struct ExitFunction {
    /* +0x00 */ long flavor;                 // 记录类别及槽位状态

    /* +0x08 */ union {
        void (*at)(void);                   // 无参数回调

        struct {
            void (*fn)(int status, void *arg);
            void *arg;                      // 登记时附带的数据
        } on;

        struct {
            void (*fn)(void *arg, int status);
            void *arg;                      // 对象地址或其他附带数据
            void *dso_handle;               // 所属模块的关联标识
        } cxa;
    } func;
};                                          // 共 0x20 字节
```

联合体中的成员共用存储空间，其容量由最大的一种形式决定。加上前面的 `flavor`，每个元素在这里统一占用 `0x20` 字节，便可以放进同一个数组中。

`flavor` 说明当前槽位应如何解释。与本次讨论有关的取值为：

| 值 | 名称 | 含义 |
|---|---|---|
| `0` | `ef_free` | 空闲槽位 |
| `1` | `ef_us` | 已占用、尚待填写完成的内部状态 |
| `2` | `ef_on` | 带退出状态与附带数据的回调 |
| `3` | `ef_at` | 无参数回调 |
| `4` | `ef_cxa` | 带附带数据及模块关联信息的回调 |

这些值表示互斥的类别或状态。处理一条记录时，运行库先查看标签，再选择联合体中的对应成员及调用形式。

| 记录类别 | 登记时保存的主要信息 | 执行时的调用形式 |
|---|---|---|
| `ef_at` | 函数地址 | `fn()` |
| `ef_on` | 函数地址、`arg` | `fn(status, arg)` |
| `ef_cxa` | 函数地址、`arg`、模块标识 | glibc 内部采用 `fn(arg, status)` |

这里列出的是内部记录形式。公开登记接口与内部类别之间可以存在转换，实际采用哪一种形式，要看登记实现。

其中，`status` 来自当前这次退出调用。本次 `exit(0)` 传入的状态已经保存在 `%r14d`，调用需要退出状态的回调时再取出。它由这次退出处理统一提供，不必保存在每一条登记记录中。`arg` 则属于某一次登记，各条记录可以保存不同的值。

以 `__cxa_atexit` 为例，登记可以概括为：

```c
__cxa_atexit(cleanup_object, object_address, module_handle);
```

运行库取得一个可用槽位，保存函数地址、对象地址和模块标识，并把类别设置为 `ef_cxa`。函数地址在保存时会经过指针混淆，调用前再还原。

公开的 `__cxa_atexit` 接口接收 `void (*)(void *)` 形式的函数；上面结构中的 `cxa.fn` 则展示 glibc 内部保存和调用时使用的形式。这属于当前实现与调用约定的安排，普通 C 程序不宜照此随意改换不兼容的函数指针类型。

退出时，运行库取出该记录，按相应类别准备参数，再间接调用。`dso_handle` 用于关联记录与所属模块，例如在共享模块卸载时识别相关登记；它不作为第三个参数传给这个回调。

如果一个清理方法需要更多数据，可以让 `arg` 指向一个结构体：

```c
struct CleanupContext {
    void *buffer;       // 待释放的缓冲区
    int descriptor;     // 待关闭的描述符
};
```

回调取得指针后，再按照双方约定读取成员。运行库只需要保存一个附带数据指针，具体数据怎样解释，由登记者和回调决定；这片数据也需要保持有效，直到相应回调使用完毕。

这样，统一的记录格式便能承载不同的清理任务。数组管理面对的是相同大小的元素，实际调用则依据标签保留各自所需的参数安排。

### 7. 用链表连接固定容量的数组块

单条记录统一之后，外层采用下面的组织方式：

```c
struct ExitFunctionList {
    /* +0x000 */ struct ExitFunctionList *next; // 后继数组块
    /* +0x008 */ size_t idx;                   // 待处理槽位的上界
    /* +0x010 */ struct ExitFunction fns[32];   // 每条记录占 0x20 字节
};                                            // 共 0x410 字节
```

每个节点容纳 32 条记录，节点之间再通过链表连接。这个固定容量数组属于节点内部；第一块节点由运行库静态分配，后续容量不足时可以动态申请新的节点。

这种组织方式可以分批扩充：通常连续登记多条记录，只需要使用当前块中的下一个槽位；需要新容量时再申请一整块，不必每条记录单独分配一个链表节点，也不必为了扩大容量搬迁整个已有数组。实现还会考虑可复用的数组块与尾部空闲槽位。需要申请新块时，新块被接入链表头，原来的节点继续保留。

记录的位置也保存了登记顺序。通常在块内从前向后使用槽位，执行退出回调时则从后向前处理；较新的块位于链表前面，也先被访问。块间次序与块内次序配合，支持按登记顺序的逆序进行处理。

这部分通常直接依照现有位置反向遍历。后面进入动态链接器的模块终结时，还会遇到依据模块依赖关系组织顺序的另一层处理。登记次序与依赖关系都影响清理，但需要结合具体机制判断它们怎样发挥作用。

`idx` 表示当前块中待处理槽位的上界。槽位可能已经被标为空闲，因此不能始终把它当作精确的有效回调数量。读取数组元素时，还需要查看各条记录的 `flavor`。

归档中，原始 Sanitizer 版本在 `<+70>` 处读到头节点地址 `0x7ffff7e05fc0`，该节点的 `idx` 为 `5`；后来的无 Sanitizer 对照版本在对应位置读到同一节点地址，`idx` 为 `1`。这两份记录来自不同实验：业务源码之外，参与程序运行的组件也会登记自己的退出工作，构建配置会影响实际看到的回调记录。

至此，当前线程的 TLS 析构检查已经结束，执行流取得了进程退出回调链表，记录及数组块的含义也有了对应。接下来再看运行库怎样选中一条记录、还原函数地址、准备参数，以及在回调返回后继续处理登记变化。
