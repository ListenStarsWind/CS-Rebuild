## 二、逐条讨论记录（按对话推进顺序）

### 01. 函数序言：保存帧指针并分配栈空间

```asm
0x7ffff7c2a150 <+0>: pushq %rbp
0x7ffff7c2a151 <+1>: movq %rsp, %rbp
0x7ffff7c2a154 <+4>: subq $0x90, %rsp
```

用户原始判断（其后又重新精确表述）：

> 第一条很简单, 是一套常见的操作, 其目的是为了让函数返回更上一层的调用者, 以及为当前函数建立栈帧 ... 第一条是将当前的 rbp 压栈, 便于之后回到上一级函数的栈状态, 第二条指令是为了建立栈基准, 之对于这个栈帧, 而不考虑其他调用链的情况下, rbp 就不会动了, 第三条是预留栈空间, 以供之后的使用

讨论核对：保存旧 `%rbp` 主要为恢复调用者的帧指针和维护栈帧链；`ret` 所依赖的返回地址由先前的 `call` 压栈。`subq $0x90, %rsp` 预留 144 字节。当前函数正常路径调用不返回的 `exit`，不必实际通过自身的普通尾声返回调用者。

### 02. 保存第一个入口形参：`main` 的函数指针

```asm
0x7ffff7c2a15b <+11>: movq %rdi, -0x78(%rbp)
```

用户原话：

> 接下来, 将由上级传递的复制实参的寄存器内容保存到当前栈空间上, 作为形参, 结合后续上下文可知, 该形参实际上就是 main 的入口反汇编机器码地址

讨论核对：`%rdi` 是当前函数通过 ABI 接收的第一个参数；其值是 `main` 的函数指针，不是 `main` 指令字节本身。将其暂存到 `rbp-0x78`，方便 `%rdi` 改作其他用途。后来 `movq -0x78(%rbp), %rax` 与 `callq *%rax` 构成使用证据。

### 03. `_setjmp` 的第一个实参

```asm
0x7ffff7c2a15f <+15>: leaq -0x70(%rbp), %rdi
```

用户原话：

> 接下来是准备另一个即将被调用函数_setjmp的实参

讨论核对：`leaq` 仅计算 `rbp-0x70` 这一存储区的地址，将其作为 `_setjmp` 的第一个实参；并不解引用该地址。此区域位于栈帧中，用于 `pthread_unwind_buf` 内的跳转上下文。

### 04. 保存 `argc`、`argv`

```asm
0x7ffff7c2a163 <+19>: movl %esi, -0x7c(%rbp)
0x7ffff7c2a166 <+22>: movq %rdx, -0x88(%rbp)
```

用户原话：

> 接下来是初始化本函数的第 2, 3 形参, 他们实际上就是 argc 和 指向 argv 的指针

讨论核对：准确说是保存传入的第二、第三个形参。`argc` 为 32 位整数，`argv` 为 64 位指针；之后调用 `main` 前分别加载到 `%edi` 和 `%rsi`。

### 05. 栈金丝雀的读取与保存

```asm
0x7ffff7c2a16d <+29>: movq %fs:0x28, %rax
0x7ffff7c2a176 <+38>: movq %rax, -0x8(%rbp)
```

用户原话：

> 接下来是把栈金丝雀从段基址偏移处取出, 通过比对前后数据是否一致, 金丝雀是否死亡, 就可以判断是否存在写形式的栈溢出, 不过, 实际上, 我没找到检测的汇编在哪里, 所以实际上无法确定当前观点是否正确

讨论核对：两条符合 glibc/x86-64 上常见的栈保护值保存模式；在用户所贴的调用者函数完整反汇编中未见常规金丝雀检查尾声。讨论认为这一点与其正常路径不返回的性质有关。**后续若写成正式论证，应进一步核验当前 glibc 机器码的栈保护实现及编译配置，而不能简单断言存在完整保护检查。**

### 06. `xorl %eax, %eax` 的意义

```asm
0x7ffff7c2a17a <+42>: xorl %eax, %eax
```

用户提出的关键问题：

> 对自己异或是一种常见的清零手段, 此处把 rax 清零了, 但问题是, 为什么要特意进行这种清零如果我想保存某些值, 保存8字节, rax 远内容被覆写, 保存4字节, eax 被写, 剩下 rax 高位也会自动清零

讨论结论：这条清零紧跟在金丝雀保存之后，解释为尽快消除 `%rax` 中的金丝雀临时副本，而不是为 `_setjmp` 设定返回值。写 `%eax` 会把 `%rax` 的高 32 位清零。

用户的概括：

> 所以还是敏感性方面的考虑, 用完马上覆写就不会让这种敏感值继续留存在寄存器中, 简单有效

### 07. 为什么要 `_setjmp`：非局部跳转及其适用范围

```asm
0x7ffff7c2a17c <+44>: callq 0x7ffff7c44fa0 ; _setjmp
```

用户初步推测（保留原始不确定性）：

> _setjmp 函数的具体作用我并不知晓, 但根据进入之后的代码, 我认为他似乎起着存储某些重要上下文或者及其索引的功能, 他会以刚才准备好的 rdi 所指向地址为基准, 在 当前函数栈帧中保存许多信息, 比如, argc, argv , 什么清理函数索引什么的, 到时候具体来看, 此外, 他似乎还和某些关键进程初始状态的触发或者检查有关

讨论中用多层函数解析配置的例子说明 `setjmp` / `longjmp`：在外层 `main` 建立恢复点，内部 `read_number` 发现错误后触发 `longjmp`，绕过 `parse_field`、`parse_config` 的普通返回路径；外层 `setjmp` 的返回值由 0 变为指定的非零值，进入错误处理分支。这不是整个栈内存的复制或回滚，堆对象、文件操作等副作用不会自动撤销。

用户联系自己曾写过的服务和异常处理：

> 有意思, 这让我想起当年写具体服务代码(C/C++)的时候, 会在 main 里面设置多个异常捕获进行错误分流, 然后暂时不管这次错误, 继续运行服务 ... 这也让我联想到了 RAII

**重要纠错**：用户曾暂时推断 `_setjmp` 是进程最后一道异常保险，内核遇 SIGSEGV 可以让它恢复并进入线程退出分支。讨论明确否定：一般 SIGSEGV 的默认处理是终止进程，内核不会自动查找 libc 的 `jmp_buf`；需要显式的非局部跳转机制。此处恢复点主要与 glibc/NPTL 的主线程退出、取消处理有关。

用户后续修正：

> 如果我没猜错, 此处的 rdi 基址空间就是所谓的 jmp_buf 而 `setjmp` 是供应用层有特殊需求的非一般的函数返回所设计的机制, 而段错误那个什么东西, 是另一套机制, 比如信号, 由内核态控制的 ... 但如果利用不当, 就可能产生要命的资源泄露问题

讨论纠错：`%rdi` 指向的区域对应 `pthread_unwind_buf` 内的 `cancel_jmp_buf`，不等于整个对象；`pthread_exit` 并非直接“内嵌同一个 setjmp 调用”这么简单。glibc 的线程退出可使用强制栈展开和清理处理，需区别普通 `longjmp` 与 C++ 异常/析构行为。普通 `longjmp` 不会自动逐帧运行 C++ 对象析构逻辑。

用户单步输出：

```text

    frame #0: 0x00007ffff7c44fa0 libc.so.6`_setjmp

    0x7ffff7c44fa4 <+4>: xorl   %esi, %esi
```

用户对 `endbr64` 的长段分析摘要（原观点）：直接 `call`/`jmp` 的目标由指令确定，间接调用/跳转可能使用可写内存中被篡改的目标；Intel IBT 通过 `endbr64` 标记受检查的合法间接分支落点；启用 IBT 时，未标记位置不能成为被跟踪间接分支的落点；未启用时该指令不会产生相关限制；函数内部例如跳转表落点也可能设标记。

讨论补充：`endbr64` 标记的是允许的间接分支落点，并不认证“业务上正确的目标”；错误地跳到另一个带 `endbr64` 的位置仍可能通过 IBT 检查。本次调用 `_setjmp` 是直接 `callq`，故它本身不依赖入口处的 `endbr64`。`_setjmp` 用 `jmp` 而不是 `call` 进入 `__sigsetjmp`，不会再压入返回地址，最终内部尾声的 `retq` 能直接返回原始调用者。

### 09. `savemask = 0` 与信号阻塞集

```asm
0x7ffff7c44fa4 <+4>: xorl %esi, %esi
0x7ffff7c44fa6 <+6>: jmp 0x7ffff7c44ed0 ; __sigsetjmp
```

用户最初观察：

> 我确实不是非常肯定知道此处将第二个通用寄存器清零是为了什么, 不过结合后续上下文, 我认为, 这个参数可能实际上就是零, 或者是我记错了

讨论结论：`_setjmp` 将 `__sigsetjmp(env, 0)` 的第二参数 `savemask` 设为零，表示不额外保存当前线程信号阻塞集。

用户结合曾学的 Linux 信号机制指出：

> 你所谓的信号掩码是所谓的信号阻塞集吗? 即判断是否要屏蔽对应信号的位图结构? 不过这里这个参数为0是完全可以理解的, 因为目前main 还没有运行, 掩码保持默认状态, 不需要把他当作真正有实际意义的上下文, 并且如果再次进入这里的 setjmp, 就线程退出了, 也不用操心什么信号

讨论纠错：信号掩码即当前线程的信号阻塞集；`main` 尚未运行不保证信号掩码为默认值，因为信号掩码可以跨 `execve` 继承。用户保留第二个解释：这个恢复点用于线程退出，通常没有恢复先前信号掩码的需求。

用户特别强调其曾系统学习过 Linux 信号、阻塞集与相关 API，不应按初学者讲解。后续讨论以已有知识为前提。

### 10. `__sigsetjmp`：真正保存上下文的实现

用户概括：

> 这没什么好说的, 形象来说, 就是 setjmp 中实际负责处理"快照保存"的逻辑

讨论限定：“快照”仅指恢复执行所需的寄存器及控制流状态，不是完整进程或整个栈的快照。

#### 10.1 保存 `%rbx`

```asm
0x7ffff7c44ed0 <+0>: endbr64
0x7ffff7c44ed4 <+4>: movq %rbx, (%rdi)
```

用户观察：

> rbx 存储的是指向 argv 数值的指针, 尽管我觉得实际上没有必要再把他暂存一下, 因为 call main 是属于跳过内容的, 其实没必要特别存一下他的参数, 但是优化级别是0, 所以他可能顺手存了一下

用户之后补充：确实用 LLDB 读过 `%rbx`，在**这次实验的当前状态**下它指向与 `argv` 有关的内容。讨论纠错：`__sigsetjmp` 并不关心具体业务含义；`%rbx` 属于被调用者保存寄存器，所以无条件保存其当前状态，和用户程序的 `-O0` 无直接因果关系。保存的是指针值，不复制 `argv` 全部数据。

用户接受的概括：

> 在调用setjmp 时, rbx 中确实存着某个值, 为此我们需要把他当作上下文的一种, 打包进那个空间

#### 10.2 保存并混淆 `%rbp`

```asm
0x7ffff7c44ed7 <+7>:  movq %rbp, %rax
0x7ffff7c44eda <+10>: xorq %fs:0x30, %rax
0x7ffff7c44ee3 <+19>: rolq $0x11, %rax
0x7ffff7c44ee7 <+23>: movq %rax, 0x8(%rdi)
```

用户原始判断：

> 不过接下来存的值确实具有特殊含义, 那就是 rbp, 存储着栈基指针的值, 并且由于十分重要, 还通过异或, 移位旋转方式进行了指针混淆, 以达到.... 的目的

讨论结论：glibc 将 `%rbp` 的值放入 `%rax`，和 `%fs:0x30` 的 pointer guard 异或，循环左旋 17 位，再保存到 `jmp_buf+0x8`；未来按相反方向旋转和异或恢复。目的是提高恶意篡改保存的地址/控制流上下文的难度；这不是加密，也不是每次使用前的完整性认证。`%fs:0x30` 与栈金丝雀的 `%fs:0x28` 不同。

#### 10.3 保存 `%r12`～`%r15`

```asm
0x7ffff7c44eeb <+27>: movq %r12, 0x10(%rdi)
0x7ffff7c44eef <+31>: movq %r13, 0x18(%rdi)
0x7ffff7c44ef3 <+35>: movq %r14, 0x20(%rdi)
0x7ffff7c44ef7 <+39>: movq %r15, 0x28(%rdi)
```

用户根据跟踪推测：

> 这四个寄存器中的值可能具有特殊含义, 比如根据他们的值和粗略追踪, 推测 r12 是 argc 的值, r13 是是否保存信号掩码的值, 也就是savemask=0 , r14是什么指向 .fini_array的指针, r15是指向 _rtld_global的

讨论结论：这些都是按 ABI 需要保存的寄存器，其当时的业务含义不决定 `__sigsetjmp` 的保存行为。特别是 `savemask` 实际由 `%esi` 传入，不能仅因 `%r13=0` 推定 `%r13` 就代表 `savemask`。用户对 `%r12`/`%r14`/`%r15` 的推测保留为实验线索，待反向追踪确认。

#### 10.4 保存未来恢复时的 `%rsp`

```asm
0x7ffff7c44efb <+43>: leaq 0x8(%rsp), %rdx
0x7ffff7c44f00 <+48>: xorq %fs:0x30, %rdx
0x7ffff7c44f09 <+57>: rolq $0x11, %rdx
0x7ffff7c44f0d <+61>: movq %rdx, 0x30(%rdi)
```

用户最初以为这里保存了 `call _setjmp` 压入的下一条指令地址。讨论纠正：`leaq 0x8(%rsp), %rdx` 保存的是**执行完返回后应恢复的栈顶地址**，不是读取 `(%rsp)`；加 8 是为了跳过 `call` 压入的 8 字节返回地址。相应的 `jmp_buf` 偏移 `0x30` 是恢复的栈指针槽位。

用户随后确认：

> 好吧, 我知道了, 是那条存下一条指令空间的地址.

#### 10.5 保存未来恢复的指令地址（PC）及探针 `nop`

```asm

0x7ffff7c44f15 <+69>: nop
0x7ffff7c44f16 <+70>: xorq %fs:0x30, %rax

0x7ffff7c44f23 <+83>: movq %rax, 0x38(%rdi)
```

用户最初说“对当前栈顶的地址进行了混淆之后存储”，并推测 `nop` 用于对齐。讨论纠正：`movq (%rsp), %rax` **读取栈顶存储的返回地址**，即原来 `call _setjmp` 的下一条指令地址 `0x7ffff7c2a181`；随后混淆并保存为恢复 PC。讨论中将 `nop` 解释为 glibc `LIBC_PROBE(setjmp, ...)` 的可观测探针位置，而非简单的对齐指令；此项可在日后正式核对源码和该发行版二进制的静态探针信息。

#### 10.6 可选的硬件影子栈上下文

```asm
0x7ffff7c44f27 <+87>:  testl $0x2, %fs:0x48
0x7ffff7c44f33 <+99>:  je    0x7ffff7c44f3e ; <+110>
0x7ffff7c44f35 <+101>: rdsspq %rax
0x7ffff7c44f3a <+106>: movq %rax, 0x58(%rdi)
0x7ffff7c44f3e <+110>: jmp 0x7ffff7c44f50 ; ___lldb_unnamed_symbol_44f50
```

用户原始判断：

> 接着似乎是保存上下文的又一种机制, 但是这里没有开启, 应该叫做影子栈,然后继续 jmp到另一个函数, 我记得是有关信号掩码保存的逻辑, 当然实际上因为参数是0, 也会跳过

讨论结论：影子栈（Intel CET Shadow Stack）是与普通栈分离、由硬件保护的返回地址栈。开启时普通 `call`/`ret` 会与之协同，`ret` 需匹配普通栈与影子栈的返回地址。由于 `longjmp` 跳过逐层普通返回，若只恢复 `%rsp` 而不协调影子栈，可能触发控制保护异常；因此 `setjmp` 视运行时条件选择是否保存 SSP，随后在 `longjmp` 端处理恢复。IBT 主要约束间接分支目标，Shadow Stack 主要保护返回地址。本次用户认为该可选分支被跳过；这代表当时没有进入保存 SSP 的路径，不等价于断言 CPU/内核从不支持该特性。

用户专门要求补充影子栈的机制：两份返回地址如何比较、影子栈为何不能用普通写指令修改、SSP 为什么不能与 RSP 共用、`longjmp` 为何必须同步影子栈，以及可通过 `/proc/<pid>/status` 中的 `x86_Thread_features` 检查实际启用情况。

### 14. 读取旧线程恢复点和清理链表信息

```asm
0x7ffff7c2a189 <+57>: movq %fs:0x300, %rax
0x7ffff7c2a192 <+66>: movq %rax, -0x28(%rbp)
0x7ffff7c2a196 <+70>: movq %fs:0x2f8, %rax
0x7ffff7c2a19f <+79>: movq %rax, -0x20(%rbp)
0x7ffff7c2a1a3 <+83>: leaq -0x70(%rbp), %rax
0x7ffff7c2a1a7 <+87>: movq %rax, %fs:0x300
```

用户问两个成员用途。讨论中解释为：`%fs:0x300` 保存当前线程登记的恢复节点指针（`cleanup_jmp_buf`），`%fs:0x2f8` 保存旧式清理处理器链表的头指针（`cleanup`）；新节点先保存旧节点指针和原有清理链表位置，再将新节点登记到线程局部数据。具体字段名称/偏移仅针对当前观测的 glibc 实现。

用户的关键原始理解：

> 好吧, 目前我的理解是, %fs:0x300 所处的空间, 存储着一份指针, 这个指针所指向的节点中的一些信息描述了当前层次下(因为状态恢复, 以及恢复后的清理可能是一层一层的)状态恢复所依赖的关键参数, 以及相应的清理方法, 如果这一层的恢复被触发了, 那么内核就会顺着指针域找到那个代表更深层恢复关系的节点, 这样才能让 setjmp 之间可以明确对应起来, 这里我们相当于在栈上创建了这样的一个节点, 所以我们首先把 0x300 上旧的地址拿出来, 写到当前栈上节点的指针域上, 维持了链式关系, 至于那个清理方法, 由于没有做什么特别的事, 所以我们依旧使用之前的, 这样的话, 也不用重新写回 0x2f8了, 随后我们可以看到, 他会把-0x70(%rbp)这个基地址给写回 0x300

讨论纠错：是 **glibc 的用户态线程管理与展开机制**，不是内核直接沿 `pthread_unwind_buf` 链表处理；保存到节点的 `cleanup` 是清理处理器链表头指针，不是单个清理方法本体；`prev` 保留更早登记的节点。用户特别指出自己所称的“更深层”和助手所说的“外层”在该语境下指同一方向，避免在措辞上争论。并强调链式登记不等于每一层一定要执行一次 `longjmp`。

当时助手按用户要求曾将这段观点另行整理为文字稿。其主体可以保留为日后附录素材：先保存原有恢复关系与清理状态，再把 `rbp-0x70` 登记为当前线程新的恢复节点，同时使原有恢复节点仍可由 `prev` 找到；不因未修改 `cleanup` 链表而写回 `%fs:0x2f8`。

### 15. GOT 与 `__environ`：为何先取全局变量地址

```asm

```

用户最初判断：

> 我没记错的话, 这是在读某个全局变量

讨论中按 RIP 相对寻址计算：本条结束处 `0x7ffff7c2a1b7` + `0x1d9de9` = `0x7ffff7e03fa0`，从该地址读取 8 字节至 `%rax`。结合后面的 `movq (%rax), %rdx`，讨论将其识别为通过 GOT 读取全局符号 `__environ` 的地址，再取出该全局变量的值。

用户追问：

> 好好的, 为什么要把全局变量地址放到寄存器里面

后续讨论引入 ELF 共享库的全局偏移表（GOT）及符号抢占（symbol preemption）：动态链接器按符号查找规则决定最终引用哪个符号，GOT 表项存放解析出的地址，机器码通过本模块 GOT 做间接访问，通常不必每次重新解析符号。

用户提出重要修正：

> GOT 也没有解决符号抢占问题, 该歧义的情况仍旧会产生奇异, 他只是专门建立了一个运行时才确定的统一全局资源访问表, 里面存储的是真实采纳的实际全局变量的值或者索引, 而程序运行, 都只是先找到这张表, 然后从表中获得真实值或者指针

讨论结论：GOT 不消除同名符号或歧义；符号选择依赖动态链接器的解析规则。GOT 通常保存**符号地址**，不一定是变量值；它也通常不是整个进程共享的唯一一张表，而是相关 ELF 模块拥有自己的表；“运行时决定”通常具体发生在装载及重定位阶段。PIC 的装载地址独立性与 symbol preemption 是相关但不同的问题。

用户继而问：

讨论解释：glibc 支持按照三参数形式 `main(argc, argv, __environ)` 调用入口；第三个 `envp` 是 glibc/Linux 扩展惯例，并非 ISO C 强制的第三参数。即使当前 `main` 声明为 `int main(void)` 或只有两个参数，glibc 的通用启动代码也不会据应用程序需求专门消除准备环境参数的逻辑。

### 20. `__run_exit_handlers`：粗略收尾，不继续逐指令

用户明确要求：

> 大致说一说, 没有精力具体去看了

讨论按处理阶段归纳：

1. **TLS 析构**：`testb %cl,%cl`，对应分支调用 `__call_tls_dtors`，用于执行适用的线程局部对象析构。
2. **退出回调遍历**：遍历 `__exit_funcs` 维护的链表，对登记函数按类别选择调用形式，包括 `atexit`、`on_exit`、`__cxa_atexit`。`rorq` 配合 `%fs:0x30` 的异或反向还原混淆的回调指针。
3. **并发及重入控制**：`lock cmpxchgl`、`xchgl`、`__lll_lock_wait_private`、`__lll_lock_wake_private` 等涉及锁与并发访问协调，调用回调后可能重新检查链表变化。
4. **最终收尾**：在相应开关启用时进行标准 I/O 等运行库收尾，然后调用 `_exit(status)` 结束进程。

保留的重要区别：**`main` 的 `retq` 不会直接终止进程，而是回到 glibc，由 `exit` 组织回调与收尾，最终才进入 `_exit`。** `exit` 也不能替业务代码保证所有资源都被清理，尤其不能假定普通 C++ 局部对象会因 `exit` 而统一执行析构。

## 四、后续正式整理时的技术复核清单

这部分**不是本次归档时新作的结论**，只记录哪些讨论点值得回到机器码、glibc 版本及源码再确认：

- `___lldb_unnamed_symbol_2a150` 与 `___lldb_unnamed_symbol_44f50` 的真实内部符号名称及源文件、当前 glibc 构建版本。LLDB 未解析出名称时，讨论中的命名须单独验证。
- 入口栈金丝雀读入、栈上保存、清零 `%eax` 的具体编译器实现来源；为什么该 `_Noreturn` 路径未显示通常的尾部金丝雀校验。
- `_setjmp` / `__sigsetjmp` / `__sigjmp_save` 的 ABI、`jmp_buf` 布局、指针混淆与 `LIBC_PROBE` 的源码和这版二进制是否完全一致。
- 用户用 LLDB 观测到 `%rbx` 指向 `argv` 的证据应保留；对 `%r12`、`%r13`、`%r14`、`%r15` 的业务含义仍需回溯初始化位置，而不是根据值直接赋名。
- `%fs:0x300`、`%fs:0x2f8`、`%fs:0x48`、`%fs:0x30`、`%fs:0x28` 的具体结构定义与版本相关性。尤其不要把它们误写成所有 Linux 或所有 glibc 版本的固定 ABI。
- 主线程经 `pthread_exit` 或取消展开到该恢复点的完整过程，包括强制栈展开、清理处理器、C++ RAII 的适用范围以及线程和进程退出的差别。
- 影子栈本次实际是否启用，以及 `rdsspq` 分支没有执行的直接观测证据；CET/IBT 的启用条件、`longjmp` 对 SSP 的恢复行为。
- `0x7ffff7e03fa0` GOT 表项所指向的具体符号，通过 LLDB 的 `memory read`、符号表、重定位表复验；glibc 三参数 `main` 是实现扩展而非 ISO C 标准统一承诺。
- `exit` 入口参数的准确命名，TLS 析构、退出函数处理、标准 I/O 收尾与最终 `_exit` 的顺序和边界；“exit 会释放什么”不能作无限扩大解释。

## 五、这轮研究的实际边界与后续写作定位

此次只追踪 `main` 的直接调用者及其内部必要的支线，**没有尝试全面展开更上层的 `_start`、`__libc_start_main` 的所有启动指令**。`main` 之后的退出管理只保留粗略认识，不逐行解释所有原子锁、回调类型、重入分支和 TLS 细节。

原始讨论的主线是“为什么这条机器指令存在、实际修改了什么状态、这种状态为何需要保存或恢复”，而不是把 glibc 源码翻译成完整教程。将来可以拆成：`main` 调用者汇编附录、`_setjmp` 及线程清理补充材料、`exit` 的退出链路简述。最终文章仍应以实验地址和 LLDB 原始观察为证据，而非以本文讨论中的推测直接充当已证事实。
