## 十一、标准 I/O 收尾与最终的进程终止

```asm
; 以下偏移量属于 __run_exit_handlers
; 当前数组块的待处理槽位已经耗尽
0x7ffff7c47ad8 <+456>: movq  (%r15), %rax
0x7ffff7c47adb <+459>: movq  -0x38(%rbp), %rdx
0x7ffff7c47adf <+463>: movq  %rax, (%rdx)
0x7ffff7c47ae2 <+466>: testq %rax, %rax
0x7ffff7c47ae5 <+469>: je    0x7ffff7c47a10 ; <+256>
0x7ffff7c47aeb <+475>: movq  %r15, %rdi
0x7ffff7c47aee <+478>: callq 0x7ffff7c283e0 ; 源码对应 free
```

动态链接器终结回调返回后，执行流重新回到退出回调处理器。前面已经讨论过重新加锁、检查新登记及继续遍历的过程。现在，沿着无 Sanitizer 对照实验继续向前，看看运行库怎样结束这一轮用户态收尾，再把进程终止交给内核。

这一段与上一段采用相同的阅读方式：保留关键汇编位置，结合源码说明职责和交接关系，不再进入标准 I/O 清理函数内部逐条阅读反汇编。

### 1. 退出记录处理完毕，结束链表管理

归档中的对照实验实际停在了 `<+456>`。此时，当前节点的 `idx` 已经为零，没有更多槽位需要遍历。

`<+456>` 读取节点的 `next`，随后取回头指针变量的地址，在 `<+463>` 把链表入口推进到后继节点。若还有后继，便释放刚刚处理完的动态节点，再继续处理后面的数组块。

链表末端是运行库静态分配的初始节点，它本身也容纳回调记录。处理到它时，后继为空，执行流直接转向 `<+256>`，不会调用 `free` 释放这块静态存储。头指针已经更新为空，而初始节点的存储仍然存在。

这也与前面分块扩充的方式相互对应：容量不足时动态申请新的数组块，处理完后逐块回收；最初静态提供的数组块则有不同的存储期。

```asm
0x7ffff7c47a10 <+256>: xorl  %eax, %eax
0x7ffff7c47a12 <+258>: movb  $0x1, 0x1be9cf(%rip)
0x7ffff7c47a19 <+265>: xchgl %eax, (%rbx)
0x7ffff7c47a1b <+267>: cmpl  $0x1, %eax
0x7ffff7c47a1e <+270>: jg    0x7ffff7c47b79 ; <+617>
0x7ffff7c47a24 <+276>: cmpb  $0x0, -0x4c(%rbp)
0x7ffff7c47a28 <+280>: jne   0x7ffff7c47b6f ; <+607>
```

归档同样记录了 `<+256>` 的实际命中。结合源码，`<+258>` 把 `__exit_funcs_done` 设为真，标记退出回调处理已经完成。登记路径会检查这一状态，到这里便不再接受新的相关退出登记。

标志更新发生在锁保护下，随后释放链表锁。如果存在等待者，还需要进入唤醒分支。本次对 `<+617>` 设置的断点没有命中，程序最终正常退出。

### 2. 为什么还需要标准 I/O 收尾

```asm
0x7ffff7c47b6f <+607>: callq 0x7ffff7c968c0 ; 源码对应 _IO_cleanup
0x7ffff7c47b74 <+612>: jmp   0x7ffff7c47a2e ; <+286>
```

`<+276>` 检查的是入口时保存的 `run_list_atexit`。本次值为 `1`，所以进入 `<+607>`，调用标准 I/O 收尾函数。这个调用位置在对照实验中实际命中；内部函数在 LLDB 中仍显示为未命名符号，结合 glibc 源码对应到 `_IO_cleanup`。

使用 `printf`、`fprintf` 等接口时，输出可以先进入运行库维护的用户态缓冲区，再由运行库安排写出。函数返回，并不意味着所有数据都已经交给内核。比如，向普通文件写入少量内容时，内容可能暂时留在 `FILE` 流关联的缓冲区中。

进程结束之后，这片用户态内存也会失去。内核可以回收进程资源，却不会替运行库解释缓冲区中哪些字节还应当作为输出提交。因此，在最终终止进程之前，标准 I/O 层需要尝试刷新尚未提交的缓冲输出，并完成相应的缓冲管理收尾。

`_IO_cleanup` 就承担这一层工作。结合源码，其核心包括刷新输出流以及随后对流缓冲状态的整理。这里确认它的作用即可，不再展开不同流类型、缓冲模式及内部调用的实现细节。

本程序此前已经在终端看到 `30`。这份观测不能用来断言最终收尾时一定还有哪些字节待写出；这里说明的是正常退出路径为标准 I/O 提供的整体收尾机会。

需要分清两个层次：标准 I/O 收尾面对运行库管理的流和用户态缓冲，内核最终退出面对进程持有的内核资源。刷新缓冲也不等于保证普通文件的数据已经持久写入物理存储介质，那还涉及后续的内核与存储设备行为。

退出回调也可能继续产生输出，所以这一轮标准 I/O 收尾安排在退出回调处理之后，再进入最终终止。

### 3. 把退出状态交给 _exit

```asm
0x7ffff7c47a2e <+286>: movl  %r14d, %edi
0x7ffff7c47a31 <+289>: callq 0x7ffff7cee300 ; _exit
```

标准 I/O 收尾返回后，执行流跳回 `<+286>`。这里再次取出一直保存在 `%r14d` 中的退出状态，把它放进第一个整数参数寄存器 `%edi`，调用 `_exit`。

本次状态为 `0`。它来自 `main` 的返回结果，经过运行库的收尾过程一直保存到这里，最终作为进程退出状态交给终止路径。

`exit` 与 `_exit` 在本次路径中的职责也因此清楚了：`exit` 组织用户态的退出处理，包括当前线程适用的 TLS 析构、退出回调和标准 I/O 收尾；这些阶段完成后，再调用 `_exit` 请求最终终止。直接调用 `_exit`，则不会再补做前面这套普通退出回调和标准 I/O 刷新流程。

在本次 Linux/glibc 环境中，`_exit` 的实现通过 `exit_group` 系统调用请求终止整个线程组，也就是这里讨论的整个进程。进程中若还有其他线程，它们也会被终止。

这一点与前面讨论的线程退出相呼应：主线程执行了本次退出路径，但最终请求的作用范围是整个进程。至于其他线程各自可能安排的用户态清理，不能因为最终发生了进程终止，就认为它们都曾完整执行。

这里关于 `exit_group` 的说明来自对应平台的实现源码。本次实验没有继续保存系统调用入口的寄存器读数，也没有逐项跟踪内核内部的退出处理，所以不把这一部分写成已经单步观察到的机器指令过程。

### 4. 用户态收尾结束之后

进入内核终止路径后，内核负责结束进程中的执行线程，释放进程持有的文件描述符引用、撤销相应地址空间，并推进退出状态的保存及父进程通知等工作。资源若还有其他持有者，会依照各自的引用关系继续存在；进程结束并不意味着所有关联对象都立即从系统中消失。

这些工作属于操作系统的进程生命周期管理。本次追踪到用户态与内核的交接处就结束，不继续进入内核逐项展开。

无 Sanitizer 对照实验最后记录到的结果是：

```text
Process ... exited with status = 0
```

从正文中的函数调用走到这里，各层结束的含义也逐渐分开了。`Add` 返回，是把结果交回 `main`；`main` 的 `retq` 返回到调用它的运行库代码；运行库随后组织对象、模块和标准 I/O 的收尾，最后通过 `_exit` 进入内核终止路径。

所以，`main` 撤销栈帧只是自身调用的结束。它之后仍然有运行库代码继续执行，直到最终请求终止进程，这条执行路径才真正走到尽头。
