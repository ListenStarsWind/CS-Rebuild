## 九、一条退出回调怎样被执行

```asm
; 以下偏移量均属于 __run_exit_handlers
0x7ffff7c47968 <+88>:  movq 0x8(%r15), %rax
0x7ffff7c4796c <+92>:  testq %rax, %rax
0x7ffff7c4796f <+95>:  je   0x7ffff7c47ad8 ; <+456>
0x7ffff7c47975 <+101>: subq $0x1, %rax
0x7ffff7c47979 <+105>: movq 0x1be620(%rip), %r12
0x7ffff7c47980 <+112>: movq %rax, 0x8(%r15)
0x7ffff7c47984 <+116>: shlq $0x5, %rax
0x7ffff7c47988 <+120>: addq %r15, %rax
0x7ffff7c4798b <+123>: movq 0x10(%rax), %rcx
0x7ffff7c4798f <+127>: cmpq $0x3, %rcx
0x7ffff7c47993 <+131>: je   0x7ffff7c47a98 ; <+392>
0x7ffff7c47999 <+137>: cmpq $0x4, %rcx
0x7ffff7c4799d <+141>: je   0x7ffff7c47a40 ; <+304>
0x7ffff7c479a3 <+147>: cmpq $0x2, %rcx
0x7ffff7c479a7 <+151>: jne  0x7ffff7c47968 ; <+88>
```

上一段已经认识了退出回调记录及其外层数组块。现在，运行库持有退出链表锁，`%r15` 指向当前节点，执行流开始从其中选择一条记录。

### 1. 从最后一个待处理槽位开始

节点内偏移 `0x8` 保存 `idx`。`<+88>` 读取这一上界，检查为零时转向节点处理完成的分支；还有待处理槽位时，就先减一，并在 `<+112>` 写回节点。

因此，原始 Sanitizer 版本的 `idx` 为 `5` 时，首先选择 `fns[4]`；去除 Sanitizer 后的对照版本为 `1`，首先选择 `fns[0]`。两次实验分别从各自节点的末尾向前处理。

每条记录占 `0x20` 字节，数组在节点内的起始偏移为 `0x10`，所以目标地址可以表示为：

```c
记录地址 = 节点地址 + 0x10 + 索引 * 0x20;
```

`<+116>` 左移 5 位，完成索引乘以 32。`<+120>` 加上节点基址之后，`%rax` 仍然只包含“节点地址加索引乘以 32”。数组起点的额外 `0x10` 留在后续访存指令中。因此，`<+123>` 的 `0x10(%rax)` 才对应所选记录的 `flavor`。

接下来的比较根据标签选择调用形式：`3` 对应无参数的 `ef_at`，`4` 对应 `ef_cxa`，`2` 对应 `ef_on`。空闲及尚未填写完成的内部状态不进入这几类回调调用。本次实际选中的记录类别为 `4`，执行流跳到 `<+304>`。

`<+105>` 还保存了登记计数器 `__new_exitfn_called` 的当前值。它暂存在 `%r12` 中，等回调返回后，再用来判断期间是否发生了新登记。

### 2. 取出函数和参数，更新记录状态

```asm
0x7ffff7c47a40 <+304>: movq 0x18(%rax), %rcx
0x7ffff7c47a44 <+308>: movq 0x20(%rax), %r8
0x7ffff7c47a48 <+312>: movq $0x0, 0x10(%rax)
0x7ffff7c47a50 <+320>: movq %rcx, %rax
0x7ffff7c47a53 <+323>: movl %r13d, %ecx
0x7ffff7c47a56 <+326>: rorq $0x11, %rax
0x7ffff7c47a5a <+330>: xorq %fs:0x30, %rax
```

结合上一段给出的结构，几次访问可以一一对应：

| 当前寻址表达式 | 对应成员 | 操作 |
|---|---|---|
| `0x18(%rax)` | `fns[i].func.cxa.fn` | 取得混淆后的函数地址 |
| `0x20(%rax)` | `fns[i].func.cxa.arg` | 取得登记时附带的数据 |
| `0x10(%rax)` | `fns[i].flavor` | 写入 `ef_free` |

这里已经先递减了 `idx`，现在又在实际调用之前，把记录标为空闲。两个操作相互配合：前者推进当前遍历的位置，后者让其他可能检查记录的终结路径知道，这条记录已经被接手处理。

这一点与模块终结有关。进程退出处理器会访问这些记录，模块终结时的相关机制也可能访问其中属于特定模块的登记。glibc 源码在此明确说明，将 `ef_cxa` 记录预先标为空闲，是为了避免模块卸载与进程退出之间的竞争导致同一回调被调用两次。

所需的函数地址和附带数据已经取到寄存器中，可以继续使用这些副本完成调用。随后，函数地址被转移到 `%rax`，先右循环移位 17 位，再与 `%fs:0x30` 中的 pointer guard 异或，恢复实际入口地址。前面保存接续点时见过的指针混淆，在退出回调记录中再次出现。

### 3. 释放链表锁，再执行回调

```asm
0x7ffff7c47a63 <+339>: xchgl %ecx, (%rbx)
0x7ffff7c47a65 <+341>: cmpl  $0x1, %ecx
0x7ffff7c47a68 <+344>: jg    0x7ffff7c47b48 ; <+568>
0x7ffff7c47a6e <+350>: movl  %r14d, %esi
0x7ffff7c47a71 <+353>: movq  %r8, %rdi
0x7ffff7c47a74 <+356>: callq *%rax
```

`%rbx` 保存退出链表锁的地址，`%r13d` 此前已被清零，所以 `<+323>` 之后 `%ecx` 也是零。`xchgl` 把零写入锁，同时把原来的锁状态取回 `%ecx`，随后检查是否需要进入唤醒等待者的分支。内存形式的 `xchg` 本身提供原子交换语义。

这里为何要在调用之前解锁？因为回调要执行的工作由登记者决定，其中可能再次登记退出方法，也可能调用具有其他锁依赖的函数。登记操作还需要取得同一把链表锁；如果当前线程一直持有它，再在回调内部尝试获取，就可能等待自己尚未释放的锁。

运行库因此把共享记录的处理与回调的执行分开：先在锁保护下取得调用材料、更新记录，再释放锁，将执行权交给回调。这样，回调可以间接进入登记等需要使用这把锁的路径。

解锁时若发现有等待者，会进入 `<+568>` 所在的唤醒路径；这属于锁竞争时的处理，本段沿着无需唤醒的路径继续看。

随后，两条传参指令把这一记录转成实际调用：

```c
rdi = arg;
esi = status;
```

附带数据来自 `%r8`，退出状态来自入口时保存的 `%r14d`。本次分别为 `NULL` 和 `0`，与 `ef_cxa` 内部使用的 `fn(arg, status)` 形式对应。最后，通过 `%rax` 中的地址间接调用。

### 4. 本次回调为什么进入动态链接器

在 `<+356>` 调用之前，归档记录了反混淆后的目标：

```text
rax = 0x00007ffff7fca380
所属映像：ld-linux-x86-64.so.2
映像内偏移：0x5380
LLDB 显示：___lldb_unnamed_symbol_5380
```

旧版选中的 `fns[4]` 与无 Sanitizer 对照版本选中的 `fns[0]`，均指向这个入口。结合后续内部行为及 glibc 源码，可以将它对应到动态链接器的 `_dl_fini`。这里的函数名来自源码对应，LLDB 当时显示的仍是未命名符号。

理解它的任务之前，需要把前面出现的“ELF 模块”说具体一些。ELF 是本次 Linux 环境中可执行文件和共享库采用的文件格式。本文在动态链接语境下，把动态链接器管理的主程序、共享库等 ELF 对象称为 ELF 模块。它们有各自的代码、数据以及运行时管理信息，例如当前主程序、libc 和其他加载的共享库。

模块可以提供业务功能，也可以提供运行库或辅助功能；功能与模块并不一定一一对应。某些辅助运行时代码可以直接链接进主程序。本次 Sanitizer 的若干回调被 LLDB 识别为属于 `main` 映像，就属于需要结合实际构建结果判断的情况。

这些模块除了正常运行的代码，还可以安排生命周期末尾执行的终结方法。模块内部可能需要处理对象、释放资源或完成其他收尾。动态链接器掌握模块的加载与依赖信息，因此由 `_dl_fini` 组织这部分终结过程。

它会收集仍然加载的相关模块，根据依赖关系安排处理次序，再逐个调用模块的终结入口。假设 A 依赖 B，A 的终结方法仍可能使用 B 提供的服务，就需要在 B 的相关服务结束之前完成 A 的终结。运行期间还可能通过 `dlopen` 加载其他模块，终结时因而需要重新考虑模块之间的关系。

落实到单个模块，动态链接器会依据 `DT_FINI_ARRAY`、`DT_FINI` 等动态信息调用相应的终结函数。具体释放什么资源、改变哪些状态，由各模块的终结方法决定。代码仍然映射在进程地址空间中，也不意味着模块内部对象和服务仍保持正常运行时期的使用条件。

因此，这条通用退出记录内部还包含另一层调度：`__run_exit_handlers` 调用 `_dl_fini`，后者组织模块终结，再由各模块执行自己的收尾。模块终结完成后，动态链接器回调可以返回，运行库继续后续退出工作。

glibc 的启动过程会接收动态链接器提供的 `rtld_fini` 函数指针，并把它登记到退出处理机制中。于是，组织程序启动环境的一方，在正常退出时也获得执行收尾的机会。下一段再结合对应汇编，观察这一层调度怎样展开。

### 5. 登记位置与实际执行顺序

数组块与块内位置记录了登记先后，退出处理器也确实按逆登记顺序推进。不过，完整退出过程还包含回调内部的嵌套调用。

例如，模块终结辅助代码可以进入 `__cxa_finalize`，处理与相应模块关联的已登记记录。这样，外层退出处理器正在执行一条回调时，其中某些其他记录就可能已经通过内层终结路径得到处理。

因此，要解释完整的执行顺序，需要同时看外层逆序遍历、记录的模块归属，以及回调之间的嵌套调用。登记位置提供明确的遍历次序，单独观察位置却不足以还原整个调用过程。

这也让前面预先更新记录状态的意义更具体：多个终结入口可能接触同一批登记记录，记录状态需要让它们协调已经接手或完成的工作。后续遍历再次遇到相应槽位时，可以依据状态决定如何处理。

### 6. 回调返回后，重新取得锁

```asm
0x7ffff7c47a76 <+358>: movl     $0x1, %ecx
0x7ffff7c47a7b <+363>: movl     %r13d, %eax
0x7ffff7c47a7e <+366>: lock
0x7ffff7c47a7f <+367>: cmpxchgl %ecx, (%rbx)
0x7ffff7c47a82 <+370>: je       0x7ffff7c479e6 ; <+214>
; 其后的锁等待分支暂略，等待完成后也转向 <+214>
```

回调正常返回后，执行流来到 `<+358>`。无 Sanitizer 的对照实验实际命中了这里，确认该次动态链接器回调已经返回。

接下来先重新取得链表锁。`%ecx` 准备要写入的锁定值 `1`，`%eax` 准备预期的空闲值 `0`，`lock cmpxchgl` 原子地比较并尝试更新锁。成功则转向 `<+214>`；需要等待时，进入底层锁等待路径，之后再继续。锁等待函数的具体机器码不在这里展开。

### 7. 解锁期间是否发生了新登记

```asm
0x7ffff7c479e6 <+214>: movq  0x1be5b3(%rip), %rax
0x7ffff7c479ed <+221>: cmpq  %r12, %rax
0x7ffff7c479f0 <+224>: je    0x7ffff7c47968 ; <+88>
0x7ffff7c479f6 <+230>: movq  -0x38(%rbp), %rax
0x7ffff7c479fa <+234>: movq  (%rax), %r15
0x7ffff7c479fd <+237>: testq %r15, %r15
0x7ffff7c47a00 <+240>: jne   0x7ffff7c47968 ; <+88>
```

取得锁之后，还需要判断回调期间是否有新的退出方法登记。`<+105>` 保存的计数快照，现在与 `__new_exitfn_called` 的当前值比较。

如果没有变化，就继续当前节点的遍历。如果计数发生变化，则重新读取链表入口，因为新记录可能位于当前数组块中，也可能位于新接入的头节点中。重新从入口查找，可以跟上这次登记后的实际结构。新增登记既可能来自当前回调，也可能来自同时运行的其他线程。

上一段的 TLS 析构循环在回调后直接重读当前线程的链表头；这里面对进程共享的分块数组链表，则配合锁和登记计数决定是否重新查找。两者都需要容纳回调对后续待处理集合造成的变化。

在这一过程中，链表锁保护共享结构访问，登记计数帮助发现解锁期间的新登记，记录状态协调同一项清理的处理情况。回调执行前后的这些安排，使运行库既能管理退出记录，又能把执行权交给包含各种依赖和嵌套调用的清理代码。

接下来进入本次实际选中的动态链接器回调，看看模块的收集、排序与终结是怎样组织的。

### 本段实验补充：Sanitizer 版本为何未返回到断点

以下单独记录额外实验的解释，供审阅和核对使用，不并入上面的叙述主线。

#### 1. 补充调用栈确认的嵌套关系

根据补充实验提供的调用栈信息，按实际调用方向可以整理为：

```text
__run_exit_handlers
    调用动态链接器的 _dl_fini
_dl_fini
    调用 _dl_call_fini
_dl_call_fini
    执行主程序的终结辅助函数
__do_global_dtors_aux
    调用 __cxa_finalize
__cxa_finalize
    调用已登记的 __lsan::DoLeakCheck
```

这是对补充记录的结构化整理，下面保留其中可用于定位的栈帧信息；当前提供的是实验结果摘录，并非完整的 LLDB 原始输出。

| 栈帧 | 记录中的位置 | 可以确认的关系 |
|---|---|---|
| `#0` | `__lsan::DoLeakCheck` | 已进入 LSan 泄漏检查函数 |
| `#1` | `__cxa_finalize +194` | 检查函数由模块关联的回调处理路径调用 |
| `#2` | `__do_global_dtors_aux +39` | 来源为主程序终结辅助代码 |
| `#3` | 动态链接器内部函数 `<+98>` | 结合调用链对应模块终结调用路径 |
| `#4` | `_dl_fini` 对应入口 `<+504>` | 动态链接器终结调度尚未返回 |
| `#5` | `__run_exit_handlers <+358>` | 外层正在等待该回调返回 |

`#5` 的 `<+358>` 是 `<+356>` 调用时压入的返回地址。调用栈显示它，并不表示执行流已经返回并执行该指令。`#4` 中的 `<+504>` 也应按相同原则理解为下层调用后的接续位置。

#### 2. 对此前异常现象的解释

原始 Sanitizer 版本在退出时报告 LeakSanitizer 致命错误，并提示其无法在 `ptrace` 调试环境下正常完成检测。补充调用栈进一步确认，这次泄漏检查是在动态链接器执行主程序终结方法的过程中，经由 `__cxa_finalize` 触发的。

据此，可以把未命中回调后断点的经过解释为：模块终结路径进入 LSan 检查，检查在调试环境中失败并终止进程，执行流未能正常返回外层的 `<+358>`。这一解释结合了此前的错误输出、补充调用栈以及 LSan 的实现行为；调用栈本身没有展示具体失败的底层跟踪操作。

先前“模块已进入终结状态，导致 Sanitizer 代码无法正常执行”的推测，应由上述解释替换。补充实测已经进入 `__lsan::DoLeakCheck`，失败发生在后续检测过程。

去除 Sanitizer 后，对照实验实际命中了 `<+358>`，因此可以继续追踪原生运行库的后续退出路径。

#### 3. 对顺序与状态协调的补充认识

旧版首先选择 `fns[4]` 中的动态链接器回调，但该回调内部又通过模块终结进入 `__cxa_finalize`，触发其他已登记记录。实际调用顺序因此包含嵌套关系，不能只把槽位顺序写成一条扁平调用序列。

这一现象也说明，外层遍历与模块终结之间需要协调记录状态。已经由内层处理的记录，后面不应再次作为待执行回调调用；具体状态检查可结合 `__cxa_finalize` 的实现进一步对照。
