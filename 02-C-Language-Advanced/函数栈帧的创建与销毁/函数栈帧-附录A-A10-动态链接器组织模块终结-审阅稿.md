## 十、动态链接器怎样组织模块终结

```asm
; 动态链接器中对应 _dl_fini 的入口
0x7ffff7fca380 <+0>:  endbr64
0x7ffff7fca384 <+4>:  pushq %rbp
0x7ffff7fca385 <+5>:  movq  %rsp, %rbp
0x7ffff7fca388 <+8>:  pushq %r15
0x7ffff7fca38a <+10>: pushq %r14

; 以下为函数内部几个关键位置，中间指令暂略
0x7ffff7fca509 <+393>: callq 0x7ffff7fd83a0 ; 源码对应：排列模块终结次序
0x7ffff7fca511 <+401>: callq *0x32511(%rip) ; 源码对应：释放加载器锁
0x7ffff7fca573 <+499>: callq 0x7ffff7fc6090 ; 源码对应：调用当前模块的终结入口
0x7ffff7fca5e8 <+616>: retq
```

上一段，退出回调处理器通过间接调用进入了动态链接器。结合函数内部行为与 glibc 源码，这个入口对应 `_dl_fini`。LLDB 在本次实验中显示的仍是未命名符号，下面的名称和职责依据源码进行对应。

### 1. 到这里，换一种阅读方式

最初跟到这个函数时，我只确认了它的大致任务：组织进程中 ELF 模块的终结，考虑模块之间的依赖关系，再依次执行对应的终结方法。至于内部怎样收集信息、实现排序，以及处理各种特殊情况，当时并没有继续逐项追踪。

走到这里，继续逐条阅读汇编的收益已经有所变化。前面关注的是一条指令怎样修改寄存器和栈、参数怎样传递、返回位置怎样保存。现在看到的长段指令，主要在落实动态链接器的数据结构、遍历和管理规则。想理解这些规则，直接查阅对应源码，往往比先从指令中重新拼出整套逻辑更清楚。

因此，这一段保留关键汇编位置作为对照，结合源码说明整体安排。具体排序算法、审计机制及各模块自己的终结代码，就停在这里，不再逐条展开。

### 2. 终结方法也需要其他模块继续提供服务

前面已经把动态链接器管理的主程序、共享库等 ELF 对象称为 ELF 模块。它们在运行期间相互调用，也可能在终结时继续依赖彼此。

假设模块 A 使用模块 B 提供的服务，A 的终结方法也可能需要调用 B，才能完成自己的收尾。如果 B 已经先销毁了相关状态，A 即使还能找到函数入口，也未必仍然具备正常调用这些服务的条件。

所以，终结需要考虑模块之间的依赖：在存在明确依赖的情况下，先完成使用者的终结，再处理它所依赖的模块。模块代码是否仍在地址空间中，与模块内部对象和服务是否仍然可用，是需要分别观察的两件事。

这也解释了为什么不能简单地把最初的初始化过程倒放。程序运行期间可能通过 `dlopen` 加载其他模块，模块集合及其依赖关系已经发生变化。glibc 源码因此在终结阶段重新组织模块次序，以适应退出时实际存在的加载关系。

这套安排依据动态链接器掌握的信息进行。具体业务在指针、回调和对象之间建立的所有关系，并不会自动全部转化为加载器可识别的模块依赖；终结方法自身仍然需要遵守相应的生命周期约定。

### 3. 先准备处理清单，再交给模块执行

从源码整体看，`_dl_fini` 按动态链接命名空间遍历模块。这里的命名空间可以理解为动态链接器分别管理的模块集合及符号查找范围。普通程序主要涉及默认集合，更复杂的加载方式还可以使用其他集合。本文只需要知道，它会按这些管理单位组织处理。

对于当前集合，运行库先在加载器锁保护下取得模块信息，建立临时的模块指针数组。数组元素指向动态链接器保存的模块运行时记录，也就是 `link_map` 对象。随后，根据模块依赖安排数组中的处理顺序。

这样的数组相当于本轮终结的处理清单：既便于排序，后面也可以依据它继续工作，而不用始终沿着原来的加载链表前进。

准备清单时，还会临时增加相关模块的打开计数，避免处理期间模块被卸载。清单保存的是指针，所以除了知道要处理谁，还需要保证使用这些指针时，对应模块仍然存在。

完成这些准备后，动态链接器释放加载器锁，再调用各模块的终结方法。终结代码可能直接或间接进入其他运行库路径，其中也可能需要使用加载器锁。先整理好本轮清单、保护模块生命周期，再释放锁执行，便能为这些调用留下条件。

这里与上一段的安排形成了联系：退出回调管理器调用回调之前释放退出链表锁，动态链接器调用模块终结方法之前释放加载器锁。两把锁保护不同的结构，但都需要考虑把执行权交给外部代码后可能发生什么。

### 4. 从模块次序进入模块自身的终结入口

```asm
0x7ffff7fca530 <+432>: movq  (%r8), %r15
0x7ffff7fca533 <+435>: testb $0x10, 0x354(%r15)
0x7ffff7fca53b <+443>: jne   0x7ffff7fca568 ; <+488>

; 中间为其他推进路径

0x7ffff7fca568 <+488>: movq %r15, %rdi
0x7ffff7fca56b <+491>: movq %rax, -0x40(%rbp)
0x7ffff7fca56f <+495>: movq %r8, -0x38(%rbp)
0x7ffff7fca573 <+499>: callq 0x7ffff7fc6090 ; 对应 _dl_call_fini
```

排序完成后，动态链接器沿数组逐个取得模块记录，结合模块状态判断是否需要执行终结，再把当前记录交给内部的 `_dl_call_fini`。上面的 `<+435>` 对应源码中对初始化状态 `l_init_called` 的检查。

这一层调用主要根据模块动态信息找到相应的终结入口。其中，`DT_FINI_ARRAY` 描述一组终结函数，当前实现从数组末尾向前执行；随后再调用存在的 `DT_FINI` 入口。这里也就从运行库统一组织的过程，进入了模块各自安排的收尾。

模块的终结方法可能处理内部对象、释放资源，还可能通过模块关联的登记机制进一步执行退出回调。具体任务要看对应模块的实现。本文在这里确认调度关系，不继续进入每个模块逐项查看。

需要区分的是两层顺序：`_dl_fini` 安排模块之间的终结次序，单个模块的终结入口再执行其内部安排。加上上一段见过的退出回调嵌套关系，完整退出过程需要结合这些层次来理解。

### 5. 完成模块终结，再回到外层退出处理

```asm
0x7ffff7fca588 <+520>: subl $0x1, 0x350(%r15)

; 各组模块处理完成后，最终恢复本函数的栈与寄存器
0x7ffff7fca5da <+602>: leaq -0x28(%rbp), %rsp
0x7ffff7fca5de <+606>: popq %rbx
0x7ffff7fca5df <+607>: popq %r12
0x7ffff7fca5e1 <+609>: popq %r13
0x7ffff7fca5e3 <+611>: popq %r14
0x7ffff7fca5e5 <+613>: popq %r15
0x7ffff7fca5e7 <+615>: popq %rbp
0x7ffff7fca5e8 <+616>: retq
```

本轮对模块的处理结束后，会相应减去此前临时增加的打开计数。`<+520>` 就是其中一个对应位置。这是在撤销本轮增加的生命周期保护，不能单凭这条指令认定模块已经解除映射。

其余管理分支还涉及审计通知、可选统计输出及一致性检查。本次只保留它们在整体流程中的位置，没有继续研究内部实现。

最后，函数恢复栈和保存的寄存器，执行 `retq`，回到 `__run_exit_handlers` 的回调接续位置。无 Sanitizer 对照实验已经实际命中了外层 `<+358>`，确认该次调用正常返回。

模块终结这一轮工作完成后，退出流程仍在用户态继续推进。外层还需要检查剩余退出记录、处理数组块，并执行后续标准 I/O 收尾。下一段再回到那里，沿着最终的进程终止路径继续向前。
