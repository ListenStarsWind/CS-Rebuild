# 左旋字符串：五种解法

假设存在字符串：

```text
abcdef
```

左旋 2 位以后：

```text
cdefab
```

所有方法在真正处理以前，都先统一做一次：

```text
k %= n;
```

其中 `n` 是字符串长度。

因为左旋满 `n` 位以后，字符串会重新回到原状态，所以真正有意义的旋转次数只需要保留 `0 ~ n-1`。

---

## 1. 解法一：把左旋 k 位看成 k 次左旋 1 位

这是最直接的一种想法。

左旋 1 位：

```text
abcdef
↓
bcdefa
```

处理逻辑非常简单：

```text
1. 暂存首字符
2. 其余字符整体向前移动一位
3. 把暂存字符放到最后
```

那么左旋 `k` 位，就重复执行 `k` 次左旋 1 位。

例如：

```text
abcdef
↓
bcdefa
↓
cdefab
```

这种方法没有复杂结构，就是严格按照“左旋”本身去做。

时间复杂度：

```text
O(n * k)
```

考虑前面的取模以后，更准确一点：

```text
O(n * (k % n))
```

额外空间：

```text
O(1)
```

缺点也很明显：同一个字符会被反复搬动。

---

## 2. 解法二：先把字符串真正看成一个环

这一种最开始的模型，不是从下标公式来的，而是直接准备两倍长度空间，把字符串复制两份，物理上形成首尾相接的效果。

例如：

```text
abcdefabcdef
```

左旋 2 位以后，只需要从原下标 2 开始，连续取一个原字符串长度：

```text
  cdefab
```

结果自然就是：

```text
cdefab
```

所以最初的理解非常直接：

> 先把线性字符串展开成一个首尾相接的环，然后重新确定开头。

真正写程序时当然没必要真的准备 `2n` 长度空间。

因为最终结果无非就是：

```text
[k, n) + [0, k)
```

所以只准备一倍长度的目标空间就够了：

```text
先写后半部分
再写前半部分
```

如果继续抠空间，当然还能只暂存更短的一段，把额外空间继续压低。

但这种小算法里，如果字符串长度本身有明确上限，我更倾向于直接准备定长局部空间。除非本身存在内存池，否则为了省那几个字符去频繁申请和释放动态内存，未必值得。

这一种真正值得保留的是最开始那个模型：

> 左旋本质上只是把一个环重新选定起点。

时间复杂度：

```text
O(n)
```

额外空间通常：

```text
O(n)
```

---

## 3. 解法三：三次逆置

把字符串分成两个部分：

```text
A = [0, k)
B = [k, n)
```

那么原字符串就是：

```text
AB
```

目标是：

```text
BA
```

例如：

```text
abcdef
```

左旋 2 位：

```text
A = ab
B = cdef
```

先分别逆置：

```text
ab      -> ba
cdef    -> fedc
```

于是：

```text
ab cdef
↓
ba fedc
```

再把整个字符串逆置：

```text
ba fedc
↓
cdef ab
```

第一次分别逆置以后，两块内部顺序都被破坏；第二次整体逆置时，一方面两个块整体交换位置，另一方面两块内部又分别被逆置一次，所以内部顺序恢复。

也就是：

```text
AB
↓
A反 B反
↓
BA
```

这一种的核心是：

> 允许中间过程暂时破坏块内部顺序，再利用整体逆置把这种破坏抵消。

时间复杂度：

```text
O(n)
```

额外空间：

```text
O(1)
```

---

## 4. 解法四：块交换

三次逆置的思路是：

> 块内部可以先乱，最后再恢复。

那么反过来可以想：

> 如果我不想让块内部发生逆置，只移动完整块呢？

还是：

```text
AB -> BA
```

如果：

```text
|A| == |B|
```

那么直接交换两个等长块即可。

例如：

```text
ab cd
↓
cd ab
```

真正的问题是两块长度不一致。

当 `A` 比 `B` 短时，例如：

```text
ab cdef
```

可以拆成：

```text
ab | cd | ef
```

交换 `ab` 和 `cd`：

```text
cd | ab | ef
```

此时 `cd` 已经落到最终位置，接下来只需要处理：

```text
ab | ef
```

再交换一次：

```text
ef | ab
```

最终：

```text
cd ef ab
```

也就是：

```text
cdefab
```

当 `A` 比 `B` 长时，例如：

```text
abcd ef
```

拆成：

```text
ab | cd | ef
```

从 `A` 靠近分界线的一侧切出与 `B` 等长的 `cd`，与 `ef` 交换：

```text
ab | ef | cd
```

这时 `cd` 已经落到最终位置，剩下：

```text
ab | ef
```

继续交换：

```text
ef | ab
```

最终：

```text
ef ab cd
```

因此每次块交换以后，较短块都会完成最终重定位，剩余数据长度也会逐渐减小。

因为每次处理的都是完整块，所以块内部原来的先后顺序可以一直保持不变。

这一种和三次逆置正好形成对照：

```text
三次逆置：
允许块内暂时乱序，换取简单控制逻辑

块交换：
块内始终有序，但需要多轮缩小问题
```

理论上仍然可以做到：

```text
时间 O(n)
空间 O(1)
```

但实际写 C 时，它的控制逻辑显然比三次逆置复杂，而没有明显工程优势。

---

# 5. 解法五：循环置换

在前面几种方法里，我们其实已经能隐约发现一件事：

> 字符串发生旋转以后，元素和下标之间的对应关系发生了变化，而且这种变化似乎不是完全没有规律。

先看一个具体例子。

假设：

```text
abcdefghij
```

长度：

```text
n = 10
```

左旋：

```text
k = 3
```

那么原来位于下标 3 的元素，旋转以后会来到下标 0。

所以先有：

```text
0 <- 3
```

再继续看，原来位于下标 6 的元素会来到下标 3。

于是又有：

```text
3 <- 6
```

到这里其实还没什么特别的。

正常情况下，我们很容易把它理解成：

> 左旋以后元素的位置发生变化，所以新的位置要去原来的某个位置拿数据。

甚至会觉得这不就是下标计算的问题吗，好像没什么值得继续研究的。

但如果不急着停在这里，而是继续问一句：

> 既然 `0` 的数据来自 `3`，`3` 的数据又来自 `6`，那这种关系如果一直往后延伸，会不会出现一个更完整的结构？

于是继续追下去：

```text
0 <- 3 <- 6 <- 9 <- 2 <- 5 <- 8 <- 1 <- 4 <- 7 <- 0
```

也可以顺着数据来源方向写成：

```text
0 -> 3 -> 6 -> 9 -> 2 -> 5 -> 8 -> 1 -> 4 -> 7 -> 0
```

这时候才真正出现一个值得注意的现象：

```text
1. 这条链把 0 ~ 9 全部下标都包含进去了
2. 下标之间形成了一条连续关系
3. 更重要的是，这条关系最后又回到了最开始的 0
```

也就是说，它不是一条无限向后延伸的链，而是首尾相接。

于是这里可以产生一个真正能拿来写程序的猜测：

> 既然这些下标最终会首尾相接，那么也许根本不需要准备一整个辅助数组。只要先准备一个临时字符，保存当前即将被覆盖的数据，然后顺着这条关系一个位置一个位置地搬下去，最后重新回到起点时，再把最开始保存的字符填回去，就可以完成这一整条链上的旋转。

例如：

```text
0 <- 3 <- 6 <- 9 <- 2 <- 5 <- 8 <- 1 <- 4 <- 7 <- 0
```

实现时可以理解成：

```text
先保存位置 0 原来的字符

3 写到 0
6 写到 3
9 写到 6
2 写到 9
5 写到 2
8 写到 5
1 写到 8
4 写到 1
7 写到 4

最后把最开始暂存的字符写回最后空出来的位置
```

如果事情永远都是这样，那这个方法其实已经结束了：

```text
准备一个临时字符
顺着一条闭环搬完所有数据
```

但是事情显然没有这么简单。

---

## 5.1 换一种情况以后，原来的“大环”裂开了

继续保持：

```text
n = 10
```

但把左旋距离改成：

```text
k = 4
```

从 0 开始继续按照同样的关系追：

```text
0 -> 4 -> 8 -> 2 -> 6 -> 0
```

这一次没有覆盖全部下标。

它只走了：

```text
0 4 8 2 6
```

就已经重新回到了 0。

而：

```text
1 3 5 7 9
```

还完全没有进入这条链。

继续从另一个还没有处理过的位置开始，例如 1：

```text
1 -> 5 -> 9 -> 3 -> 7 -> 1
```

现在再看，整个 10 个下标最终变成：

```text
0 -> 4 -> 8 -> 2 -> 6 -> 0

1 -> 5 -> 9 -> 3 -> 7 -> 1
```

第一种情况：

```text
n = 10
k = 3
```

得到的是一个覆盖全部下标的大环。

第二种情况：

```text
n = 10
k = 4
```

却变成了两个互相独立的小环。

但是这两个小环合在一起，仍然恰好覆盖了全部下标，而且每一个小环内部仍然首尾相接。

所以到这里，原来的猜测应该继续修正。

在旋转过程中，原来的坐标元素映射关系似乎会：

> 分裂成若干个相互独立，但每个内部又首尾相接的逻辑环。

这才是循环置换真正值得研究的地方。

---

## 5.2 接下来真正需要量化的是“分裂行为”

既然一个大映射可能分成多个环，那么接下来最重要的问题就非常明确：

> 到底会分裂出多少个环？

这个问题不是为了数学上看起来漂亮，而是直接关系到代码怎么写。

如果只有一个环，那么：

```text
做一次循环
沿着这一条链把所有字符搬完
```

就够了。

如果有两个环，就必须分别处理两次。

如果有更多环，也一样。

所以程序真正需要知道的是：

```text
外层到底应该处理多少个独立环
```

也就是说，我们必须把这种“有时一个环、有时多个环”的现象进行量化。

接下来才有必要建立数学模型。

---

## 5.3 把下标变化重新解释成圆环上的固定步长运动

这里如果继续用模运算追下标，会很快变得不直观。

所以换一种更容易理解的模型。

把 `0 ~ n-1` 这些下标真的摆成一个圆环。

这个圆环一整圈共有：

```text
n 格
```

每次固定向前走：

```text
k 格
```

假设一共走了：

```text
t 次
```

那么总路程就是：

```text
tk
```

如果最后重新回到原来的起点，那么总路程一定正好等于若干个完整圆周。

假设完整绕了：

```text
q 圈
```

那么就有：

```text
tk = nq
```

到这里我们已经把“下标映射”改写成了一个更简单的问题：

> 每次固定走 k 格，要走多少次以后，累计路程才第一次刚好等于若干个完整圆周？

因为我们只关心第一次重新回到起点，所以这里要求的是最小的 `t`。

而：

```text
tk
```

显然一定是 `k` 的倍数。

同时，因为：

```text
tk = nq
```

所以它又一定是 `n` 的倍数。

因此，第一次闭环时的总路程 `tk`，就是：

```text
n 和 k 的最小公倍数
```

即：

```text
tk = lcm(n, k)
```

所以：

```text
t = lcm(n, k) / k
```

这里的 `t`，就是一个环走完一圈所需要的步数，也就是一个环里包含多少个下标。

到这里，最自然出现的是：

```text
lcm(n, k)
```

也就是最小公倍数。

---

## 5.4 从最小公倍数继续往下推

现在已经知道：

```text
单个环长度
= lcm(n, k) / k
```

接下来我们真正想要的不是“一个环多长”，而是：

```text
整个 n 个下标最终会分成多少个环
```

环个数就是：

```text
总下标数 / 单个环长度
```

所以：

```text
环个数
= n / t
```

而：

```text
t = lcm(n, k) / k
```

因此：

```text
环个数
= n / [lcm(n, k) / k]
= nk / lcm(n, k)
```

推到这里以后，会自然碰到另一个我们熟悉的量：

```text
gcd(n, k)
```

也就是最大公约数。

已知：

```text
gcd(n, k) * lcm(n, k) = n * k
```

所以：

```text
nk / lcm(n, k)
= gcd(n, k)
```

于是最终得到：

```text
环个数 = gcd(n, k)
```

也就是说：

> 字符串长度 `n` 与左旋距离 `k` 的最大公约数，正好就是这次下标映射会分裂出的独立逻辑环数量。

相应地：

```text
单个环长度
= n / gcd(n, k)
```

---

## 5.5 这一步确实存在一点“跳跃”

从：

```text
最小公倍数
```

突然联想到：

```text
最大公约数
```

再进一步想到：

```text
gcd(n, k) * lcm(n, k) = n * k
```

这一步并不像前面的推导那么自然。

前面：

```text
固定步长
-> 累计路程
-> 整圈
-> 最小公倍数
```

基本都是沿着当前模型一步一步走出来的。

但从最小公倍数继续联想到最大公约数，并利用二者之间的乘积关系去化简，确实需要已有的数论知识作为桥梁。

所以这部分没必要假装成“我从几个例子里自然看出了 gcd”。

更真实的说法应该是：

> 先通过圆环模型自然得到最小公倍数；随后为了把“单环长度”进一步换算成“环的数量”，再借助最小公倍数与最大公约数之间已有的关系，最终得到环数等于 `gcd(n, k)`。

这样整个思路才是连续的。

---

## 5.6 回到前面的两个例子验证

先看：

```text
n = 10
k = 3
```

有：

```text
gcd(10, 3) = 1
```

所以应该只有：

```text
1 个环
```

实际：

```text
0 -> 3 -> 6 -> 9 -> 2 -> 5 -> 8 -> 1 -> 4 -> 7 -> 0
```

确实只有一个大环。

再看：

```text
n = 10
k = 4
```

有：

```text
gcd(10, 4) = 2
```

所以应该有：

```text
2 个环
```

实际：

```text
0 -> 4 -> 8 -> 2 -> 6 -> 0

1 -> 5 -> 9 -> 3 -> 7 -> 1
```

确实正好两个。

这样前面观察到的“一个大环”和“两个小环”，终于有了统一解释。

---

## 5.7 最后再回到代码

现在整个结构已经明确。

对于一次长度为 `n`、左旋距离为 `k` 的字符串旋转：

```text
环个数 = gcd(n, k)
```

所以代码最外层需要处理：

```text
gcd(n, k)
```

个独立环。

对于每一个环：

```text
1. 先保存当前起点即将被覆盖的字符
2. 沿着当前环的下标关系不断搬运
3. 直到这一环重新闭合
4. 把最开始保存的字符填回最后的位置
```

一个环完成以后，再处理下一个环。

直到所有独立环全部处理完成。

因为所有字符最终都只随着自己的环完成一次重新定位，所以总体仍然可以做到：

```text
时间复杂度 O(n)
额外空间 O(1)
```

不过从实际 C 字符串左旋来说，这一套的控制逻辑显然比三次逆置复杂得多。

所以它真正值得保留的地方，不是工程上更优，而是它揭示了一个更底层的结构：

> 一次左旋所产生的下标重排，可以被分解成若干个彼此独立、内部首尾相接的循环；而这些循环的数量，最终由 `gcd(n, k)` 决定。

---

# 6. 最后重新看五种方法

这五种方法真正不同的地方，不只是代码不同，而是观察问题的角度不同。

### 第一种

直接按照操作执行：

```text
左旋 k 位
= k 次左旋 1 位
```

### 第二种

从空间上看：

```text
字符串首尾相接
左旋只是重新确定起点
```

### 第三种

从区间结构看：

```text
AB -> BA
```

允许块内部暂时逆序。

### 第四种

仍然是：

```text
AB -> BA
```

但坚持块内部顺序不变，通过交换等长块逐步缩小问题。

### 第五种

先从具体下标变化里发现“闭环”的迹象，再通过不同参数发现“大环会分裂成若干个独立小环”；随后为了让代码知道究竟要处理多少个环，再建立圆环上的固定步长模型，先得到最小公倍数，最后借助最大公约数与最小公倍数之间的关系，求出：

```text
环个数 = gcd(n, k)
```

所以第五种真正完整的思维过程不是：

```text
下标映射 -> gcd
```

而是：

```text
局部下标变化
-> 继续追踪
-> 发现完整闭环
-> 猜测可以沿环搬运
-> 换参数后发现闭环会分裂
-> 提出“到底分几个环”的程序问题
-> 建立圆环数学模型
-> 求第一次闭合
-> 得到最小公倍数
-> 借助 lcm 与 gcd 的关系
-> 最终得到环数量
```

这才是这一种方法真正值得归档的地方。
