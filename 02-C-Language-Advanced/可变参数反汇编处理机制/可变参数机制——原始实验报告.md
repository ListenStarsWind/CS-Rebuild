## 一、实验目的及讨论缘起

本次实验从下面的 `printf` 调用点展开：

```asm
0x55555566abf7 <+47>: movl   %eax, -0x10(%rbp)
0x55555566abfa <+50>: movl   -0x10(%rbp), %esi
0x55555566abfd <+53>: leaq   0x13edc(%rip), %rdi ; .str
0x55555566ac04 <+60>: movb   $0x0, %al
0x55555566ac06 <+62>: callq  0x55555559ad7c ; __interceptor_trampoline_printf
```

讨论集中在三个问题：

1. 64 位平台如何约定整数、指针和浮点等类型的传参位置，尤其是可变参数如何在寄存器与栈之间定位？
2. `%al = 0` 在调用可变参数函数时究竟表达什么，和 `va_list` 的读取索引有什么关系？
3. 既然参数先通过寄存器传入，为什么函数可能将参数寄存器内容复制到栈上？如果实际只传入少量参数，是否连**没有携带本次有效参数**的寄存器也会被保存？

随后设计一个仅使用少量通用寄存器参数的函数，观察被调用方序言和 `va_arg` 展开的机器指令。原计划还准备浮点可变参数的第二份代码，但看到第一份反汇编后认为已足以观察 `%al` 分支的作用，因此**第二份没有提供实际运行记录**。

## 三、测试程序

以下是讨论中为实验一准备的源代码。它对应“固定参数 `count` + 两个 `int` 可变参数”的测试意图；**未另外上传经过校验的实际源文件**，因此这是对话中保存的实验用代码版本，而非已核对文件哈希的源文件快照。

文件名：`no_fp.c`

```c
#include <stdarg.h>
#include <stdio.h>

__attribute__((noinline))
int probe(int count, ...)
{
    va_list ap;
    va_start(ap, count);

    int a = va_arg(ap, int);
    int b = va_arg(ap, int);

    va_end(ap);

    return a + b;
}

int main(void)
{
    int result = probe(2, 10, 20);
    printf("result = %d\n", result);
    return 0;
}
```

调用 `probe(2, 10, 20)` 时，按 ABI 预期：

| 参数 | 预期传参寄存器 | 说明 |
|---|---|---|
| `count = 2` | `%edi` | 固定参数 |
| `10` | `%esi` | 第一个 `int` 可变参数 |
| `20` | `%edx` | 第二个 `int` 可变参数 |
| 向量参数使用信息 | `%al = 0` | 本调用没有向量寄存器参数 |

其余通用参数寄存器（如 `%rcx`、`%r8`、`%r9`）没有承载此次调用声明的其他参数。它们的位模式可能是任意既存值，**不能称为空寄存器**。

## 五、由机器指令直接支持的观察

### 5.1 向量寄存器保存由 `%al` 的零／非零条件控制

```asm
0x55555555514b: testb  %al, %al
0x55555555514d: je     0x555555555178
0x55555555514f: movaps %xmm0, -0xb0(%rbp)
...
0x555555555174: movaps %xmm7, -0x40(%rbp)
```

**代码结构事实**：如果 `%al == 0`，分支直接跳到 `0x555555555178`，跳过八条 XMM 保存指令；如果非零，则顺序执行保存 `%xmm0`—`%xmm7` 的八条指令。**本次调用按代码语义应设置 `%al = 0`，但提供的 LLDB 文本没有单独记录一次 `register read al`，也没有展示 `thread step-inst` 走过该分支。**

**解释**：此处 `%al` 承载的是本次可变参数调用中向量寄存器传参数量的上界信息；它不是 `va_list` 的 `fp_offset`，也不表示 XMM 寄存器物理上已清空。在当前这份序言中，编译器只检查是否为零，非零时一次性保存八个寄存器，并未按数量逐一选择。

### 5.2 通用参数寄存器保存

```asm
0x555555555178: movq %r9,  -0xb8(%rbp)
0x55555555517f: movq %r8,  -0xc0(%rbp)
0x555555555186: movq %rcx, -0xc8(%rbp)
0x55555555518d: movq %rdx, -0xd0(%rbp)
0x555555555194: movq %rsi, -0xd8(%rbp)
0x55555555519b: movl %edi, -0x4(%rbp)
```

**代码结构事实**：五个潜在的通用寄存器可变参数来源 `%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9` 都被保存；固定参数 `%edi` 另存在 `-0x4(%rbp)`。在本例的调用约定里，真正用于两个可变参数的只有 `%rsi` 和 `%rdx`。

**结论限定**：这证明该机器代码**包含**对剩余通用寄存器的冗余保存，不能仅凭这一份反汇编推论所有编译器、所有优化级别都会这样做，也不能据此声称这些寄存器原本是零或无效数据。

### 5.3 `va_list` 初始化：偏移量与两个区域指针

```asm
0x55555555519e: leaq -0x20(%rbp), %rax
0x5555555551a2: leaq -0xe0(%rbp), %rcx
0x5555555551a9: movq %rcx, 0x10(%rax)
0x5555555551ad: leaq 0x10(%rbp), %rcx
0x5555555551b1: movq %rcx, 0x8(%rax)
0x5555555551b5: movl $0x30, 0x4(%rax)
0x5555555551bc: movl $0x8, (%rax)
```

`%rax` 最初指向 `-0x20(%rbp)`，即本例 `va_list` 状态的存放位置。可对应：

| 字段 | 在 `va_list` 内的偏移 | 初始化值 | 解释 |
|---|---:|---|---|
| `gp_offset` | `+0x00` | `0x8` | 固定整数参数已经消耗一个 8 字节通用寄存器槽位 |
| `fp_offset` | `+0x04` | `0x30`（48） | 浮点／向量寄存器保存区的起始偏移 |
| `overflow_arg_area` | `+0x08` | `%rbp + 0x10` | 从栈上传递的后续参数的起始读取位置 |
| `reg_save_area` | `+0x10` | `%rbp - 0xe0` | 寄存器保存区的逻辑基址 |

这里 `reg_save_area + 8 = %rbp - 0xd8`，正好对应 `%rsi` 的保存位置；`reg_save_area + 16 = %rbp - 0xd0`，对应 `%rdx`。保存区**不必把固定参数 `%rdi` 的原值也复制进去**，因为后续 `va_arg` 不会取固定参数。

即使本次没有浮点参数，`fp_offset` 仍按约定初始化；这不是说向量寄存器里必然存在可读取的合法可变参数。

### 5.4 第一次 `va_arg(ap, int)` 的指针求值

最能说明机制的片段：

```asm
0x5555555551cd: movl   -0x20(%rbp), %eax
0x5555555551d6: cmpl   $0x28, %eax
0x5555555551d9: ja     0x5555555551fd
...
0x5555555551e8: movslq %edx, %rax
0x5555555551eb: addq   0x10(%rcx), %rax
0x5555555551ef: addl   $0x8, %edx
0x5555555551f2: movl   %edx, (%rcx)
...
0x555555555221: movl   (%rax), %eax
```

解释为：

```text
gp_offset <= 40:
    address = reg_save_area + gp_offset
    gp_offset += 8
    a = *(int *)address
否则：
    address = overflow_arg_area
    overflow_arg_area += 8
    a = *(int *)address
```

以上是**为便于理解而作的等价伪代码**，并非原始 C 源码。`0x28`（40）是最后一个 8 字节通用寄存器槽位的起始偏移；再向后一个槽位将超出六个通用寄存器参数槽位的 48 字节范围。

第二次 `va_arg(ap, int)` 使用类似逻辑，起始 `gp_offset` 预计为 16，随后变为 24；最后两次结果相加。

**细节**：这里的 `va_arg` 确实通过 `movl (%rax), %eax` 从内存读取。该内存属于被调用方设立的参数寄存器保存区，而不是调用方最初直接压入的全部参数。这与传统 32 位 `cdecl` 的调用者压栈模型在“最后通过内存取参”这一局部观察上相似，但数据形成路径不同。

### 5.5 关于栈帧与 Red Zone 的补充

入口有：

```asm
pushq %rbp
movq  %rsp, %rbp
subq  $0x90, %rsp
```

但后续局部变量访问可到 `-0x110(%rbp)`。两者相差 `0x80`，等于 128 字节。因此，本反汇编符合借用 System V AMD64 **Red Zone（红区）** 的布局特点：显式分配的 `0x90` 字节之下仍有可利用区域。此处 `probe` 的机器代码没有其他函数调用，属于叶子函数。正式文章如介绍这一点，应注意红区的使用受 ABI 和环境约束，不应泛化到所有栈或所有平台。

## 六、讨论中形成的理解与边界

1. **调用约定与具体指令顺序不同。** ABI 约束调用发生时的参数位置，并不要求编译器必须从左往右、或从右往左逐条准备寄存器。传统 32 位 `cdecl` 的逐个右向左压栈，是另一种典型实现方式。
2. **工程中主动传指针与 ABI 自动改变传值语义不同。** 对大型对象，程序员可以主动选择指针参数，由通用寄存器传递指针；不能把这误写成“ABI 自动把所有大对象转换成指针”。
3. **`va_list` 可类比为多个读取游标。** `gp_offset`、`fp_offset` 和 `overflow_arg_area` 维护不同参数通道的读取状态。`va_arg(ap, T)` 依赖调用代码提供的 `T` 决定应按哪类参数规则读取；它**不能自动识别参数真实类型和个数**。
4. **`%al` 和 `va_list` 不是同一个索引机制。** `%al` 是调用者给被调用者的向量参数使用信息；`fp_offset` 是可变参数读取状态。当前机器代码里 `%al` 决定是否提前保存 XMM 寄存器，这些保存结果才可能被后续 `va_arg` 使用。不能说它们完全互不相关，也不能说 `va_arg` 每次直接读取 `%al`。
5. **提前保存寄存器，是为了让后续取参不依赖传参寄存器始终不变。** 被调用函数内部可能使用、覆盖这些寄存器或调用其他函数。当前 `-O0` 风格的机器代码选择了较直接的预保存机制。
6. **是否能够减少保存，是后续优化实验的问题。** 优化器可能根据函数体精简寄存器保存，甚至将 `va_arg` 计算折叠成直接使用寄存器；目前**没有本实验的 `-O2` 或 `-O3` 实测输出**，不能将这种可能性写成已得到的观察结论。

## 八、供后续正式文章使用的建议

正式文章建议按照“**先发现疑问，再用实验回答**”组织，而不是从一开始就陈列 ABI 规范：

- 先展示 `printf` 前的 `%rdi`、`%esi` 和 `%al`，提出“变参究竟如何被识别和读取”。
